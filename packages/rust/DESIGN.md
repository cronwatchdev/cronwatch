# The Rust port

`packages/rust` is a Cargo workspace whose main crate is `cronwatch` on crates.io: the same library as `@cronwatch/sdk`, for Rust services, from a `main` a crontab runs to an axum service with tokio-cron-scheduler or apalis inside it. It is a port, not a new design, made the way the Ruby gem and the Python, PHP and Go ports were (see their `DESIGN.md`), and like the last three it is made in phases. The Go port is the nearest model: both are compiled, typed and concurrent, and much of `packages/go` (the croner port, the JavaScript regular expression engine, the JSON writer, the store dialects) is carried over nearly line for line. The TypeScript SDK is the source of truth for every behaviour, message and stored byte; when the two disagree, the Rust side is wrong.

Phases 1 and 2 are built (see Phases): the core, the memory store, the blocking client, the SQL store on SQLite, Postgres, MySQL and MariaDB, the pg_cron source, the alert channels and Claude triage. The rest of this file is the design the later phases start from; each updates it as the Go port's phases updated that port's.

## Rules

- Rust 1.85 or newer (`rust-version = "1.85"`, edition 2024), tested on 1.85 and on the current stable in CI. 1.85 is the first release with edition 2024 and is what Debian 13 ships as `rustc`, so a service built with a distribution's toolchain can use the crate; it is some nineteen months old at the first release. The floor is set by the edition and by support, not by any one feature. Cargo's MSRV-aware resolver (resolver 3, the edition's default) reads `rust-version`, so an app on 1.85 is given dependency versions that build there. A crate of the workspace whose dependency needs a newer compiler says so in its own `rust-version` (`cronwatch-sqlx` with sqlx 0.9 needs 1.94; see Storage and Decisions), and the core never follows it up.
- The core crate depends on tokio (`rt`, `time`, `sync`), `getrandom` (run ids, the development token), `jiff` (zones) and RustCrypto's `sha2`, `hmac` and `md-5` (the dashboard's cookie, the alert ids, webhook signatures and SigV4, and the app tag), and on nothing else by default. `sha2` and `hmac` came in with phase 2's channels, optional under `alerts` until the dashboard's cookie needs them always; `md-5` comes with the app tag in phase 4, since nothing before it hashes with MD5. Every other dependency is behind a feature or in a crate of its own (see Crates and features). Cron parsing and fire times are a port of croner 10 (`schedule::cron`, carried over from the Go port's `internal/schedule/cron`), JSON is written and read by `js` (not serde_json, whose numbers and key order differ; see below), and secret redaction runs on `jsre`, the Go port's small backtracking engine with JavaScript's semantics, carried over (the `regex` crate has no lookaround and matches code points, not UTF-16 code units; `fancy-regex` has lookaround but the same units and Unicode classes). `jsre` refuses what it does not implement rather than read it as something else, as the Go engine does.
- `#![forbid(unsafe_code)]` in every crate of the workspace. Nothing here needs `unsafe`: panics are caught with `std::panic::catch_unwind`, Postgres's JSONB is encoded in safe code, and the hashes come from RustCrypto.
- Times are `i64` epoch milliseconds everywhere, as in the SDK and the other ports, so `evaluate` ports line for line and stored rows are identical. Durations are `f64` milliseconds inside (a definition may hold `1.5`, which the SDK keeps), and the public API takes `std::time::Duration` or the SDK's text where Rust code would pass one.
- Anything that leaves the process (store rows, JSON columns, alert JSON) uses the SDK's exact field names, key order and values, so a Node, Ruby, Python, PHP, Go and Rust process can share one database and `@cronwatch/mcp` works against any of them. Each public type's `to_json()` is `JSON.stringify` byte for byte (`js`): numbers as JavaScript prints them (`2` not `2.0`, `1e-7`, `1e+21`, `123456789012345680000`), keys in JavaScript's order (array-index keys first in ascending order, then the rest as inserted; `js::Object` keeps that order), only control characters, quotes and backslashes escaped, and lone surrogates written `\ud83d` where a value holds one (see UTF-16 below). serde_json was weighed and left out of the core: its `f64` output is ryu's (`1e21`, `1.2345678901234568e20`), its maps are sorted or, with `preserve_order`, never put array-index keys first, and a Rust `String` cannot hold the lone surrogate Slack's and Discord's cut bodies carry. JavaScript's digits come from the standard library: `format!("{:e}", x)` is the shortest round-trip form, and `js` lays its digits and exponent out as `Number.prototype.toString` does, so no float-printing crate is needed. A `serde` feature gives the public types `Serialize` and `Deserialize` for an app's own use (returning a `JobSummary` from its own handler, say); the stores and channels never use it.
- A definition keeps its fields in the order they were given. The SDK writes `{ ...defaults, ...options, name }` with `expect` moved last, so the stored JSON follows the object literal an app wrote; Rust has no literal to follow, so job options are a builder whose setters append in the order called (a setter called twice keeps its first place and its last value, as a JavaScript object does), and a Rust process declaring a job writes the same bytes a Node process declaring it with its options in that order does. Fields a newer writer added are kept.
- Alert titles and messages are the SDK's text, character for character, with numbers as `toLocaleString("en-US")` writes them: ICU's rounding, from the shortest decimal digits of the double, half away from zero (the Go port's `format.go`, carried over).
- Lengths and cuts are in UTF-16 code units, as JavaScript counts them (`js::len16`, `slice16`, `tail16`). A cut through a surrogate pair leaves U+FFFD where JavaScript would keep a lone surrogate, which is the character that surrogate becomes once written out as UTF-8, so stored bytes are the same. The two places the SDK sends a lone half on the wire (Slack's and Discord's cut bodies, triage's prompt) keep it through `js::LoneJson`, which cuts in UTF-16 code units and writes a lone half as JSON.stringify does (`\ud83d`), as the Go port's `js.Slice16Lone` and `StringifyLone` do, so even those bodies are the SDK's bytes.
- Secret redaction uses the SDK's patterns, copied verbatim as JavaScript source into `output` and run by `jsre` over UTF-16 code units, so a quantifier counts an emoji as two, `\s` is JavaScript's set, `\b` and `/i` are ASCII-only as they are in JavaScript without the `u` flag, and every one of `conformance/output.json`'s 204 redaction cases gives the SDK's bytes.
- Every condition opens once and closes with a recovery. No repeat alerts. A job whose schedule is removed while missed is open has missed closed by the next check with a recovery of its own (`reason: "unscheduled"`).
- Errors are returned as `Result`, never panicked, for a bad option, a bad schedule or a store failure. A job's function returns `Result<T, E>`; an `Err` fails the run and is handed back from `run`. A panic in a job's function is recorded as a failed run (`panic: <message>`) and then resumed with `std::panic::resume_unwind`, so no run is left `running` to be reported stuck later; under `panic = "abort"` nothing can be recorded, and the run is reported stuck at its timeout, as a killed process's is. The store failing never stops a job: store errors go to the error handler, and the job's own outcome is returned.
- An error is written `Name: message`: the last path segment of the error's type name, without generics, when the job's `E` is a concrete type (`std::any::type_name`, taken before anything is boxed), and `Error` for `Box<dyn Error>`, `anyhow::Error`, `String` and `&str`. Many Rust error types are called `Error` (`std::io::Error`, `sqlx::Error`), so `Error: ...` is common, as it is for the Go port's standard library errors. An error's `source()` chain is not written; its `Display` is the message. Rust errors carry no frames on stable, so a returned error has none; a panic has frames only when the app opted in (see Where it cannot match the SDK).
- The environment is read in one place, `env.rs`: the first of `CRONWATCH_ENV`, `APP_ENV` and `RUST_ENV` that is set (the SDK reads `NODE_ENV`; `RUST_ENV` is the Go port's `GO_ENV`, a name some Rust deploys set); `development`, `dev`, `local`, `test` and `testing` are development and `prod` is production, as in the Go and PHP ports. A debug build is not development: `cfg!(debug_assertions)` says how the code was compiled, not where it runs. The other reads are the SDK's own: `CRON_SECRET`, `CRONWATCH_TOKEN`, and triage's `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL`.
- `Send + Sync` throughout: the client, a job, a run handle, a job context and every store. `Client` and `Job` are cheap `Clone` handles (an `Arc` inside), so an app keeps one in its state and clones it into tasks.
- No em or en dashes anywhere, as in the rest of the repo.

## Crate name and releases

`cronwatch` is free on crates.io (checked 2026-09-28: `crate "cronwatch" does not exist`), as are `cronwatch-sdk` and every other name below. The core takes the plain name, which matches the gem and the import names of the Python and Go ports and gives `use cronwatch::...`. crates.io's policy discourages publishing an empty crate to hold a name, so nothing is published as a placeholder: the name is taken by the next batched release, 0.7.0, once phase 1 works; until then it could be taken by someone else. If it is, the fallback is `cronwatch-sdk`, the PyPI package's name, with `[lib] name = "cronwatch"` so code still writes `use cronwatch::...`, as the Python package is imported as `cronwatch`. cronwatch.io is an unrelated hosted product; the crate's description and README say this is the library behind cronwatch.dev, as the other packages' do.

crates.io reads a crate from the tarball `cargo publish` uploads, not from a repository, so a crate in a subdirectory of a monorepo needs no split repository (the PHP package's case) and no tag prefix (the Go module's). The release's own tag `vX.Y.Z`, which `scripts/release.mjs` makes, is the only tag; each crate's tarball carries `.cargo_vcs_info.json` naming the commit it came from. Every crate of the workspace is released at the release's version: `[workspace.package] version` in `packages/rust/Cargo.toml` is the one place it lives, each crate inherits it (`version.workspace = true`), and the crates require each other at exactly that version through `[workspace.dependencies]` (`cronwatch = { path = "cronwatch", version = "=X.Y.Z" }`), so a release's crates always come together. `cronwatch::VERSION` is `env!("CARGO_PKG_VERSION")`, so it needs no row of its own.

`scripts/release.mjs` gets its two rows in phase 1, with the workspace's `Cargo.toml` (the script refuses to run while a directory under `packages/` lacks them, so until then this file alone holds up a release): in VERSIONED, `packages/rust/Cargo.toml`'s `[workspace.package]` version and the `=X.Y.Z` pins in `[workspace.dependencies]`; in PUBLISH, the line that says the pushed tag publishes the crates. Publishing is `.github/workflows/crates.yml`, on a pushed `v*` tag, off until the repository variable `CRATES_ENABLED` is `true`, as `pypi.yml` is: it checks that the workspace version is the tag's, runs the checks, and runs `cargo publish --workspace` (Cargo 1.90 or newer publishes a workspace's crates in dependency order: `cronwatch`, then `cronwatch-sqlx`, then the integrations) with a token from crates.io's trusted publishing (`rust-lang/crates-io-auth-action`), so no long-lived token is stored. Trusted publishing is set up per crate on crates.io and a crate must exist first, so the first release is published by hand (`cargo login`, then `cargo publish --workspace`), after which the owner adds the repository and workflow as a trusted publisher on each crate and turns the variable on. A crates.io release cannot be deleted, only yanked, which is one more reason nothing is published before phase 1 works. `Cargo.lock` is not committed, as the other ports' lock files are not; CI resolves the newest versions each toolchain allows, and a minimal-versions job holds the lower bounds honest (see Testing).

## Crates and features

A workspace, not one crate with every integration behind a feature, because a crate that takes another crate's types in its public API is tied to that crate's major version: `cronwatch-sqlx` takes the app's `sqlx::PgPool`, so it must be built against the app's sqlx, and sqlx 0.8 and 0.9 are different types. Keeping those in crates of their own means a new sqlx or apalis moves one small crate's requirement and `rust-version`, never the core's. What only needs the core's own dependencies, or small, stable ones (`http`, `tower-service`), is a feature of the core. Unlike Go, a crate's dev-dependencies never reach the apps that depend on it, so the drivers the tests use need no module of their own.

The core's features, none on by default:

- `alerts`: the alert channels (Slack, Discord, the webhook, Resend, Postmark, SendGrid, Mailgun, SES, Twilio, Sentry, Honeybadger, Datadog, Rollbar, Bugsnag, New Relic) over the `Transport` trait, plus the default transport on reqwest 0.13 (no default features; `rustls`, which is aws-lc-rs and so needs a C compiler, and `gzip`), with `url` for fetch's URL parsing and `sha2` and `hmac`. `Console` and custom channels need no feature.
- `triage`: Claude triage over the same transport (implies `alerts`'s transport, not its channels).
- `tower`: the dashboard and a job's handler as `tower::Service<http::Request<B>>` for any `B: http_body::Body` (brings `http`, `http-body`, `http-body-util`, `bytes`, `tower-service`), which hyper, axum, tonic's HTTP stack and `lambda_http` all take.
- `axum`: implies `tower`, and reads axum's `NestedPath` and `OriginalUri` to find where the dashboard is mounted (see Dashboard); `Routes::into_router()`.
- `blocking`: a blocking client for programs with no runtime of their own (see The Rust API). Built in phase 1.
- `regex`: `expect_match` accepts a `regex::Regex` (any type implementing `cronwatch::Matcher` works without it).
- `serde`: `Serialize` and `Deserialize` on the public types, for the app's own use.
- `storetest`: the store contract test (the SDK's `store-conformance.ts`), the `store.json` replay and the finish-once scenarios, exported for stores of the app's own, as the Go port's `storetest` package is. Built in phase 1: `storetest::run(make)`, `storetest::replay_fixture(text, make)` (the caller hands it the fixture's text, since a published crate cannot read the repository) and `storetest::finish_once(shared)`.

Phase 1 has `blocking` and `storetest`, phase 2 `alerts` and `triage` (which share a hidden `__transport` feature: reqwest, `url`, and `idna_adapter` held at 1.1, see Decisions); each other feature comes with the phase that builds it, and `regex` and `serde` with the audit, so no feature ships empty.

## The Rust API

```rust
use cronwatch::{Client, JobOptions};
use cronwatch_sqlx::SqlStore;

let store = SqlStore::postgres(pool.clone());        // the app's sqlx::PgPool
let cw = Client::builder()
    .store(store)                                     // default: a MemoryStore
    .alert(cronwatch::channel_fn("pager", page))      // default: Console
    .retention("30d")
    .build()?;

let nightly = cw.job("nightly-report", JobOptions::new()
    .schedule("0 2 * * *").timezone("UTC")
    .grace("15m").timeout(Duration::from_secs(30 * 60))
    .expect("Report written").budget("cost", 2.0)
    .failures_before_alert(1))?;

let path = nightly.run(|job| async move {
    let path = build_report(job.cancelled()).await?; // job.cancelled() resolves at the job's timeout
    job.log(format!("Report written: {path}"));
    job.metric("cost", 1.2);
    Ok::<_, ReportError>(path)
}).await?;

let result = cw.check().await?;          // missed and stuck runs, retries, pruning
cw.start(Duration::from_secs(60));        // a task that checks every minute (long-running services)
cw.silence("nightly-report", Duration::from_secs(2 * 3600)).await?;
```

The shape follows Rust's conventions while keeping the SDK's names recognisable: `cronwatch({...})` is `Client::builder()...build()`, `cw.job(name, options)` is `cw.job(name, options)`, `job.run(fn)` is `job.run(fn).await`, and `recordRun`, `resumeRun`, `jobsWithRuns` and `jobSummary` are `record_run`, `resume_run`, `jobs_with_runs` and `job_summary`. Every call that can reach the store is `async` and returns a `Result`.

- *A builder for the client, an ordered builder for jobs.* For jobs it is how a definition keeps its fields in the order given (see Rules). For the client it keeps the SDK's three-way options readable: `cron_secret(s)` and `no_cron_secret()` where the SDK has a string, `null` and absent; `redact(fn)` and `no_redaction()` where it has a function and `false`; `deliver(Deliver::AtCheck)`. `defaults(JobOptions)` takes `grace`, `timeout`, `timezone` and `failures_before_alert`, and `build()` refuses others with an error.
- *Durations* take the SDK's text or a Rust duration through `impl Into<DurationSpec>`, implemented for `&str`, `String`, `std::time::Duration` and plain milliseconds (`u64`, `i64`, `f64`): `grace("15m")`, `grace(Duration::from_secs(900))` and `grace(900_000)` all compile; text is stored as written and a `Duration` as its milliseconds, as the Go and Python ports store theirs.
- *Expect* is three setters: `expect(text)` (contains), `expect_match(m)` for anything implementing `cronwatch::Matcher` (`regex::Regex` with the `regex` feature; stored as `matches /source/`), and `expect_fn(|output| bool)` (stored as `custom function`; a panic in it fails the run with `Output check threw: ...`).
- *Job functions* are `FnOnce(JobContext) -> impl Future<Output = Result<T, E>>`. `JobContext` is a cloneable handle (log, metric, `cancelled()`, `is_cancelled()`), so the future owns it and needs no borrow; async closures (Rust 1.85) were weighed and left out, since a future from an `AsyncFnOnce` bound cannot be required to be `Send` on stable Rust, and a job's future must be to run inside `tokio::spawn`. `run` asks nothing of the function's future, `T` or `E` beyond `T: 'static` (to tell a returned `String` by `Any`) and `E: Display`: its own future is `Send` whenever they are, so it can be spawned, and a job whose future is not `Send` can still be awaited in place. `run` takes no run id: that is `StartOptions::id`, for `start` only, so the Go port's runtime refusal (`WithRunID is for Start`) is a type error here. `cw.run(name, Option<JobOptions>, f)` runs a job by name, declaring it on first use, and answers `Result<Result<T, E>, Error>`: the outer error is a declaration the SDK refuses, the inner the function's own. The context is also set as a tokio task-local for the run, so code deep in a call chain finds it with `cronwatch::current()`. `cancelled()` resolves at the job's timeout, the SDK's `signal`: the function decides what to do, as a JavaScript function decides what to do with an aborted signal; the future is not dropped. A `String` or `&str` the function returns is the output when nothing was logged (and what `expect` checks); `Job::run_http` is `run` for a function that returns an `http::Response` (the `tower` feature), failing the run with `HTTP <status> <reason>` at 400 or more, as the SDK does for a fetch `Response`.
- *Dropped futures.* Rust cancels a future by dropping it, which Go and JavaScript have no counterpart for: a `run` inside `tokio::time::timeout`, or in an axum handler whose client went away, can be dropped at any await. Two rules keep a run from being left half recorded. Everything after the job's function returns (the finish, the state, the alerts) runs in a task of its own that `run` awaits, so dropping `run` then detaches the recording rather than cancelling it (the Go port's `context.WithoutCancel`). And dropping `run` while the function itself is running drops the function's future too; a guard then records the run as failed, `Cancelled: the run's future was dropped before it finished`, from a task on the runtime it started on, rather than leave it `running` to be reported stuck at its timeout (see Decisions).
- *Channels, triage and sources are traits*: `Channel` (`name()`, `send(&Alert, &ChannelContext)`; `channel_fn` wraps an async function, `Console` is the default), `Triage` (`channel_fn`'s counterpart `triage_fn`) and `Source` (`name()`, `sync(&Client)`: a source is handed the client itself rather than the Go port's `SourceHost` interface, since a Rust test can make a real client over a memory store as cheaply as a fake). Trait methods return boxed futures (`BoxFuture<'_, Result<...>>`, a type alias in the crate), so they are object safe for `Arc<dyn Channel>` without the `async-trait` crate; `async fn` in traits is not object safe on stable.
- *Stores* are the `Store` trait, boxed futures likewise. The SDK's two optional methods, `update_run_if` and `compare_and_set_state`, and the Go and PHP ports' `delete_run_if` (which `discard_when` needs, below) are provided methods whose default answers `Unsupported`, where Go checks for an optional interface; the client then falls back to a read and a write, as the SDK does. `MemoryStore` and `SqlStore` implement all three.
- *A run given back*: `RunOptions::discard_when(|err| bool)` takes a run back rather than judge it when the function returns an error the predicate answers true for, for an attempt a queue gives back without failing. It is the Go port's `DiscardWhen`, rule for rule: the running row is deleted with `delete_run_if`, nothing is judged or alerted, the job's state is left as it was, and the error is still returned.
- *Writing a declaration now*: `cw.sync_job(name)` writes the job declared in this process to the store unless the store already holds that definition (compared as JSON, keys in any order), and says whether it wrote, as the Go port's `SyncJob`; the integrations use it.
- *Nullable values are `Option`* in `Run`, `JobState` and `JobSummary`. A state's `pending_recovery` and `undelivered` are `Option<Vec<_>>`, `None` for a state written before the fields existed, as the Go port's nil slices are; `null` there reads as absent, as it does in Go, which the SDK's own states never write. Unknown keys a newer writer added are kept in their places and written back.
- *Errors* are `cronwatch::Error`, cheap to clone so a shared check hands every caller the same one: `Invalid` (an option, name, schedule or run id the SDK refuses, with its message), `Store` (the store's own error, kept as its source) and `Other` (a definition that cannot be evaluated, a check that panicked, a state that kept changing). A store, channel, triage or source returns `BoxError`.
- *The blocking API*, behind `blocking`: `cronwatch::blocking::Client` and its `Job`, for a `fn main` a crontab runs and for sync apps (diesel, a CLI). It owns a current-thread tokio runtime on a thread of its own, as `reqwest::blocking` does; `job.run(|job| ...)` takes a plain closure that runs on the calling thread, and the store calls go to the runtime. `blocking::Client::new(builder)` takes the async client's builder, and `blocking::Client::with_async(|| async { .. })` makes the builder on the client's runtime, for a store that needs one to be made (a sqlx pool). Every call waits by parking the calling thread (a small executor of its own, not tokio's `block_on`), so it never panics or deadlocks inside another runtime either, where the draft had it return an error: it works there, blocking one of that runtime's threads, which its documentation says to avoid. A job function that is async can use the async client with `#[tokio::main]`, which is two lines; the blocking client is for code that has no runtime and does not want one.

There is no global client (the Python port's `configure()`): an app puts its `Client` in its state (axum's `State`, a `OnceLock`) and clones it.

## Runs that span calls

`job.start(StartOptions { trigger, id })`, `job.resume(run_id)` and `cw.resume_run(name, run_id)` are the SDK's `start()`, `resume()` and `resumeRun()`, and return a `RunHandle`: `id`, `job`, `started_at`, `is_active`, `log`, `metric`, `flush`, `finish`, `finish_with(result)` and `fail(err)`, following `client.ts` and the Go port's `handle.go` rule for rule: a start with an id holds a per-process entry keyed by the job and the id while it reads the store and inserts; `finish` reads the stored run again, joins its output with the handle's (capped) and merges metrics (the handle's win); `flush` writes only over a row still running and of this job; the store never fails out of `start`, `resume`, `flush` or `finish` (failures go to the error handler as `recording <job>`, `starting <job>`, `resuming <job>`, `flushing <job>` or `finishing <job>`); and a store that fails during `finish` leaves the handle active, lines kept, so it can be called again. A `RunHandle` dropped while active records nothing: it is a handle to a run another call may finish, and a run left unfinished is what the stuck check is for.

A run is judged once, however many processes finish it: the finish is written only over a stored row still `running`, else over one still `timeout`, through `update_run_if`, one conditional `UPDATE`, and only the process whose write lands evaluates. `insert_run` refuses an id already stored. `storetest::finish_once` holds the SDK's multi-process scenarios, run against the memory store in the core and against SQLite, Postgres, MySQL and MariaDB in `cronwatch-sqlx`, each process a store of its own over one database.

## Tasks and state

The client never blocks a job on anything but its own store writes. Every read-modify-write of a job's state goes through `update_state`: holding the job's `tokio::sync::Mutex` (the SDK's `serial()` queue), it reads the state, works out the next one, and writes it only when it changed, with `version` one higher, through `compare_and_set_state` against the version read; a refused write is worked out again from a fresh read, up to 10 times. Only store calls happen under the lock; alerts are sent after it is released. Closing missed and stuck at a run's start happens in a task beside the job, awaited before the finish is written. Concurrent `check` calls share one check, spawned as a task of its own, so a caller whose future is dropped neither fails the check for the others nor leaves a job half checked; each caller awaits the shared result through a `tokio::sync::watch`. A panic in the check (a store's, say) is that check's error, and the next `check` runs a new one. `start(every)` spawns the interval task, the first check after a second and then on the interval (a minute by default, five seconds at least); a second `start` does nothing, and `stop` ends it. The client needs a tokio runtime to spawn on; it takes the current one's `Handle` when built, and `build()` outside a runtime is an error that names the blocking client.

## Delivery

`Deliver::Now` (the default) sends each alert from the process that produced it; `Deliver::AtCheck` queues it in the job's state (`undelivered`, at most 20, the oldest dropped first and reported) for the next check in a process that delivers now. An alert no channel accepted is queued the same way and retried once per check, oldest first; one that no longer describes the job (`staleAlert`) is dropped; one check spends at most 20 seconds retrying across all jobs. Triage is tried once per alert.

Each channel sends in a task of its own under `tokio::time::timeout` of 15 seconds, and triage under 25. Here Rust matches the SDK better than Go can: a send past its time is dropped, which cancels it at its next await (the request, the answer), so the Go port's bookkeeping for a hung channel is not needed and the next alert is sent to it as the SDK sends it. A channel that blocks its thread (synchronous I/O inside an async function) cannot be cancelled this way and holds a worker thread until it returns; the `Channel` documentation says to use `spawn_blocking` for such work.

## Channels

With `alerts`, `cronwatch::alerts` holds the SDK's channels, request for request, each made from an options struct with the SDK's option names in Rust's case (`alerts::resend(ResendOptions { api_key, email: EmailOptions { from, to, .. }, .. })`) and returning an `Arc<dyn Channel>` (what `ClientBuilder::alert` takes) or the SDK's refusal in Rust's words (`alerts::resend needs an api_key`). A boolean the SDK defaults to true is the negative (`skip_recovered` for Sentry and Rollbar), so `Default::default()` is always the SDK's default, as in the Go port. The requests are the SDK's: the same URL, header names and values, and body written by `js`, so the bytes are identical; the same stable alert id (the first 32 hex characters of SHA-256 over job, type and time); the same error text. Header names are lowercase in the `http` crate and on the wire over HTTP/1 through hyper, as fetch sends them, so the Rust requests are nearer the SDK's than Go's, whose client writes canonical case in sorted order; the tests compare each header's name, value and position.

Every request goes through `alerts::post`, a transport-free port of the Go port's `internal/post` and its audit's hardening, over a `Transport` trait (one POST: URL, headers in order, body; it answers a status and a body read a chunk at a time, so `post` itself holds every transport to the deadline and the cap). An options struct's `transport` is `Option<Arc<dyn Transport>>`; `ReqwestTransport::new()` is the default and `ReqwestTransport::with_client(c)` wraps an app's own `reqwest::Client`:

- One deadline for the whole request, connecting, sending and reading the answer: ten seconds (`post::TIMEOUT`) inside the channel's own. Past it before an answer is `The operation was aborted due to timeout`, fetch's message; past it while the body arrives is the answer with no body.
- A redirect is refused, not followed: the default transport is a `reqwest::Client` built with `redirect::Policy::none()`, and a 3xx is an answer outside 2xx like any other, so credential headers never go where it points. reqwest cannot turn redirects off per request, so an app's own client given to `with_client` follows them unless it was built with `Policy::none()`, which its documentation says. The default transport keeps no idle connections, since a pooled connection belongs to the runtime that opened it.
- At most 1 MiB of an answer is read, chunk by chunk, so a gzip answer cannot grow without bound.
- TLS is never turned off: the default transport is reqwest on rustls with the platform's roots; an app's own `reqwest::Client` (a proxy, a custom root) is its own choice.
- The URL is read with the WHATWG parser (`url`), as fetch reads it (a space inside is encoded and posted, `javascript:` is refused as `not javascript:`, a user name is refused), and must be `http` or `https` with a host, never quoted in an error, since a webhook URL's path is its credential. Only the URL's origin appears in any error; reqwest's errors quote the whole URL, so every one goes through `reqwest::Error::without_url` and the port of Go's origin-only rewriting for any text a transport adds.
- Credentials are trimmed of the spaces and newlines a paste leaves; a header value with a CR, LF or NUL left inside is refused, naming the header, never its value.
- Every secret the channel holds is cut out of a quoted answer before the answer is cut to 200 UTF-16 units on a code point.

Twilio texts every number at once, a task each, and follows the SDK's segment fitting and partial-delivery report. Twilio's sends are a tokio `JoinSet`, so dropping the send aborts them all and a panic is only that number's failure. `alerts` replays every case of `conformance/channels.json` (619 cases) through a recording `Transport`, and a hardening suite runs every channel against real local servers (tokio listeners, in the tests): a redirect refused by all fifteen, the deadline before an answer and while a body drips in, a 64 MiB gzip answer read to exactly 1 MiB, the URL and header refusals, only the origin in an error, an untrusted certificate refused (made at run time with `rcgen`, no key committed), a secret straddling the cut, and Twilio's partial delivery through a real client. `tests/alerts.rs` sends a failed run through triage to Slack over a transport written outside the crate.

## Triage

`cronwatch::triage::anthropic(AnthropicOptions { .. })` is `triage/anthropic.ts` without an Anthropic client, as the Go and PHP ports do it: the Messages API is one POST, so it sends the request the official client makes (`conformance/triage.json`'s `wire` cases, made for the PHP port): the same URL with `?beta=true`, `anthropic-version`, `anthropic-beta` for the fallback beta, `x-api-key`, and the body byte for byte, with `cronwatch-rust/<version>` as the user agent. The defaults are the SDK's (model, effort, tokens, the prompts, the `<job_data>` fencing, the fallbacks unless `no_fallbacks`); `max_tokens` is an `Option`, and `Some(0)` is sent as 0, as the SDK sends it, where the Go port reads 0 as unset. One attempt, no retries, within the smaller of 24 seconds and what the client allows. No Anthropic client crate is needed, so an app takes on nothing for triage but the transport; the tests replay `triage.json`, 17 cases.

## Sources

The pg_cron source is in `cronwatch-sqlx` behind its `pgcron` feature, `PgCron::new(pool, PgCronOptions { .. })`, over a `sqlx::PgPool` only (a source outlives any one caller, so it cannot hold an app's transaction; the SDK's `jobs` option is `jobs`, `job_ids` and `pick`, as in the Go port), `sources/pgcron.ts` line for line as the Go port's is: the SDK's SQL, arrays of cursors passed as text literals (`$1::text::bigint[]`), settings read from `pg_settings`, run ids `pgcron:<prefix><runid>`, the twenty newest runs copied quietly on first sight, the hold for a run queued without a start time, and jobs declared again only when their definition changed (`cronwatch::describe_job`). The tests replay `conformance/pgcron.json` (30 cases), port the SDK's source tests against a fake `cron` schema, and run against a real pg_cron when `CRONWATCH_TEST_PGCRON` is set (CI's stable entry starts one, as the Go job does). The source puts an app's options between its own description, tags and schedule with `JobOptions::merge`, the core's spread of one set of options over another.

## Dashboard

`cw.routes(RoutesOptions { .. })` is the SDK's `cw.routes()`: a `Routes` whose answers are `routes/index.ts` line for line and whose pages are `routes/html.ts` and `routes/timeline.ts` byte for byte, the CSS, the app shell, the icons, the sign-in form and the `<wbr>` after a name's separators included. The options are the SDK's, in Rust's three-way form where the SDK has one: `token(t)`, `no_token()` or neither (reading `CRONWATCH_TOKEN`, `""` counting as unset), `base_path`, `origin` (read as `new URL(value).origin` reads it; anything but http or https is an error from `routes`, with the SDK's message) and `trust_proxy`. A development token is announced once per `Routes` on standard output, where `console.info` writes it.

The core is framework-free: `Routes::handle(web::Request) -> web::Response`, over plain types (the method, the request target as sent, headers as bytes, the body, whether it came over TLS), as the Go port's `Lambda` reads an event without an AWS module. Everything a framework adds is an adapter over that one function, so the golden replay tests the same code every adapter runs:

- `tower`, the first adapter: `Routes` is a `tower::Service<http::Request<B>>` answering `http::Response<Full<Bytes>>`. That is what hyper serves, what axum mounts with `nest_service`, what tonic and most Rust HTTP stacks accept, and what `lambda_http::run` takes, so AWS Lambda needs no code of the crate's own (the Go port had to write `Lambda`; here the app's `lambda_http` does it).
- `axum`, the framework shown first in the docs because it is the most used: `Router::new().nest_service("/cronwatch", cw.routes(opts))`, or `routes.into_router()`. axum strips the mount from the request's path and records it in `NestedPath` and `OriginalUri`, which the `axum` feature reads, so the base path is found from the mount as the Go port finds it from `http.StripPrefix` and a `ServeMux` pattern; without the feature it is `base_path`, else the SDK's `/cronwatch`.
- actix-web, the second most used framework, does not use tower; an adapter there is made only when someone asks for one (see Decisions).

What a request says is read as the SDK reads a fetch `Request`, carried over from the Go port's `routes_request.go` and `routes_origin.go`: the path from the target as sent (hyper keeps it, so a `%2F` in a job name stays one) as the URL parser leaves it, the query as `URLSearchParams` parses it, headers joined as `Headers.get` joins them and compared as Latin-1 bytes, the body as `request.json()` and `request.formData()` read it, read only once a route wants it and capped at 1 MiB and one byte (413 past it, as the Go, Python and PHP ports answer), and the origin from the scheme and `Host`. The style sheet, scripts and icons are the SDK's files copied into `cronwatch/src/web/assets` and read with `include_bytes!` (a published crate cannot reach outside its own directory); `scripts/make-dashboard-icons.mjs --check` and `npm run check:conformance` fail when they differ from the SDK's.

`tests/routes_golden.rs` replays the gem's fixture, `packages/ruby/test/web/golden.json` (57 captures of the SDK's routes over a fixed seed, PNGs as base64), three ways: straight into `Routes::handle`, through the tower service, and through a real hyper server with the dashboard nested in an axum `Router`, its base path found from the mount; every status, header and body matches, `Content-Length` and the server's `Date` aside. `CRONWATCH_TEST_RUST=1 npm test --workspace packages/mcp` drives `@cronwatch/mcp` against `webserver` (seeded, served by axum), as it runs against the other ports' dashboards. A behaviour change lands in TypeScript first, and `TZ=UTC node packages/ruby/test/web/golden.mjs` regenerates the fixture for every port.

## Handler

`job.handler(fn, HandlerOptions { .. })` is the SDK's `handler()`, for a platform cron that calls a URL: framework-free like the dashboard (`Handler::handle`), with the same `tower` and `axum` adapters. It runs `fn(JobContext, web::Request)` as a recorded run with the trigger `"handler"` for each request whose `Authorization` is `Bearer <secret>`, compared in constant time; the secret is the option's, else the client's (`CRON_SECRET` by default, `""` counting as unset); `no_secret()` lets anyone run the job. With no secret and no opt-out, outside development, it answers 503 with the SDK's JSON; a wrong or missing bearer is 401. A run is answered with `{"ok","job","run","status","durationMs"}`, 200 or 500, and the error's first line only when a secret was required, with the headers of the SDK's `json()`. The function may return a response of its own, which is passed through and fails the run at 400 or more with `HTTP <status> <reason>`; a panic is a failed run answered 500, as the SDK answers a throw, since the tower service owns the response and nothing has been sent yet (the Go port's aborted-response case, where a Go handler had already begun writing, has no counterpart). An EventBridge Scheduler invoking a Lambda directly sends no bearer, so its handler takes `no_secret()`, as in the Go port.

## Scheduler integrations

The SDK has none; these follow the Go port's, whose shared rules (declaring entries as jobs, several entries of one name on different schedules being one job without a schedule, tags for the integration and the app, jobs gone declared again without their schedule, workers elsewhere declaring from the store's definition, schedules checked against the scheduler's own fire times, retries as the gem's Sidekiq rules) are the core's `bridge` module, carried over from `cronwatch.dev/go/bridge`: `Watch`, `check_fires`, `app_tag` (the PHP port's `appTag()` character for character, MD5 when empty or long), `unscheduled` and `options_of`. The app is the integration's `app` option, else `$CRONWATCH_APP_ID`, else the executable's file name.

### tokio-cron-scheduler

tokio-cron-scheduler (0.15, the newest; the oldest supported is set in phase 4) runs closures on tokio from cron expressions it parses with the Rust `croner` crate, seconds first (`sec min hour day month weekday`, a year optional), in UTC unless a job is made with a zone; it names jobs only by a UUID, and a job's closure returns nothing, so its start, stop and removed notifications cannot tell a failed run from a good one. The integration therefore stands in for its constructors, as the Go port's River integration stands in for `NewPeriodicJob`: `cronwatch_tokio_cron_scheduler::Watcher::new(&cw, Options { .. })` gives `watcher.job(name, schedule, zone, |job| async move { .. }, options)`, which declares the job and returns a `tokio_cron_scheduler::Job` for the app's `scheduler.add(...)`, whose closure runs the app's future inside `job.run`, so a returned error fails the run and a panic is recorded before it goes on to tokio. `watcher.repeated(name, every, ..)` is `Job::new_repeated_async` and declares `every <interval>`; one-shot jobs are not jobs. The removed notification unschedules a job, and the UUID is kept to map it back to its name.

The expression is passed to both unchanged. croner (JavaScript) reads six fields as seconds first too, so what CronWatch expects is what the scheduler runs, but the two croners are separate implementations by the same author, so each schedule is checked with `bridge::check_fires` against the scheduler's own next ticks (from the `croner` crate the scheduler already depends on, in its zone), and one that differs is reported and watched without a schedule, as the Go port does for robfig/cron. A zone is given as an IANA name and turned into the `chrono_tz::Tz` the scheduler wants inside the integration, so the job and the scheduler cannot disagree on it. `watcher.check_job(every)` is a job that runs `sync` and a check, never itself a job; a service can also just call `cw.start(every)`. The tests run a real scheduler with a paused tokio clock: runs, errors, panics, jobs removed while it runs, a zone around New York's clock changes, and two apps on one store.

### apalis

apalis runs tower services as workers over storage backends, and apalis-cron gives a worker a schedule as its backend (`WorkerBuilder::new(name).backend(CronScheduler::new(schedule))`). apalis 1.0 is at release candidate 10 as this is written (apalis-cron at 1.0.0-rc.9, with MSRV 1.85 and sqlx 0.9); the integration targets 1.0 if it has shipped by phase 4, else the release candidate (see Decisions). Two parts:

- *A layer.* `cronwatch_apalis::Watch::layer(&cw, Options { .. })` is a `tower::Layer` for `WorkerBuilder::layer`, recording each attempt of the worker's jobs as a run of the job named by the worker (or by `Options::name`), with the run's `JobContext` as the task-local, so the handler can log and add metrics through `cronwatch::current()`. Added after `.retry(...)`, it sits inside the retry layer, so every attempt is a run of its own: failing attempts open one failed alert and the one that succeeds closes it, as the gem's Sidekiq rules have it. It works for any backend, so a queued job on apalis's Postgres, MySQL, SQLite or Redis storage that the app names in `Options::jobs` is watched too, and a worker in a process of its own declares from the store's definition (`bridge`'s workers-elsewhere rule).
- *A schedule.* apalis-cron takes any schedule implementing its schedule trait, so `cronwatch_apalis::schedule("0 2 * * *", "Europe/London")` gives it CronWatch's own croner port: the worker runs on exactly the fire times CronWatch expects, and no conversion or fire check is needed. A worker given a schedule of another kind (the `cron` crate's, an English routine, the builder's) is converted where its source text is available and checked with `check_fires`, and watched without a schedule otherwise, reported once.

`cronwatch_apalis::check_worker(&cw, every)` is a cron worker that runs `sync` and a check. The tests run workers on a paused clock and, when `CRONWATCH_TEST_PG` is set, on apalis's Postgres storage: a job failing twice then succeeding (three runs, one alert and its recovery), a panic, a queued job opted in by name, and a worker in another process keeping the scheduler's definition.

### A plain crontab

A program a crontab runs needs no integration: `#[tokio::main]`, declare the job, run it, exit non-zero on the error, and a second crontab line runs `cw.check()`, both on a store both processes reach; or the same with the blocking client and no runtime of its own. `examples/crontab` is that program on SQLite, with a test that runs its two commands on one file. A command-line tool wrapping a shell command (`cronwatch run nightly -- ./backup.sh`), which `cargo install` would make easy to ship, is made only if someone asks for it (see Decisions).

## Storage

`MemoryStore` is `stores/memory.ts`: a mutex, clones in and out, names sorted by byte order, the same prune rule.

`cronwatch-sqlx` keeps the same three tables in the app's database through sqlx, with the app's pool: `SqlStore::sqlite(pool)`, `SqlStore::postgres(pool)` and `SqlStore::mysql(pool)`, each behind the crate's feature of the same name (which turns on sqlx's; `sqlite` turns on `sqlite-bundled`, not sqlx's extras), and `.prefix(p)` for the table prefix (the SDK's rule and message). Every statement is written from a `Dialect` (`sql.rs`), rows are read and parameters bound through one type shared by the three databases (`rows.rs`), and SQLite's one connection is `sqlite.rs`; phase 1 built SQLite and phase 2 Postgres and MySQL. The constructors are plain calls, and the tables are made when the client first calls `init`. sqlx's `mysql-rsa` feature, which MySQL 8.4's default sign-in without TLS needs, is left to the app (it brings the `rsa` crate and its advisory, RUSTSEC-2023-0071); the tests turn it on as a dev-dependency, and the crate's README says to turn it on or use TLS. sqlx was chosen over a crate per database (rusqlite, tokio-postgres, mysql_async) because it is one API for all three, async on tokio, the most used SQL crate in Rust services, and what apalis's own storage uses; an app on another driver can implement `Store` (the contract test is exported) or ask for a store over it.

- *The schema, byte for byte.* The SQLite and Postgres statements are `stores/sql.ts` text for text: the same `CREATE TABLE IF NOT EXISTS` text for `jobs`, `runs` (with `seq BIGSERIAL` first on Postgres) and `state`, the same two indexes, so `sqlite_master` reads the same whoever created the tables; `INTEGER` or `BIGINT` times, `TEXT` or `JSONB` JSON, `rowid` or `seq` breaking ties, names sorted `COLLATE "C"` on Postgres; `init` under `pg_advisory_xact_lock(hashtext('cronwatch:<prefix>'))` so many processes can start at once. The MySQL dialect is the PHP and Go ports' (MySQL 8.0.13 or MariaDB 10.6 or newer: `utf8mb4_bin`, JSON as `LONGTEXT` holding the SDK's bytes, never MySQL's `JSON` type, `ON DUPLICATE KEY`, the prune's newest start per job as a derived table, compare-and-set from version 0 in two steps, a landed write read back when MySQL counts changed rather than matched rows, `trigger` as `VARCHAR(255)`), copied from `packages/go/sqlstore/sql.go`, which is `packages/php/src/Store/Sql.php`'s.
- *JSONB without a cast.* node-postgres sends parameters untyped and Postgres infers `jsonb`; sqlx sends a `String` typed as `text`, which a `jsonb` column refuses. Rather than add `::jsonb` casts (and so change the statements' text), the store binds JSON through a small type of its own that tells sqlx it is `JSONB` and encodes it in Postgres's binary format (a version byte, 1, and the text). Reading, the JSON is taken as Postgres returns it and parsed with `js` in the order the database gives the keys (Postgres reorders them; everything written is the SDK's order).
- *SQLite.* The store holds one connection for its statements, in turn, as the SDK's and the Go port's do: the pool's connections would each need the pragmas, an in-memory database is one per connection, and SQLite has one writer at a time anyway. That connection is put in WAL mode with the SDK's retry of a busy database while switching (`busy.ts`), then `busy_timeout` 5000 and `synchronous` NORMAL. sqlx builds SQLite from source (`libsqlite3-sys`, bundled), so an app needs a C compiler, as every SQLite crate asks.
- *Postgres and MySQL.* Each statement runs on the pool on its own, in autocommit, so the store's writes never join a transaction the app has open, and `delete_job` is one transaction of the store's own. Rows are read by column name whatever type the driver gives.
- *Foreign rows.* A row of another shape than the SDK writes, valid JSON all the same, is read as the SDK reads it rather than failing every read it is part of, as the Go port's audit fixed there. MySQL's `utf8mb4_bin` columns come back flagged binary, so everything but numbers is read as bytes and taken as UTF-8; a MySQL write whose answer was lost counts as written when the stored row equals what was sent, as the PHP port does; Postgres writes a large JSONB number out in full (`1e21` is stored as `1000000000000000000000`), which reads back as the SDK's bytes.

sqlx 0.9 needs Rust 1.94, which becomes `cronwatch-sqlx`'s `rust-version`; the core stays at 1.85. Only sqlx 0.9 is supported (see Decisions); sqlx 0.8, through renamed dependencies behind features, was weighed and left out.

`cronwatch-sqlx`'s tests run, per database, the contract test (`storetest::run`), the `conformance/store.json` replay, the finish-once scenarios over several stores on one database, a client end to end, a run surviving the app's rollback, and rows of another shape (`tests/servers.rs`, each test on tables of its own prefix, dropped at the end): SQLite always, Postgres, MySQL and MariaDB when `CRONWATCH_TEST_PG`, `CRONWATCH_TEST_MYSQL` and `CRONWATCH_TEST_MARIADB` are set. Its node-compat test has the built SDK and the Rust store replay the same calls into two SQLite files and compares what each reads of the other's and every column's bytes and SQLite type, and has a Node client and a Rust client take turns on one file and one job's state version, as the Go port's does.

## Zones

Rust's standard library has no time zones. `jiff` gives them: it reads the system's zone database (`/usr/share/zoneinfo`, or `$TZDIR`) and, with its `tzdb-bundle-platform` feature, bundles the database only on Windows, which has none; it looks names up without regard to case, as `Intl` does, and takes fixed offsets. The croner port uses it only for the offset at an instant and the transitions around one (croner's `fromTZ` rule is the port's own), and the process's own zone comes from `$TZ` or `/etc/localtime` through jiff, as Go's `time.Local` does. A TZif reader of the crate's own (a few hundred lines, and a POSIX TZ string parser for the rules past the last transition) was weighed: it would drop the dependency, but jiff is small, has no required dependencies, is maintained by the author of `regex`, and gets the database's corner cases right; the owner accepted it (see Decisions).

## Keeping in step

`conformance/` at the repo root holds JSON cases generated from the TypeScript build by `scripts/conformance.mjs`. The Rust tests replay every case, comparing values as the JSON the SDK writes, byte for byte, reading the files from the repository (`env!("CARGO_MANIFEST_DIR")/../../../conformance`; each crate's `include` list keeps them and the tests out of the published tarball): `duration.json` and `schedule.json` against `schedule`, `output.json` against `output`, `evaluate.json` (every scenario's events played through the pure functions, as the script's `Sim` plays them), `format.json` and `health.json` in the core, `store.json` against every store, `channels.json` in `alerts`, `triage.json` in `triage` and `pgcron.json` in `cronwatch-sqlx`. A test fails when the SDK writes a fixture file this port does not know. The tests run with `TZ=UTC`, as the fixtures are made; `cargo test` cannot set the process zone before the harness starts, so the workspace's `.cargo/config.toml` sets `TZ = "UTC"` in `[env]` and a test checks it. A behaviour change lands in TypeScript first, `npm run conformance` regenerates the fixtures, and this workspace is fixed until they pass. Nothing new is expected in the fixtures for this port: the PHP and Go ports already added what a port without the official clients needs (`triage.json`'s `wire` cases).

Croner parity is also checked against croner itself, as the Go port's `fuzz_test.go` does: 3,000 expressions from three fixed seeds in zones with and without daylight saving, from times around the clock changes, where the SDK in Node (reading `packages/sdk/dist`) must give the same error message or the same fire times; it skips, with the reason, when `node` or the built SDK is missing. The same generator runs against the Rust `croner` crate as a report, not a gate, so the design's reason for porting rather than depending (below) stays measured.

*Why port croner rather than use the `croner` crate.* The crate is by croner's author and is what tokio-cron-scheduler uses, so it was the first thing weighed. It is a separate implementation, not a translation of croner 10: its options, its error messages, its reading of some forms (`?`, `W` and `L` combinations, `+`, a seventh field, legacy day matching) and its fire times around clock changes are its own, and nothing holds them to the JavaScript. CronWatch needs the SDK's messages and fire times byte for byte, which three ports already get from a line-for-line translation checked against croner itself; the Go port's `internal/schedule/cron` is the nearest code to start from, and the fuzz check above tells how far the crate is from it.

## Testing and CI

`cargo test --workspace --all-features` in `packages/rust` is the whole suite; the Postgres, MySQL, MariaDB and pg_cron tests run when their `CRONWATCH_TEST_*` variables are set, as the other ports' do. The client, store, handle, finish-once and routes tests are the SDK's, ported, as the Go port ported them, and tokio's paused clock (`start_paused`) stands in for the fake clocks.

The CI job `rust`, beside `go`. ## Where it cannot match the SDK

What is known before any code, mostly shared with the Go port; phase 5 completes the list.

- The croner port answers that a schedule naming a date no month has (`0 0 30 2 *`) never fires, where croner runs out of stack; a one-time date string is refused (`CronPattern: a one-time date is not supported by the Rust port`); a bad zone is refused when the expression is read rather than when a fire time is asked for. These are the Go port's answers, for the same reasons.
- Zones come from jiff: without a `timezone`, a cron is read in `TimeZone::system()` (`$TZ`, else `/etc/localtime`); names are matched without regard to case through jiff's database, which refuses path-like names; `Local` and jiff's fallback `Etc/Unknown` are not zones; and past jiff's range (the years -9999 to 9999) the offset at the end of the range is used.
- Rust errors carry no stack on stable, so a failed run's error has no frames; a panic has them only when the app opts in with `cronwatch::capture_panic_frames()`, which installs a panic hook (chained to the one already set) that keeps the panicking thread's backtrace for the run, since the standard library gives it to no one else. Error names are Rust's type names (see Rules), not JavaScript's classes.
- A run whose future is dropped while the function runs is recorded as failed at once (see The Rust API); the SDK has no way to drop a running function.
- A value logged that is not a string is written with its `Display`, where JavaScript writes objects as JSON; `JobContext::log` takes one line, which the app formats, where `console.log` joins its arguments.
- A panic whose payload is neither a `&str` nor a `String` is recorded as `panic: Box<dyn Any>`, as the standard library's hook prints it.
- A request that gets no answer fails with the transport's own words after the origin (`https://hooks.example: error sending request: client error (Connect): ...`), where fetch says `fetch failed`.
- Header names are lowercase, as fetch sends them, but the order of headers with distinct names follows the `http` crate's map, which the tests pin; reqwest's `User-Agent` and `Accept-Encoding` stand where fetch sends its own, and triage's user agent is `cronwatch-rust/<version>`.
- A redirect is an answer outside 2xx (`... answered 307`), where fetch with `redirect: "error"` throws `fetch failed`; either way nothing is sent where it points. A request that gets no answer fails with `<origin>: <reqwest's error, without the URL>`.
- A body past 1 MiB is answered 413; the SDK leaves the limit to the server in front of it.
- An interval longer than 2^53 ms is held at 2^53 ms, and a timeout past what a `std::time::Duration` holds is held there, as in the Go port.
- A silence given a fraction of a millisecond ends on a whole millisecond, since state times are `i64`.
- The dashboard's locked page and a handler's 503 name the Rust API (`RoutesOptions::token`, `no_token()`, `no_secret()`), where the SDK names its options.
- The SDK has no scheduler integrations, no `delete_run_if` and no blocking client.
- A job given `expect_fn` with a different function is not declared again by a source (both store `custom function`); the SDK compares the function's source text.

## Decisions

The owner settled the draft's open questions before phase 1:

1. **The crate name** is `cronwatch`, claimed by the next batched release (0.7.0) once phase 1 works. Nothing is published as a placeholder. If the name is taken first, the fallback is `cronwatch-sdk`, with `[lib] name = "cronwatch"`.
2. **The MSRV** is 1.85 for the core. Only sqlx 0.9 is supported, so `cronwatch-sqlx` needs 1.94; sqlx 0.8 is not.
3. **The core's dependencies**, tokio, getrandom, jiff, sha2, hmac and md-5, are accepted. Each comes in with the phase that first needs it: phase 1 takes tokio, getrandom and jiff.
4. **A dropped run.** A job future dropped while the job's function runs records the run as failed straight away.
5. **Panics.** A panic's message is always recorded; its stack frames only through an opt-in panic hook, off by default.
6. **apalis.** The integration targets 1.0 if it has shipped by phase 4, otherwise the release candidate.
7. **Frameworks.** tower and axum only for now; actix-web, Poem and Rocket only when someone asks.
8. **Stores.** sqlx only.
9. **The blocking client** ships in the first release, behind the `blocking` feature, for plain cron binaries.
10. **Cloudflare Workers and wasm** are out of scope.
11. **A command-line tool**: not now, only if asked.
12. **Publishing.** The first publish is by hand, then trusted publishing. No second crate owner for now.
13. **Names.** The environment variables follow the other ports: `CRONWATCH_ENV`, then `APP_ENV`, then the language's own, as the Go port reads `GO_ENV`, so here `RUST_ENV`. The integration crate is `cronwatch-tokio-cron-scheduler`.

Phase 2 settled these, which the draft left open:

14. **`idna_adapter` is held at 1.1** in the core (`~1.1`, under the transport). `url`'s newer IDNA backend pulls in `yoke-derive` 0.8.3, which declares no `rust-version` and needs 1.87, so a fresh 1.85 build with `alerts` would fail; 1.1 keeps it on the unicode-rs backend and drops some fifteen crates. An app that requires `idna_adapter` 1.2 itself would conflict.
15. **Channels are `Arc<dyn Channel>`**, and no options struct takes a raw `reqwest::Client`: an app passes `transport: Some(Arc::new(ReqwestTransport::with_client(c)))`.
16. **Webhook headers are an ordered `Vec`**, so the SDK's order holds; the Go port sorts a map.
17. **`SqlStore::postgres` and `SqlStore::mysql` are plain calls**, as `sqlite` is; the tables are made on the client's first use.
18. **`JobOptions::merge`** is public in the core, for a source (pg_cron now, the integrations later) putting an app's options between its own.
