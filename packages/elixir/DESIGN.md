# The Elixir port

`packages/elixir` is to be `cronwatch` on Hex: the same library as `@cronwatch/sdk`, for Elixir and Erlang services, from a script a crontab runs to a Phoenix app with Oban or Quantum inside it. It is a port, not a new design, made the way the Ruby gem and the Python, PHP, Go, and Rust ports were (see their `DESIGN.md`), and like the last four it is made in phases. The Rust port is the nearest model for how the work is laid out and audited, and much of what Go and Rust wrote for themselves (the croner port, the JavaScript regular expression engine, the JSON writer, the store dialects, the origin reader, the POST hardening) is carried over nearly line for line; Python and Ruby are the nearer models for a dynamic language's API. The TypeScript SDK is the source of truth for every behaviour, message, and stored byte; when the two disagree, the Elixir side is wrong.

Phase 1 is done (see Phases): the core, the memory store, and the SQL store over Ecto on SQLite, with `Cronwatch.StoreCase`. Phase 2 is done too: the SQL store on Postgres, MySQL, and MariaDB, the pg_cron source, the fifteen alert channels over `:httpc`, and Claude triage, with every file in `conformance/` replayed. So is phase 3: the dashboard and a job's handler, as Plugs. And phase 4: the bridge, runs given back, the Oban and Quantum integrations, `Cronwatch.Release.check/2` and `mix cronwatch.check`, and `examples/crontab`. And phase 5, the audit before the first release, whose findings are listed under Phases. The owner took every recommendation of the draft's open questions, which are now the Decisions at the end, with those phase 1 settled; the rest of this file is the design the phases are built from, updated by each as the Rust port's phases updated that port's.

## Rules

- Elixir 1.18 or newer on Erlang/OTP 27 or newer, tested on the floor and on the current release (Elixir 1.20 on OTP 29) in CI. Elixir 1.18.3 on OTP 27.3 is what Debian 13 ships, so a service built with a distribution's toolchain can use the package, as the Rust floor was chosen; it is some twenty-one months old at the first release and still gets Elixir's security fixes (1.18.5 came out on 2026-08-28 beside 1.19.6 and 1.20.4). Erlang/OTP supports its latest three majors, 27, 28, and 29 today, and Elixir 1.20 runs on exactly those, so OTP 27 is the oldest anyone is patched on. What the floor must at least be: Phoenix 1.8, Oban 2.24, Plug 1.20, and Req need Elixir 1.15, ecto_sqlite3 0.25 and exqlite 0.41 need 1.17, and 1.17 brings `Duration` and `to_timeout/1`, which the API takes (see The Elixir API). 1.18 adds the built-in `JSON` module and its `JSON.Encoder` protocol, which the public structs implement for an app's own use without Jason. Nothing here needs OTP 28 or 29.
- One Hex package, `cronwatch`, OTP application `:cronwatch`, every module under `Cronwatch` (Hex's rule that a package's modules share its name's prefix; `mix cronwatch.check` is the one exception, as a Mix task's module is `Mix.Tasks.Cronwatch.Check`). No umbrella: an umbrella's apps are published one by one anyway, and the Elixir norm (Phoenix, Oban, Req, Ecto) is one package with optional dependencies, each integration compiled only when its dependency is present (`if Code.ensure_loaded?(Oban) do ... end`, which Mix makes reliable by compiling optional dependencies first). Rust split its integrations into crates because a crate that takes another crate's types is tied to one major version of it; Mix resolves one version of each package for the whole app and an optional requirement can span majors (`~> 2.19 or ~> 3.0`), so that reason does not arise here.
- The package's required dependencies are `tz` (zones, see Zones) and `telemetry` (see Telemetry), both with no dependencies of their own, and OTP's own applications `:crypto` (SHA-256, HMAC, MD5, strong random bytes, `hash_equals/2`), `:ssl` with `:public_key` (the default HTTP transport, see Channels). Everything else is optional and named in `mix.exs` with `optional: true`: `plug` (the dashboard and a job's handler), `ecto_sql` (the SQL store and the pg_cron source; the app brings its own adapter, `postgrex`, `myxql`, or `ecto_sqlite3`), `oban` and `quantum` (the integrations). Cron parsing and fire times are a port of croner 10 (`Cronwatch.Cron`, carried over from the Rust port's `schedule::cron`, itself the Go port's), JSON is written and read by `Cronwatch.JS` (not Jason or `JSON`, whose numbers and key order differ; see below), and secret redaction runs on `Cronwatch.JSRE`, the Go and Rust ports' small backtracking engine with JavaScript's semantics, carried over (see Redaction).
- Times are integer epoch milliseconds everywhere, as in the SDK and the other ports, so `evaluate` ports line for line and stored rows are identical. Durations are milliseconds inside, an integer or a float (a definition may hold `1.5`, which the SDK keeps).
- Names in Elixir are snake_case (`failures_before_alert`, `max_duration`, `started_at`), as in the Ruby and Python ports. Anything that leaves the process (store rows, JSON columns, alert JSON) uses the SDK's exact camelCase field names, key order, and values, so a Node, Ruby, Python, PHP, Go, Rust, and Elixir process can share one database and `@cronwatch/mcp` works against any of them. Run statuses, conditions, alert types, and health are the wire strings (`"ok"`, `"over_budget"`), not atoms, with functions for the known values (`Cronwatch.Condition.over_budget/0`): stored values come from other writers, a newer SDK adds values that must pass through unharmed, and turning stored text into atoms would fill the atom table (see Decisions, 11).
- `Cronwatch.JS.stringify/1` is `JSON.stringify` byte for byte: numbers as JavaScript prints them (`2` not `2.0`, `1e-7`, `1e+21`, `123456789012345680000`; the shortest round-trip digits come from `:erlang.float_to_binary(x, [:short])` and are laid out as `Number.prototype.toString` lays them out), an integer beyond 2^53 written as the double JavaScript would hold, keys in JavaScript's order (array-index keys first in ascending order, then the rest as inserted), only control characters, quotes, and backslashes escaped. Elixir maps have no order (a small map iterates in term order, a large one in hash order), so JSON objects are `Cronwatch.JS.Object`, an ordered list of pairs, and `Cronwatch.JS.parse/1` reads into it, keeping the order the text had. Jason and Elixir's `JSON` were weighed and left out of everything that leaves the process: both write `2.0` for the float 2 and Erlang's exponent form, both decode objects into maps, and neither can write the lone surrogate Slack's and Discord's cut bodies carry. Each public struct implements `JSON.Encoder` through the same JSON its `to_json/1` writes, and `Jason.Encoder` when Jason is loaded, for an app returning a `JobSummary` from its own controller; the stores and channels never use them.
- A definition keeps its fields in the order they were given. The SDK writes `{ ...defaults, ...options, name }` with `expect` moved last, so the stored JSON follows the object literal an app wrote. Elixir's keyword lists are ordered, so job options are a keyword list and the stored definition follows it with no builder (Rust needed one): `schedule: "0 2 * * *", grace: "15m"` is written in that order. A key given twice keeps its first place and its last value, as a JavaScript object does. Where the SDK takes an object of the app's own keys (`budget`, metrics), a keyword list or a list of pairs keeps its order and a map is written in its keys' term order (see Where it cannot match the SDK). Fields a newer writer added are kept.
- Alert titles and messages are the SDK's text, character for character, with numbers as `toLocaleString("en-US")` writes them (the Go port's `format.go`, through Rust's `format.rs`).
- Lengths and cuts are in UTF-16 code units, as JavaScript counts them (`Cronwatch.JS.len16/1`, `slice16/3`, `tail16/2`). `String.length/1` and `String.slice/3` count grapheme clusters and `byte_size/1` counts bytes, and neither is JavaScript's count, so nothing that must match the SDK calls them; `String.trim/1` trims Elixir's whitespace, which is not JavaScript's `\s`, so trims go through `Cronwatch.JS.trim/1`. A cut through a surrogate pair leaves U+FFFD where JavaScript would keep a lone surrogate, which is the character that surrogate becomes once written out as UTF-8, so stored bytes are the same. The two places the SDK sends a lone half on the wire (Slack's and Discord's cut bodies, triage's prompt) keep it through `Cronwatch.JS.stringify_lone/1`, as the Go and Rust ports do.
- Every condition opens once and closes with a recovery. No repeat alerts. A job whose schedule is removed while missed is open has missed closed by the next check with a recovery of its own (`reason: "unscheduled"`).
- A job's function may raise, throw, exit, or return `{:error, reason}`, and each is a failed run (see Runs); the failure is then handed back as it came (re-raised with its stacktrace by `:erlang.raise/3`, or the tuple returned), so no run is left `running` to be reported stuck later. A process that dies while running a job (killed by a supervisor, a linked process's crash, a request process ended because its client went away) has its run recorded as failed at once by the client, which monitors it. The store failing never stops a job: store errors go to the error handler, and the job's own outcome is returned.
- An exception is written `Name: message` and up to five frames, innermost first, each `    at Module.function/arity (file:line)`, as a JavaScript stack reads. The name is the exception's module as Elixir code writes it (`RuntimeError`, `DBConnection.ConnectionError`, `Postgrex.Error`), not its last segment, which is so often `Error` that it says nothing. A throw is `throw: <value>` and an exit `exit: <reason>`, a binary as itself and anything else through `inspect/1`; `{:error, reason}` is the reason, written the same way, an exception in it as an exception.
- The environment is read in one place, `Cronwatch.Env`: the first of `CRONWATCH_ENV`, `APP_ENV`, and `MIX_ENV` set to more than whitespace, trimmed and lowercased (the SDK reads `NODE_ENV` third; `MIX_ENV` is the language's own, as Rust reads `RUST_ENV`); `development`, `dev`, and `local` are development and `production` and `prod` production, the rule every port follows. `test` and `testing` are not development, so `MIX_ENV=test` is not: a test run or CI needs `CRON_SECRET` or a token, as production does. `Mix.env/0` is not read: Mix is absent from a release, and a release built with `MIX_ENV=prod` does not keep the variable at run time. The other reads are the SDK's own: `CRON_SECRET`, `CRONWATCH_TOKEN`, and triage's `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL`. `CRON_SECRET` and `CRONWATCH_TOKEN`, and a token or secret given as an option, are trimmed as JavaScript trims (a value read from a file often ends in a newline no header can carry), and one that is blank counts as unset. All are read when used, never when a module is compiled, since a Phoenix router compiles its plugs' options (see Dashboard).
- No em or en dashes anywhere, as in the rest of the repo.

## Package name and releases

`cronwatch` is free on Hex (checked 2026-09-29: `https://hex.pm/api/packages/cronwatch` answers 404, as it does for `cronwatch_sdk`, `cron_watch`, and `ex_cronwatch`, while it answers every package this file names). The package takes the plain name, which matches the gem, the crate, and the Python and Go import names, and gives `{:cronwatch, "~> 0.8"}`. Hex's policies discourage holding a name with an empty package, so nothing is published as a placeholder: the name is taken by the first batched release after phase 1 works, and until then it could be taken by someone else. If it is, the fallback is `cronwatch_sdk`, the PyPI package's name: Hex lets a package's name differ from its OTP application's (`package: [name: "cronwatch_sdk"]` beside `app: :cronwatch`), so an app writes `{:cronwatch_sdk, "~> 0.8"}` and every module is still `Cronwatch`, as the Python package is imported as `cronwatch`. The package's description and README say this is the library behind cronwatch.dev, as the other packages' do.

The version lives in one place, `@version` in `packages/elixir/mix.exs`; `Cronwatch.version/0` reads it from the application's spec (`Application.spec(:cronwatch, :vsn)`), so it needs no row of its own, and triage's user agent is `cronwatch-elixir/<version>`. `scripts/release.mjs` gets its two rows in phase 1, with `mix.exs` (the script refuses to run while a directory under `packages/` lacks them, so until then this file alone holds up a release, as the Rust design did before its phase 1): in VERSIONED, `{ file: "packages/elixir/mix.exs", pattern: /^(\s*@version ")([^"]+)(")/m }`; in PUBLISH, the line that says the pushed tag publishes the package through `hex.yml`, and the command to do it by hand. Hex reads a package from the tarball `mix hex.publish` uploads, not from a repository, so a package in a subdirectory of a monorepo needs no split repository (the PHP package's case) and no tag prefix (the Go module's); the release's own tag `vX.Y.Z` is the only tag. `mix.lock` is not committed, as the other ports' lock files are not.

Publishing is `.github/workflows/hex.yml`, on a pushed `v*` tag or by hand for a tag, off until the repository variable `HEX_ENABLED` is `true`, in an environment `hex` (optionally with required reviewers), as `pypi.yml` and `crates.yml` are: it checks that `@version` is the tag's, waits for CI to pass on the tagged commit (`ci-passed.yml`), and publishes in two jobs. `build`, which holds no secret, sets up Erlang and Elixir with `erlef/setup-beam` pinned by commit, fetches the dependencies, builds the package's tarball with `mix hex.build` and the docs with `mix docs`, and uploads both; `publish`, the only job that sees the key, runs no Elixir and no dependency's code, and posts the two tarballs to Hex's API with curl, as `mix hex.publish` would (the release, then its docs for HexDocs; a release already there gets only its docs). No lock file is committed, so this split, not a lock, is what keeps the dependencies' code away from the key. Hex has no trusted publishing yet: nothing in its documentation mentions OIDC, the proposal (`hexpm/hexpm#1193`, 2023) is open, and the pull request that would add it (`hexpm/hexpm#1785`, "feat: trusted publisher", opened 2026-07-31) is open and unmerged (checked 2026-09-29). So the workflow takes a key from the environment's secret `HEX_API_KEY`, generated by the owner with only the permission to publish this package and kept in the `hex` environment, never in the repository's secrets, so only that job on a tag can read it. Hex 2.5 has no `mix hex.user key` commands (`mix hex.user` is `auth`, `whoami`, and `deauth`, over OAuth), so the key is made on hex.pm under Dashboard, Keys, where a key's permissions are API (read or write, reaching every package the account owns) or one package the account owns (`package:hexpm/cronwatch`): the key takes the package alone. Hex accepts that permission for publishing a release and its docs (`api:write` or `package`, and the account must own the package) and counts it as `api:read`, which `mix hex.publish` needs to look up the user; it asks a one-time code only of an OAuth token, never of an API key, so the job runs unattended. The key goes to Hex in the `authorization` header, from a file rather than a command line; `mix docs` runs in the dev environment, where `ex_doc` is. The workflow sets up the newest toolchain `ci.yml` tests (Elixir 1.20 on OTP 29). When Hex ships trusted publishing, the workflow moves to it and the key is revoked. The first release, 0.8.0, was published by hand (`mix hex.user auth`, then `mix hex.publish` in `packages/elixir`), after which the owner makes the key, adds the environment and its secret, and turns the variable on, as `hex.yml`'s opening comment lists. Hex lets a release be reverted only for a short time after it is published (`mix hex.publish --revert`), then only retired (`mix hex.retire`), which is one more reason nothing is published before phase 1 works.

## The Elixir API

```elixir
# lib/my_app/application.ex
children = [
  MyApp.Repo,
  {Cronwatch,
   store: {Cronwatch.Store.Ecto, repo: MyApp.Repo},          # default: a MemoryStore
   alerts: [{Cronwatch.Alerts.Slack, webhook_url: System.fetch_env!("SLACK_WEBHOOK_URL")}], # default: Console
   retention: "30d",
   check_every: :timer.minutes(1),                             # the SDK's startChecking(every); leave out where another process checks
   jobs: [
     {"nightly-report",
      schedule: "0 2 * * *", timezone: "UTC", grace: "15m", timeout: "30m",
      expect: "Report written", budget: [cost: 2], failures_before_alert: 1}
   ]}
]

# anywhere
Cronwatch.run("nightly-report", fn job ->
  path = MyApp.Reports.build(job)            # Cronwatch.cancelled?(job) turns true at the job's timeout
  Cronwatch.log(job, "Report written: #{path}")
  Cronwatch.metric(job, "cost", 1.2)
  {:ok, path}
end)

{:ok, result} = Cronwatch.check()             # missed and stuck runs, retries, pruning
:ok = Cronwatch.silence("nightly-report", "2h")
```

The shape follows Elixir's conventions while keeping the SDK's names recognisable: `cronwatch({...})` is a child of the app's supervision tree, `cw.job(name, options)` is `Cronwatch.job(name, options)` (or the `jobs:` option, declared when the instance starts), `job.run(fn)` is `Cronwatch.run(job, fun)`, and `recordRun`, `resumeRun`, `jobsWithRuns`, and `jobSummary` are `record_run`, `resume_run`, `jobs_with_runs`, and `job_summary`. BEAM processes block cheaply, so there is one API, where Python needed `cronwatch.aio` and Rust a blocking client.

- *An instance in the app's tree, named.* `{Cronwatch, opts}` starts an instance under the name `Cronwatch`, or `name: MyApp.OtherCronwatch` for a second one; every function finds its instance from a `Cronwatch.Job` handle it is given or from `instance:` in its options, else the default name, as Oban's functions default to `Oban`. The instance's options are checked when it starts, so a bad option, schedule, or job fails the app's boot with the SDK's message rather than the first run. The options are the SDK's in snake_case: `cron_secret: "..."`, `cron_secret: false`, or neither (reading `CRON_SECRET`) where the SDK has a string, `null`, and absent; `redact: fun` and `redact: false`; `deliver: :now | :check`; `defaults:` takes `grace`, `timeout`, `timezone`, and `failures_before_alert` and refuses others. There is no module a library user must define (`use Cronwatch` in the app's own module, as Ecto repos are made): a child spec is enough, and a module adds nothing a name does not (see Decisions, 8).
- *Functions answer `{:ok, value}` or `{:error, %Cronwatch.Error{}}`*, with a `!` variant that raises for each that reads or writes the store, as Elixir libraries do; `Cronwatch.Error` has a `kind` (`:invalid` for what the SDK refuses, with its message; `:store` with the store's own error as `reason`; `:other`). `run/3` answers what the function answered (see Runs), not a tuple of its own.
- *Durations* take the SDK's text (`"15m"`, `"1h30m"`), milliseconds (`:timer.minutes(15)`, `900_000`, `1.5`), or anything `to_timeout/1` takes (`%Duration{minute: 15}`, `[minute: 15]`); a `Duration` with months or years is refused, as `to_timeout/1` refuses it, since neither has a fixed length. Text is stored as written and everything else as its milliseconds, as the Go, Python, and Rust ports store theirs. Text longer than 64 characters is refused before it is read, quoting its first 32, the SDK's `duration.ts` rule, which `duration.json` holds every port to.
- *Expect* takes a binary (contains), a `%Regex{}` is refused with a message naming `{:matches, "source", "flags"}` (Elixir's regular expressions are PCRE, which reads a pattern differently from JavaScript; see Redaction), `{:matches, source, flags}` for a JavaScript pattern (stored as `matches /source/flags`, run by `Cronwatch.JSRE`), or a one-argument function (stored as `custom function`; a raise in it fails the run with `Output check threw: ...`).
- *Job functions* are `fn job -> ... end`, one argument, a `%Cronwatch.Context{}`: `Cronwatch.log(job, line)`, `Cronwatch.metric(job, name, value)`, and `Cronwatch.cancelled?(job)` (the SDK's `signal`, true from the job's timeout on; the function decides what to do, as a JavaScript function decides what to do with an aborted signal). `Cronwatch.log/1` and `metric/2` without a context use `Cronwatch.current/0`. A binary the function returns, or `{:ok, binary}`, is the output when nothing was logged (and what `expect` checks).
- *Channels, triage, and sources are behaviours*: `Cronwatch.Channel` (`name/1`, `send/3` with the channel's state, the alert, and a `ChannelContext`), `Cronwatch.Triage`, and `Cronwatch.Source` (`name/1`, `sync/2` with the instance). Each is given as `{module, opts}` (the channel's `init/1` checks the options once, when the instance starts, with the SDK's refusal in Elixir's words: `Cronwatch.Alerts.Resend needs :api_key`), or, for a quick one, `Cronwatch.Alerts.fun("pager", &MyApp.page/2)`.
- *Stores* are the `Cronwatch.Store` behaviour, given as `{module, opts}`. The SDK's two optional methods, `update_run_if` and `compare_and_set_state`, and the Go, PHP, and Rust ports' `delete_run_if` (which a run given back needs, below) are `@optional_callbacks`, found with `function_exported?/3` as Go finds an optional interface; without them the client falls back to a read and a write, as the SDK does. `MemoryStore` and `Store.Ecto` implement all three. A store that needs a process (the memory store) says so with an optional `child_spec/1` and is started under the instance.
- *A run given back*: `run(job, fun, discard_when: fn reason -> boolean end)` takes a run back rather than judge it when the function fails with a reason the predicate answers true for, for an attempt a queue gives back without failing (an Oban job that snoozes). It is the Go port's `DiscardWhen` and the Rust port's `run_or_discard`, rule for rule, with their audits' fixes: the running row is deleted with `delete_run_if`, nothing is judged or alerted, the job's state is left as it was (missed and stuck are closed only once the run is known not to be given back), the failure is still handed back, a row a check marked stuck is left as it is, a store without `delete_run_if` records the run as it ended, and a predicate that raises is reported (`discarding <job>`) and the run recorded.
- *Writing a declaration now*: `Cronwatch.sync_job(name)` writes the job declared in this instance to the store unless the store already holds that definition (compared as JSON, keys in any order), and says whether it wrote, as the Go and Rust ports' do; the integrations use it.
- *Nullable values are `nil`* in `Run`, `JobState`, and `JobSummary`. A state's `pending_recovery` and `undelivered` are `nil` for a state written before the fields existed, and `sending` (the outbox) is `nil` whenever it holds nothing, the key then left out, and unknown keys a newer writer added are kept in their places and written back, in an `extra` field holding a `JS.Object`. The alerts the state holds (`undelivered`, and each `sending` entry) keep theirs too, as the SDK keeps them as the objects it read: an alert's `extra` holds the fields it does not know, its run's `extra` the run's, its details map an `extra` key with the details' (each breach's with the breach's), the details of a type this release does not know are the `JS.Object` as read, and a `sending` entry is written back as read with its `until` and `alert` set; all are written back, and a retried alert is sent with every field it was read with.

## Processes

The client is a supervised process tree, not a plain struct, because the SDK's client has state that outlives any one call and must be shared by every process that runs jobs: which jobs are declared, the per-job queue that serialises state changes, the one check that concurrent callers share, the interval, and the runs in flight. The instance's configuration (the store, the channels, the options) is written once to `:persistent_term` when it starts, so every call reads it without a message; everything that changes lives in the processes below, started by `Cronwatch.Supervisor` with `:rest_for_one`:

- *`Cronwatch.Instance`*, first, which writes the configuration when the instance starts and erases it when the instance stops. It is not restarted when a child after it is, so a crash of the store's process or of `Cronwatch.Runs` restarts the rest with the configuration still in place; when `Cronwatch.Runs` erased it from its own `terminate/2`, a restart of it could never succeed, and one crash took the whole instance down.
- *The store's process*, when the store has one (the memory store).
- *`Cronwatch.Runs`*, which owns two ETS tables: the declared jobs (name to definition, read by any process, written through the process so two declarations of one name do not race), and the runs in flight (the run's process, its id, its job, and its lines and metrics, so a `log` from a `Task` the job started is an ETS insert, never a message to a busy process). It monitors the process of every run it holds (see Runs).
- *`Cronwatch.Locks`*, the per-job lock `update_state` holds, as the SDK's `serial()` queue: a FIFO queue per key, the holder monitored, so a lock whose holder died is released rather than held for good. Only store calls happen under the lock; alerts are sent after it is released. The same process holds the per-process entry a `start` with an id takes while it reads the store and inserts.
- *A `Task.Supervisor`* for the work the SDK does off the caller's path: the recording after a run's function returns, each channel's send, triage, the closing of missed and stuck at a run's start.
- *`Cronwatch.Checker`*, a GenServer: `check/1` is a call that joins the check in flight or starts one, in a task of its own, and every caller waiting gets the same answer, so a caller that gives up (its own timeout, its process gone) neither fails the check for the others nor leaves a job half checked. A crash in the check (a store's) is that check's `{:error, ...}` and the next call starts a new one. With `check_every`, the first check runs after a second and then on the interval (a minute by default, five seconds at least, and at most the SDK's 2^31 - 1 ms); each tick asks for a check without waiting on it, as setInterval does, so a tick while a long check runs shares that check and the ticks it outlasted are not run back to back after it. `Cronwatch.start_checking/1` and `stop/1` are the SDK's `startChecking()` and `stop()` for an instance started without `check_every`.

Monitoring being down never stops a job. `Cronwatch.run/3` on an instance that is not running (not started yet, stopping, or between a crash and its restart) runs the function unrecorded, as it would run without CronWatch, and says so once per instance through Logger; the calls a run makes to `Cronwatch.Runs` answer as if the run were gone while it restarts, and a recording whose task supervisor is restarting is made in the caller. An isolated run's task goes down with the instance's tasks when `Cronwatch.Runs` restarts: its caller, seeing that the run went with the old `Cronwatch.Runs` rather than being recorded by its monitor, records it as failed with the task's exit reason, so it is never left `running`.

Every read-modify-write of a job's state goes through `update_state`: holding the job's lock, it reads the state, works out the next one, and writes it only when it changed, with `version` one higher, through `compare_and_set_state` against the version read; a refused write is worked out again from a fresh read, up to 10 times, as in every port. A cluster of nodes is a set of processes sharing one store, as several Node processes are: each node has its own instance, and `compare_and_set_state` keeps them honest. With Oban, a cluster can run the check once per minute cluster-wide with `Cronwatch.Oban.CheckWorker` in the Cron plugin's crontab, rather than `check_every` on every node (see Oban).

## Runs

`Cronwatch.run(job, fun, opts)` runs the function in the calling process, by default. That is where the app's context lives: the Ecto sandbox's ownership in tests, Logger metadata, an OpenTelemetry span, `self()` for a reply, the Oban worker's own process. It declares the job if needed, inserts the running row (a store failure goes to the error handler and the job still runs), puts the run's `Context` in the process dictionary and registers the process with `Cronwatch.Runs`, sets the Logger metadata `cronwatch_job` and `cronwatch_run`, and calls the function inside `try` with `rescue` and `catch kind, reason`. Then:

- *What counts as failed.* A raise, a throw, an exit, `{:error, reason}`, and `:error` fail the run; anything else it returns succeeds. `{:error, reason}` failing the run is not the SDK's rule (a JavaScript function returning an object succeeds), but it is how Elixir code reports failure without raising, and Oban's workers answer the same way; an app that returns `{:error, _}` for a job that succeeded wraps the result (see Decisions, 10). After the recording, a raise, throw, or exit is raised again with `:erlang.raise(kind, reason, stacktrace)`, so the caller's own handling (a supervisor's restart, Oban's retry) sees exactly what it would have without CronWatch, and a returned value is returned.
- *Recording outlives the caller.* Everything after the function returns (the finish, the state, the alerts) runs in a task of the instance's `Task.Supervisor` that `run` awaits, so a caller killed while it waits (a supervisor shutting it down, `Task.shutdown/2`, a request process whose client went away) leaves the recording to finish rather than cut part way: the Rust port's rule for a dropped future, which a BEAM process meets in the same places.
- *A process that dies inside the function.* A process can be killed without running any code of its own: `Process.exit(pid, :kill)`, a linked process's crash when it is not trapping exits, Cowboy ending a request's process when its connection closes, Oban's worker killed at its `timeout/1`. `Cronwatch.Runs` monitors every run's process, and when one dies with a run still open it records the run as failed at once, with the exit reason (`exit: killed`, `exit: shutdown`, `exit: {%RuntimeError{...}, stacktrace}` written as the exception it holds), rather than leave it `running` to be reported stuck at its timeout. This is the Rust port's decision 4 (a dropped run is failed straight away) for the same reason: the process is gone, so waiting learns nothing more. A run whose function returned normally is closed in the table before its recording starts, so the monitor never records it twice.
- *Timeouts.* The SDK aborts a signal at the job's timeout and lets the function decide; it never stops the function, and a function that runs on is marked stuck by a check. So does this port by default: a timer in the instance flips the run's flag (`:atomics`), `Cronwatch.cancelled?/1` reads it, and nothing is sent to the caller's mailbox, which belongs to the app. `isolate: true` runs the function in a task of the instance's `Task.Supervisor` instead (`async_nolink`), for a function that should not take its caller down: the caller waits for it, a crash is a failed run and is handed back as an exit, and with `kill_at_timeout: true` the task is killed at the job's timeout and the run is recorded exactly as a check would mark it (status `timeout`, `Still running after 30m; marked as timed out`), so the alert is the SDK's stuck alert, sent sooner. A function run in isolation has its own process dictionary and Ecto ownership (a test with the sandbox must allow it; `$callers` covers `Task`), which is why it is opt in (see Decisions, 9).
- *`current/0`.* `Cronwatch.current()` answers the calling process's run from its process dictionary; in a process the job started (a `Task`, `Task.async_stream`), it walks the process's `$callers` and asks `Cronwatch.Runs` whether any of them is running a job, so `Cronwatch.log/1` from inside a `Task.async_stream` in a job's function adds to that job's output. A process started with `spawn/1` has no `$callers` and no run, as a thread started in the SDK's function has no `AsyncLocalStorage` store unless it inherits one.
- *HTTP answers.* With `plug` loaded, a function that returns a `%Plug.Conn{}` whose status is 400 or more fails the run with `HTTP <status> <reason>` (the reason from `Plug.Conn.Status.reason_phrase/1`), as the SDK fails a run for a fetch `Response`; so does an `{:ok, %Req.Response{}}` or `%Req.Response{}` of such a status when Req is loaded, since that is what an Elixir function that calls a URL returns.

## Runs that span calls

`Cronwatch.start(job, trigger: .., id: ..)`, `Cronwatch.resume(job, run_id)`, and `Cronwatch.resume_run(name, run_id)` are the SDK's `start()`, `resume()`, and `resumeRun()`, and answer a `%Cronwatch.RunHandle{}`: `id`, `job`, `started_at`, with `active?/1`, `log/2`, `metric/3`, `flush/1`, `finish/2`, and `fail/2`, following `client.ts` and the Go port's `handle.go` rule for rule: a start with an id holds `Cronwatch.Locks`' entry keyed by the job and the id while it reads the store and inserts; `finish` reads the stored run again, joins its output with the handle's (capped) and merges metrics (the handle's win); `flush` writes only over a row still running and of this job; the store never fails out of `start`, `resume`, `flush`, or `finish` (failures go to the error handler as `recording <job>`, `starting <job>`, `resuming <job>`, `flushing <job>`, or `finishing <job>`); and a store that fails during `finish` leaves the handle active, lines kept, so it can be called again. A handle is a struct, and a struct cannot change, so its lines and whether it is active live in `Cronwatch.Runs`' table under the handle's id, owned by the process that made it and dropped when that process ends: a handle whose process ended while it was active records nothing, as a Rust handle dropped while active records nothing, since a run left unfinished is what the stuck check is for.

A run is judged once, however many processes finish it: the finish is written only over a stored row still `running`, else over one still `timeout`, through `update_run_if`, one conditional `UPDATE`, and only the process whose write lands evaluates. `insert_run` refuses an id already stored. The SDK's multi-process scenarios (`finish once`) run against the memory store and against SQLite, Postgres, MySQL, and MariaDB, each process an instance of its own over one database.

## Telemetry

`telemetry` is a required dependency: it is a single small Erlang module with no dependencies, every Phoenix, Ecto, and Oban app already has it, and its events are how Elixir apps are measured (Phoenix LiveDashboard, `telemetry_metrics`, OpenTelemetry's handlers). The events, named in `Cronwatch.Telemetry`:

- `[:cronwatch, :run, :start]`, `:stop`, and `:exception`, a `:telemetry.span/3` around the function, with the job, the run id, and the trigger in the metadata and, on `:stop`, the run's status; the duration is telemetry's own measurement.
- `[:cronwatch, :check, :start]`, `:stop`, and `:exception`, with the `CheckResult`'s counts on `:stop`.
- `[:cronwatch, :alert, :sent]`, `:failed`, `:queued`, and `:dropped`, per channel and alert, with the job, the alert's type and condition, and the channel's name.
- `[:cronwatch, :error]`, whatever the error handler hears (the `where` text the SDK gives, `recording nightly-report`, and the error).

The error handler itself is the SDK's `onError`: `on_error: fun` (arity 2, the error and where), by default `Logger.error("[cronwatch] #{where}: ...")`, as the SDK's default writes `console.error`. The in-memory store's warning and `start` with `deliver: :check`'s warning are `Logger.warning` with the SDK's text.

## Delivery

`deliver: :now` (the default) sends each alert from the process that produced it; `deliver: :check` queues it in the job's state (`undelivered`, at most 20, the oldest dropped first and reported) for the next check in a process that delivers now. Either way the alert is written with the state that opens its condition, in the same write (`Evaluate.hold_alerts/4`): with `deliver: :now` into `sending`, each entry with a lease five minutes long, and taken out once its send is recorded (`Evaluate.record_sent/6`); a check releases an entry whose lease ran out into `undelivered` (`Evaluate.release_sending/2`), where the retry sends it with triage, so an alert whose node died mid-send is sent by a later check, once, or twice if a channel took it just before the node died. An alert some channel refused is queued the same way, with `owed` (in its `extra`, as the SDK writes it) naming the channels that still owe it by their keys (`Evaluate.channel_keys/1`: the channel's name, then `#2`, `#3` for repeats), and retried once per check, oldest first, to those channels only and only while they are configured; an alert without `owed` (never sent, or held by an older release) is owed by every channel configured now, and a channel is never given `owed`. `last_alert_at` moves only when some channel accepted an alert on that attempt. One that no longer describes the job (`staleAlert`) is dropped; one check spends at most 20 seconds retrying across all jobs. Triage is tried once per alert. The copy held in state has its run trimmed (`Evaluate.held_alert/1`: the error's first 2048 UTF-16 units, the output's last 2048, and the message's first 4096, each with a marker of what was left out, and only past 64 units of slack, so a trim is never trimmed again); the first send uses the alert as composed, and only a retry reads the trimmed copy.

Each channel sends in a task of its own under the instance's `Task.Supervisor`, waited on with `Task.yield/2` for 15 seconds and then `Task.shutdown(task, :brutal_kill)`, and triage for 25. As in Rust, and unlike Go, a send past its time is stopped, not abandoned: the task is killed, its socket closed with it, and the next alert is sent to the channel as the SDK sends it. A channel that raises or exits is that channel's failure only. `Console`, the default channel, writes the SDK's line through `Logger`, `Logger.info` for a recovery and `Logger.error` for anything else, where the SDK writes `console.info` and `console.error`: an Elixir app's output goes through Logger, and a line written straight to standard output would miss its formatting, metadata, and backends.

## Channels

`Cronwatch.Alerts` holds the SDK's channels, request for request: Slack, Discord, the webhook, Resend, Postmark, SendGrid, Mailgun, SES, Twilio, Sentry, Honeybadger, Datadog, Rollbar, Bugsnag, and New Relic, each a module given as `{Cronwatch.Alerts.Resend, api_key: ..., email: [from: ..., to: ...]}` with the SDK's option names in snake_case. A boolean is given as the SDK names it (`recovered: false` leaves a Sentry or Rollbar channel's recoveries out, `recovered: true` sends Twilio's, Honeybadger's, and Bugsnag's), with the SDK's default when left out. The email providers take `from`, `to`, and the rest flat, as the SDK does, or nested under `email:`, whose keys win. The requests are the SDK's: the same URL, header names and values in order, and body written by `Cronwatch.JS`, so the bytes are identical; the same stable alert id (the first 32 hex characters of SHA-256 over job, type, and time); the same error text. The webhook's extra headers are a list of pairs, so the SDK's order holds.

Every request goes through `Cronwatch.Alerts.Post`, a transport-free port of the Go port's `internal/post` and the Rust port's `alerts::post` with both audits' hardening, over the `Cronwatch.Transport` behaviour (one POST: URL, headers in order, body; it answers a status and a body read a chunk at a time, so `Post` holds every transport to the deadline and the cap). The default transport is `Cronwatch.Transport.HTTP`, one HTTP/1.1 POST over OTP's own `:gen_tcp` and `:ssl` (see Decisions, 33), so the package needs no HTTP client of its own; an app that wants its Finch pool, a proxy, or Req's retries writes a transport (a dozen lines over `Req.post/2` or `Finch.stream/5`) and gives it as `transport: {MyApp.ReqTransport, []}` on the channel or the instance. Req was weighed as the default and left optional: it brings Finch, Mint, NimblePool, Jason, and MIME into every app, where a POST over OTP's sockets needs nothing, and the SDK itself uses the platform's fetch rather than a client library, as Python uses `urllib` and Go `net/http` (see Decisions, 5).

- One deadline for the whole request, connecting, sending, and reading the answer: ten seconds inside the channel's own, held by `Post` running the request in a process of its own and killing it past the deadline, the socket going with it. Past it before an answer is `The operation was aborted due to timeout`, fetch's message; past it while the body arrives is the answer with no body.
- A redirect is refused, not followed (`autoredirect: false`), and a 3xx is an answer outside 2xx like any other, so credential headers never go where it points.
- At most 1 MiB of an answer is read, as it arrives, whatever its status and however it is framed (a `content-length`, chunked, or up to the connection's close): the transport hands `Post` the body a chunk at a time and `Post` stops at the cap. The answer's head is held to 64 KiB and 256 lines, and up to eight interim 1xx answers are passed over. Nothing is decompressed, and no `accept-encoding` is sent, so a gzip answer cannot grow in memory.
- TLS is always verified: `verify: :verify_peer` with the system's roots from `:public_key.cacerts_get/0`, the host checked with `:public_key.pkix_verify_hostname_match_fun(:https)`, and a host name sent as SNI; an IP address is never sent as SNI and the certificate is checked against the address, since `server_name_indication: :disable` also turns `:ssl`'s hostname check off. One request per connection (`connection: close`), nothing kept between sends, and no proxy read from the environment, as Node's fetch reads none.
- The URL is read by a port of the WHATWG rules the Go port's `internal/post` applies (a space inside is encoded and posted, `javascript:` is refused as `not javascript:`, a user name is refused), not by `URI.parse/1`, which is RFC 3986 and reads differently; it must be `http` or `https` with a host, and is never quoted in an error, since a webhook URL's path is its credential. Only the URL's origin appears in any error, and every error the transport returns is rewritten to its origin and its reason. The transport connects to the host the URL was read to, so what the URL names and what is reached cannot differ; an IPv6 host with a zone is refused, as fetch refuses it.
- Credentials are trimmed of the spaces and newlines a paste leaves; a header value with a CR, LF, or NUL left inside is refused, naming the header, never its value.
- Every secret the channel holds is cut out of a quoted answer before the answer is cut to 200 UTF-16 units on a code point.
- Nothing prints a credential: each channel's options, triage's, and the dashboard's and handler's hold their secrets in structs whose `Inspect` implementation names what is set, never its value (`@derive {Inspect, except: [:api_key]}`), the Rust audit's rule, so an app's crash report or `IO.inspect` of its config does not leak them.

Twilio texts every number at once, a task each, and follows the SDK's segment fitting and partial-delivery report. The tests replay every case of `conformance/channels.json` (every section) through a recording transport, and a hardening suite runs every channel against real local servers (raw `:gen_tcp` and `:ssl` in the tests, so no HTTP server is a test dependency and a server can misbehave as a test needs): a redirect refused by all fifteen, the deadline before an answer and while a body drips in, a large answer read to exactly 1 MiB, the URL and header refusals, only the origin in an error, an untrusted certificate refused (made at run time with `:public_key`'s test helpers, no key committed), a secret straddling the cut, and Twilio's partial delivery.

## Triage

`{Cronwatch.Triage.Anthropic, opts}` is `triage/anthropic.ts` without an Anthropic client, as the Go, PHP, and Rust ports do it: the Messages API is one POST, so it sends the request the official client makes (`conformance/triage.json`'s `wire` cases): the same URL with `?beta=true`, `anthropic-version`, `anthropic-beta` for the fallback beta, `x-api-key`, and the body byte for byte, with `cronwatch-elixir/<version>` as the user agent. The defaults are the SDK's (model, effort, tokens, the prompts, the `<job_data>` fencing, the fallbacks unless `fallbacks: false`); `max_tokens: 0` is sent as 0, as the SDK sends it. One attempt, no retries, within the smaller of 24 seconds and what the client allows. There is no official Anthropic client for Elixir, so the choice other ports weighed does not arise; the tests replay `triage.json`, all 17 cases (9 requests, 5 responses, 3 wire).

## Sources

The pg_cron source is `{Cronwatch.Sources.PgCron, repo: MyApp.Repo, jobs: ...}` in the instance's `sources:`, over a Postgres Ecto repo only, `sources/pgcron.ts` line for line as the Go and Rust ports' are: the SDK's SQL, arrays of cursors passed as text literals (`$1::text::bigint[]`), settings read from `pg_settings`, run ids `pgcron:<prefix><runid>`, the twenty newest runs copied quietly on first sight, the hold for a run queued without a start time, and jobs declared again only when their definition changed. The tests replay `conformance/pgcron.json` (29 cases), port the SDK's source tests against a fake `cron` schema, and run against a real pg_cron when `CRONWATCH_TEST_PGCRON` is set, as the Go and Rust jobs do.

## Storage

`Cronwatch.Store.Memory` is `stores/memory.ts`: a process holding the maps, so its calls are serialised as the SDK's are by its one thread, copies in and out, names sorted by byte order (Elixir compares binaries by byte, so `Enum.sort/1` is already the SDK's order), the same prune rule.

`Cronwatch.Store.Ecto` keeps the same three tables in the app's database through the app's own Ecto repo: `{Cronwatch.Store.Ecto, repo: MyApp.Repo, prefix: "cw_"}` (the SDK's prefix rule and message). The dialect follows the repo's adapter (`repo.__adapter__()`: `Ecto.Adapters.SQLite3`, `Ecto.Adapters.Postgres`, or `Ecto.Adapters.MyXQL`), and every statement is written from a dialect module (`store/sql.ex`) and run with `Ecto.Adapters.SQL.query/4`; nothing uses Ecto's schemas or query language. Ecto over the three drivers directly (Exqlite, Postgrex, MyXQL) because it is the one interface to all three, it is how nearly every Elixir app already holds its database (a repo with its pool, its credentials, and its test sandbox), and it is what Oban asks for (`repo:`), so an app that has Oban configures CronWatch the same way; `ecto_sql` is an optional dependency, and the adapter is the app's. A raw-driver store for a program with no repo was weighed and left for later (see Decisions, 6): a script can define a repo in five lines, and the SQLite driver is a NIF that an escript cannot carry anyway (see A plain crontab).

- *The schema, byte for byte.* The SQLite and Postgres `CREATE` statements are `stores/sql.ts` text for text: the same `CREATE TABLE IF NOT EXISTS` text for `jobs`, `runs` (with `seq BIGSERIAL` first on Postgres), and `state`, the same two indexes, so `sqlite_master` reads the same whoever created the tables; `INTEGER` or `BIGINT` times, `TEXT` or `JSONB` JSON, `rowid` or `seq` breaking ties, names sorted `COLLATE "C"` on Postgres; `init` under `pg_advisory_xact_lock(hashtext('cronwatch:<prefix>'))`, in one transaction of the store's own, so many processes can start at once. The MySQL dialect is the PHP, Go, and Rust ports' (MySQL 8.0.13 or MariaDB 10.6 or newer: `utf8mb4_bin`, JSON as `LONGTEXT` holding the SDK's bytes, never MySQL's `JSON` type, `ON DUPLICATE KEY`, the prune's newest start per job as a derived table, compare-and-set from version 0 in two steps, a landed write read back when MySQL counts changed rather than matched rows, `trigger` as `VARCHAR(255)`), copied from `packages/go/sqlstore/sql.go`. No Ecto migration is shipped: the tables are made by `init` on the instance's first use, as in every port, so a Node process and an Elixir process can make them in either order; an app that wants them in its migrations can call `Cronwatch.Store.Ecto.create_statements/1` from one.
- *JSONB through Postgrex.* Postgrex encodes a `jsonb` parameter through the repo's JSON library, so a binary of JSON text would be stored as a JSON string, and a map would lose its key order and JavaScript's numbers; it decodes a `jsonb` column into maps the same way. The codec is the repo's to configure, not the store's (a Postgrex types module is set once per repo), so the Postgres statements cast instead: a JSON parameter is written `$n::text::jsonb` and a JSON column read `col::text`, and `Cronwatch.JS` does the rest, in the order Postgres gives the keys. This is the one place the statements differ from `sql.ts`'s text; the schema does not (see Decisions, 7). The Rust port bound a type of its own for the same reason and kept the text; Postgrex has no way to do that without the repo's types.
- *Not the app's transaction.* Ecto binds a transaction to the process that opened it, so a store call made from a job's function inside `Repo.transaction/1` would join that transaction and be rolled back with it, and a failed run would vanish with the rollback it caused. When `repo.in_transaction?()` is true in the calling process, the store runs the statement from a task, which checks out a connection of its own, as the SDK's store writes on its own connection; the test "a run surviving the app's rollback" holds it, as it does in Rust. The Ecto sandbox in the app's tests follows `$callers`, so a test's sandboxed connection still reaches those tasks. On SQLite the task's connection waits for the app's: SQLite has one writer, and a transaction that has written holds the lock until it ends, so the task's write waits `busy_timeout` and then fails, reported as the store's error, and the job runs on. Holding the writes until the app's transaction ends would need a queue of writes the process outlives, and a write the SDK makes at once (the running row) made late, so it is left as it is and the README says to start a run outside the transaction on SQLite.
- *SQLite.* ecto_sqlite3 opens a pool of connections with its own settings (WAL by default, and a busy timeout); the store takes the repo as configured, where the SDK's store holds one connection with its pragmas, and the README says to keep `journal_mode: :wal` and a `busy_timeout` of at least 5000. `:memory:` databases are one per connection, so an in-memory SQLite repo needs `pool_size: 1`, which the store checks for and says. exqlite builds SQLite from source or takes a precompiled NIF, as the app's own dependency.
- *Foreign rows.* A row of another shape than the SDK writes, valid JSON all the same, is read as the SDK reads it rather than failing every read it is part of, with the Go and Rust audits' fixes from the start: metrics that are not all numbers keep the ones that are, a queued alert that is not an alert is dropped, times near the limits saturate, a duration is held from 0 to 2^53 - 1, a state's version that is not a whole number from 0 to 2^53 - 1 counts as 0, a MySQL write whose answer was lost counts as written when the stored row equals what was sent, and SQLite text that is not UTF-8 reads with U+FFFD.

`Cronwatch.StoreCase` is the SDK's `store-conformance.ts`, the `store.json` replay, and the finish-once scenarios as an ExUnit case template (`use Cronwatch.StoreCase, store: {MyStore, opts}`) for a store of the app's own, the Go port's `storetest` and the Rust `storetest` feature; it is compiled only when ExUnit is loaded, and is handed the fixture's text by the caller, since a published package cannot read the repository. The package's own tests run it, per database, with the `store.json` replay, the finish-once scenarios over several instances on one database, a client end to end, the rollback test, and rows of another shape: SQLite always, Postgres, MySQL, and MariaDB when `CRONWATCH_TEST_PG`, `CRONWATCH_TEST_MYSQL`, and `CRONWATCH_TEST_MARIADB` are set, each test on tables of its own prefix, dropped at the end. A node-compat test has the built SDK and the Elixir store replay the same calls into two SQLite files and compares what each reads of the other's and every column's bytes and SQLite type, and has a Node client and an Elixir client take turns on one file and one job's state version.

## Zones

Elixir's standard library has zones only through a `Calendar.TimeZoneDatabase`, and the one it ships knows UTC alone. `tz` gives the rest: the IANA database compiled into the package when it is built, so zones work the same in a release on a distroless or Alpine image with no `/usr/share/zoneinfo`, on Windows, and in an escript, and it has no required dependencies. The croner port calls `Tz.TimeZoneDatabase` directly for the offset at an instant and the periods around one (croner's `fromTZ` rule is the port's own); it never sets `config :elixir, :time_zone_database`, which is the app's to set, and an app that has chosen `tzdata` keeps it for its own code. `tzdata` was weighed and left out: it needs hackney and an ETS-backed server, and by default fetches new data from IANA at run time and writes it to disk, which a library should not start in someone else's app. Reading the system's database ourselves, as jiff does for the Rust port, was weighed too: it would drop the dependency, but the commonest Elixir deploy (a release in a slim container) has no database to read. Zone names are matched without regard to case, as `Intl` does, against the names tz knows, and fixed offsets (`+05:30`) are zones too, as croner accepts them. Without a `timezone`, a cron is read in the process's own zone, which the BEAM does not name: `$TZ` when it names a zone, else the name `/etc/localtime` links to, else UTC.

`time_zone_database:` on the instance takes any `Calendar.TimeZoneDatabase` module in place of tz, for an app that wants one database for everything; tz stays a dependency either way (see Decisions, 3).

## Redaction and expect patterns

Secret redaction uses the SDK's patterns, copied verbatim as JavaScript source into `Cronwatch.Output` and run by `Cronwatch.JSRE` over UTF-16 code units, so a quantifier counts an emoji as two, `\s` is JavaScript's set, `\b` and `/i` are ASCII-only as they are in JavaScript without the `u` flag, and every one of `conformance/output.json`'s 204 redaction cases gives the SDK's bytes. The engine is the Go port's `internal/jsre`, as carried over and hardened by the Rust port's audit, and reads a subject converted once to UTF-16 (`:unicode.characters_to_binary(text, :utf8, {:utf16, :big})`), indexed in constant time with `binary_part/3`. It refuses what it does not implement rather than read it as something else.

Elixir's `Regex` was weighed and left out for both redaction and stored patterns: it is `:re`, which counts in bytes or code points and never in UTF-16 units, reads `$` as matching before a final newline, has its own `\s` and `\b`, and moved from PCRE to PCRE2 with OTP 28, so one pattern could answer differently on the two ends of the supported OTP range. The Python port showed the SDK's patterns can be rewritten for another engine, but the rewrite has to be proved again whenever the engine changes, and a stored `matches /.../` pattern is JavaScript source that no rewrite can foresee.

The Rust audit's bounds come with the engine, as rules rather than findings: a pattern longer than 4096 characters or with groups nested more than 100 deep is not read; a match gives up past 512 frames of recursion; and a stored expect pattern counts its steps (each attempt at a node, and each code unit a repeat scans) and gives up past 10 million, a fifth of the Rust port's (see Decisions, 14). The BEAM would not crash where Rust's stack did (a process's stack grows on its heap), so the frame cap is kept for the same answers as the other ports, not for safety. A stored pattern that runs out of its bound fails, with the ordinary `Output did not match /source/flags`: a pattern is slow because it is searching an output it does not match, so failing is the answer an engine that finished gives in nearly every case, and a guard that passed when it could not tell would hide the broken job it is there to catch (the Rust port's decision 36, the rule every bounded port keeps). The SDK's own redaction patterns are bounded and run without a budget. A long match does not stall other work here, since the scheduler preempts a busy process, but a step costs the BEAM some twenty times what it costs Rust, which is why the budget is smaller (see Decisions, 14). The JSON reader refuses nesting past 256, as the Rust port's does, for the same answers on the same inputs.

## Dashboard

`Cronwatch.Web` is the SDK's `cw.routes()` as a Plug: its answers are `routes/index.ts` line for line and its pages are `routes/html.ts` and `routes/timeline.ts` byte for byte, the CSS, the app shell, the icons, the sign-in form, and the `<wbr>` after a name's separators included; `web/` is the Rust port's `web/`, carried over. In Phoenix it is mounted with `forward`, outside the `:browser` pipeline (the dashboard has its own cross-site check and cookie; Phoenix's CSRF plug would refuse its forms):

```elixir
# lib/my_app_web/router.ex
scope "/" do
  forward "/cronwatch", Cronwatch.Web      # the token from CRONWATCH_TOKEN, read per request
end
```

and in a plain `Plug.Router` the same way. The options are the SDK's: `instance`, `token` (a binary, `false` for none, or left out to read `CRONWATCH_TOKEN` with `""` counting as unset), `base_path`, `origin` (read as `new URL(value).origin` reads it, by a port of the Go port's `routes_origin.go`; anything but http or https is refused with the SDK's message), and `trust_proxy`. Phoenix calls a forwarded plug's `init/1` when the router is compiled, so `init/1` only checks the options' shape and keeps them; the token, the environment, and the instance are read on each request, and a token given as `{:system, name}` is read from the environment then too, so a release does not bake in the value its build machine had.

What a request says is read as the SDK reads a fetch `Request`, carried over from the Go and Rust ports: the path from `conn.request_path` as sent (Plug does not decode it, so a `%2F` in a job name stays one), the query from `conn.query_string` as `URLSearchParams` parses it, headers joined as `Headers.get` joins them, the body as `request.json()` and `request.formData()` read it, read only once a route wants it and capped at 1 MiB and one byte (`Plug.Conn.read_body/2` with that length; 413 past it, as the Go, Python, PHP, and Rust ports answer), and the origin from the scheme the adapter reports and the raw `Host` header. The base is `base_path` when given, else where the router mounted the plug (`conn.script_name`, which `forward` fills in, so a mount under a path parameter or nested twice is found as Rust finds axum's), else the SDK's `/cronwatch`.

- *Response headers.* A `Plug.Conn` starts with Plug's own `cache-control: max-age=0, private, must-revalidate`; the dashboard replaces it with the SDK's `Cache-Control` or deletes it where the SDK sends none, and sets every other header in the SDK's order and lowercase, as Plug requires and fetch sends.
- *A body Phoenix already read.* A Phoenix endpoint runs `Plug.Parsers` before the router, which reads a form or JSON body and leaves nothing to read. The dashboard then takes `conn.body_params` (a form's fields as strings, JSON through the endpoint's JSON library, a file as `[object File]`) when its own read of the body comes back empty, which gives the same answer for every body the dashboard's own pages and `@cronwatch/mcp` send, and does not hold a body the parsers read to its 1 MiB cap by its `Content-Length`, since the endpoint's own limit has already applied; a malformed JSON body is refused by `Plug.Parsers` itself before the dashboard sees it (see Where it cannot match the SDK). Mounted in a plain `Plug.Router` without parsers, or ahead of them, it reads the raw body.
- *The development token.* With no token set, in development (see Rules), the dashboard makes one (32 bytes from `:crypto.strong_rand_bytes/1`, base64url) and announces it once per mount on standard output with `IO.puts/1`, where `console.info` writes it (a closed output is ignored, as `console.info` never throws); it is kept in the instance's ETS table under the mount's options, written with `insert_new` so two first requests at once agree on it, and every request process sees the same token for as long as the instance runs (see Decisions, 39). The line shows the host only when `origin` is set or the request's origin is loopback (`localhost`, `*.localhost`, 127.0.0.0/8, `[::1]`), the SDK's `developmentSignInLine` and `isLoopbackOrigin`, and the origin is read as a URL before its host is tested, as the Rust audit found it must be: a `Host` of `evil.example/.localhost` or `localhost:1@evil.example` is not loopback, and a string test on the header took both for it. Bandit and Cowboy do not refuse every such header, so the test is the only guard. `Cronwatch.Web.token/1` is the token in use, the generated one included.
- *Carried over from the audits.* A `Host` outside ASCII longer than 1024 bytes is not punycoded or read as a URL; a body that could not be read to its end is read as none, never as the part that arrived (`for=7d` cut short is not a 7 ms silence); a request process that ends before its answer (a client gone away) reports nothing; the token and cookie are compared in constant time with `:crypto.hash_equals/2`.

The style sheet, scripts, and icons are the SDK's files copied into `lib/cronwatch/web/assets`: `scripts/make-dashboard-icons.mjs` writes the icons there beside the other ports' copies, and `packages/ruby/test/web/golden.mjs` writes `style.css`, `app.js`, and `sw.js` from its captures, and both, run with `--check` by `npm run check:conformance`, fail when a copy differs from the SDK's. Each script gets its Elixir destination in phase 3.

`test/web/golden_test.exs` replays the gem's fixture, `packages/ruby/test/web/golden.json` (59 captures of the SDK's routes over a fixed seed, PNGs as base64), three ways: straight into the plug with `Plug.Test`, through a `Plug.Router` `forward` under a real Bandit server (its base path found from the mount), and through a minimal Phoenix endpoint and router, a test-only dependency, so the body `Plug.Parsers` has already read is replayed too; every status, header, and body matches, `content-length` and what Bandit adds itself aside (its `date`, the `vary: accept-encoding` its response compression sends, and the `connection: close` the test's client asks for). The SDK's routes tests are ported as the Go and Rust ports have them (the token, the cookie, the forms, the cross-site check, the origin and the forwarded headers, the silence durations, the body cap, the app shell, the base path from the mount, the audits' cases), in `test/web/`: `routes_test.exs` straight into the plug, `server_test.exs` through Bandit and Phoenix (mounts under a longer path, a path parameter, and a Phoenix scope, a body cut short and one past the cap over the wire, JSON Phoenix cannot parse), and `env_test.exs` for what depends on the environment (locked, the development token and its sign-in line, a handler without a secret), which runs after the async tests since the environment is the node's, with no child processes of the kind Rust needed. A behaviour change lands in TypeScript first, and `TZ=UTC node packages/ruby/test/web/golden.mjs` regenerates the fixture for every port.

## Handler

`Cronwatch.Handler` is the SDK's `handler()`, for a platform cron that calls a URL (Fly.io, Render, Gigalixir, a Kubernetes CronJob with `curl`), as a Plug:

```elixir
forward "/cron/nightly", Cronwatch.Handler, job: "nightly-report", run: {MyApp.Reports, :nightly, []}
```

It runs the function (an MFA, given the context and the `conn` before its arguments, since a router's options cannot hold an anonymous function) as a recorded run of the job the instance declares under `job:` (declared with no options on the first request when it does not) with the trigger `"handler"` for each request whose `Authorization` is `Bearer <secret>`, compared in constant time; the secret is the option's (a binary, or `{:system, name}` read on each request), else the instance's (`CRON_SECRET` by default, read on each request, `""` counting as unset); `secret: false`, or the instance's `cron_secret: false`, lets anyone run the job. With no secret and no opt-out, outside development, it answers 503 with the SDK's JSON; a wrong or missing bearer is 401. A run is answered with `{"ok","job","run","status","durationMs"}`, 200 or 500, and the error's first line only when a secret was required, with the headers of the SDK's `json()`. The function may answer the request itself and return the `conn`, which is passed through (sent as it is when sent, sent when it has a response set, answered with the run's JSON when it has none) and fails the run at 400 or more with `HTTP <status> <reason>`. The handler answers with the run as recorded, which `Cronwatch.Run.Exec` hands it through an internal `recorded:` option, rather than reading it back from a store that may be down. A raise is a failed run answered 500, as the SDK answers a throw. The function runs in the request's process, so a request whose client goes away and whose process the server ends records a failed run (see Runs); an app that wants the job to outlive the request starts it under its own `Task.Supervisor`.

## Scheduler integrations

The SDK has none; these follow the Go and Rust ports', whose shared rules (declaring entries as jobs, several entries of one name on different schedules being one job without a schedule, tags for the integration and the app, jobs gone declared again without their schedule, workers elsewhere declaring from the store's definition, schedules checked against the scheduler's own fire times, retries as the gem's Sidekiq rules) are `Cronwatch.Bridge`, carried over from `packages/rust/cronwatch/src/bridge` with both ports' audit fixes from the start: `unschedule` reads what is declared again under the declaring lock and writes every declaration before it returns; a declaration's write is held to 30 seconds, and a sync an integration starts itself to 30 more; `fallback` reads the store before it declares and declares nothing when the read fails; a panic (here, a raise) in one declaration's write is that declaration's failure and never leaves the writer marked busy. `Cronwatch.Bridge.Watch` is a process of its own, and that process is the declaring lock: `declare/2`, the end of `fallback/3`, and `unschedule/1`'s declarations run in it one at a time, while the store is read and written in the caller or in a task of the instance (each write in a task held to the deadline and killed past it), never in the watch, so a hung store never blocks a lookup. The Go audit's other two fixes come with the telemetry integrations. A run whose start failed needs a placeholder, as the Go port's gocron integration found, because a `:start` event and its `:stop` or `:exception` are separate calls: each `:start` pushes onto a stack in the running process's dictionary what its end pops, a placeholder when the attempt is not watched or its start failed, so the two always pair, however jobs nest (Oban's inline testing mode runs a job inserted inside another's `perform/1` there and then). Asynq's task types were remembered as not jobs, with a window and a cap, because its middleware looked the store up for every type it saw; here neither integration looks the store up for a job it was not told of (an Oban worker outside the crontab and not named is ignored without a read, and a Quantum job is always one the scheduler lists), so nothing is remembered and the case does not arise. The app tag is the PHP port's `appTag()` character for character (MD5 through `:crypto` when empty or long), and the app is the integration's `app` option, else `$CRONWATCH_APP_ID`, else the OTP application that started the instance.

Each integration is given in the instance's options (`integrations: [{Cronwatch.Oban, oban: Oban}]`), checked when the instance starts (a module whose scheduler is not a dependency is refused by name), and started last under its supervisor, so it attaches its telemetry handlers after the instance can record and detaches them when it stops. A run seen through telemetry is opened and closed by `Cronwatch.Run.Exec.open/2` and `close/2` (or `take_back/2`), the two halves of `run/3`: the running row, the monitor on the process, the context for `current/0`, and the Logger metadata are `run/3`'s, so a worker killed part way is recorded at once, as any run is. A handle (`Cronwatch.start/2`) was the first plan and was left: its lines are dropped when its owner dies, which would race the monitor's record of that death.

### Oban

`Cronwatch.Oban` watches Oban without changes to the app's workers: one entry in the instance's options. It needs Oban 2.20 or newer in the 2 line (`~> 2.20`, released 2025-08-14): the Cron plugin has marked the jobs it inserts with `meta["cron"]` and the expression since 2.18, and with the zone (`cron_tz`) since 2.20, the oldest release that writes both, which phase 4 confirmed by reading each release's plugin. The integration itself reads only the flag and the crontab, and its tests pass on 2.19.0 too, so the floor is the design's rule rather than a need of the code. The tests run on 2.20.0 and the newest (2.24.1).

- *Which jobs.* The jobs of the Cron plugin (`Oban.Cron`, `Oban.Plugins.Cron` before 2.24), read from `Oban.config(name)`'s plugins when the integration starts and again whenever Oban's supervisor or its Cron plugin starts (`[:oban, :supervisor, :init]` and `[:oban, :plugin, :init]`), so an Oban started after the instance is found: each worker in the crontab is a job named after its module as Elixir writes it (`MyApp.Workers.NightlyReport`), on the entry's expression (a nickname written out as Oban reads it, `@daily` as `0 0 * * *`; `@reboot` is no schedule) in the entry's `timezone`, else the plugin's, else `Etc/UTC`, the entry's other options unread; a worker with several entries on different expressions is one job without a schedule, as the bridge has it. Each schedule is checked with `Bridge.check_fires/7` against Oban's own reading (`Oban.Cron.Expression.now?/2` on each minute of UTC read in the zone, as the plugin asks it; the walk steps over a day or an hour the expression does not name, and a minute at a time wherever the zone's offset changes): Oban matches a day of the month and a day of the week both, where croner (JavaScript) matches either when both are set, and reads its own nicknames, so an expression the two read differently is reported once and watched without a schedule, as the Rust port does for tokio-cron-scheduler. Workers outside the crontab are watched only when named (`workers: [MyApp.Workers.Import]`, or `{module, job_options}`, which also gives a crontab worker's job its options), so a queue of a million email jobs is not a million runs; a job the Cron plugin inserted is known by `meta["cron"]`, so a node whose own crontab lacks it (or whose Oban runs in a testing mode, which drops the plugins) records it all the same, declared from the store's definition through the bridge's `fallback`. `defaults:` are job options for every job, before its schedule.
- *Each attempt a run.* Handlers on `[:oban, :job, :start]`, `:stop`, and `:exception` run in the worker's own process, so `:start` opens a run (trigger `oban`, id `oban:<app>:<job id>:<attempt>`, with the jobs table's prefix before the job id when it is not `public`, since a job's id is unique only within its table and two apps may share one store, and `.<times snoozed>` after the attempt once the job has snoozed, since from Oban 2.24 a snooze gives its attempt back and the execution after it would otherwise share the snoozed one's id) and puts its context in the worker's process dictionary, which makes `Cronwatch.current/0` and `Cronwatch.log/1` work inside `perform/1` with no code, and `:stop` or `:exception` finishes it. A retry is a new attempt and a new run: failing attempts open one failed alert and the one that succeeds closes it, and `failures_before_alert` says how many attempts to allow first. The worker's process is monitored like any run's, so a job killed at its `timeout/1` or by a node shutting down is a failed run at once; Oban then reports the attempt from another process, whose empty stack pops nothing. A handler that raises is reported, never left to raise, since `:telemetry` detaches a handler that raises.
- *What Oban gives back.* A `{:snooze, seconds}` is taken back as a run given back (the row deleted with `delete_run_if`, nothing judged), as River's snooze is in the Go port and apalis's `RetryAfterError` in the Rust one, since the job did not fail and will run again. A snooze the store cannot take back (a store of the app's own without `delete_run_if`, or a delete that failed) is written as an `ok` run and not judged, so it neither recovers the job nor resets its failures in a row (the review's finding 52: it was judged as a success, and the retry after it, with the same id, was dropped). `{:cancel, reason}` (and the older `:discard`) is a failure, written as Oban's own `Oban.PerformError` (`MyApp.Worker failed with {:cancel, reason}`): the worker gave up on the job, as an apalis `AbortError` returned to stop retries is. A run that may be given back closes missed and stuck only once it is known not to be, the Go audit's rule, so a snooze leaves the job's state as it was. A job Oban discards after its last attempt is that attempt's failure, nothing more. An attempt left `running` by a node that died before its monitor could record it (the whole node gone) is closed when Oban's Lifeline rescues the job and its next attempt starts: that start finishes the earlier attempt's run, if still running, as failed with `Oban rescued the job after its node stopped`.
- *The check.* `Cronwatch.Oban.CheckWorker`, put in the Cron plugin's crontab (`{"* * * * *", Cronwatch.Oban.CheckWorker}`), runs `Cronwatch.Oban.sync/1` (the crontab declared again, `settle`, then `unschedule`, all within 30 seconds) and a check once per minute across the cluster, since the plugin inserts it once on the leader; its runs are never a job. An instance other than the default is named in its args (`args: %{instance: "MyApp.Cronwatch"}`), read with `String.to_existing_atom/1` and only when an instance of that name is running, so no atom is made from a job's args.
- *Not supported.* Oban Pro's `DynamicCron` stores its crontab in the database and is a commercial package this repository cannot test; its jobs are watched as named workers without a schedule until someone asks.

The tests run a real Oban, not its testing modes (which drop the plugins, so the crontab could not be read): on SQLite through Oban's Lite engine always, and on Postgres through its Basic engine when `CRONWATCH_TEST_PG` is set, the node never the leader so the plugin inserts nothing on its own, the jobs inserted as the plugin inserts them and run with `Oban.drain_queue/2`: the crontab declared (a nickname, a zone, an expression Oban reads differently reported, the check worker left out), a job failing twice and then succeeding (three runs with the attempts' ids, one alert and its recovery, the output and metrics logged through `current/0`), a snooze given back and a cancel failed, a raise, workers watched only when named, a job killed at its `timeout/1` by a running queue, an attempt left running closed by the rescue's next attempt, and the check worker unscheduling a job the crontab dropped.

### Quantum

`Cronwatch.Quantum` watches a Quantum 3.5 scheduler (`scheduler: MyApp.Scheduler`), the other scheduler Elixir apps use. Phase 4 kept it (see Decisions, 16): its repository is not archived and is kept current (the last commit 2026-09-22, dependency updates), though its last release, 3.5.3, is from February 2024; and its telemetry is enough, with the start, stop, and exception of each run in the task that runs it and an event for each job added, updated, or deleted.

- *Which jobs.* Every job of `MyApp.Scheduler.jobs()` with a name, named after it (`:nightly_report` is `nightly_report`); an unnamed job (a reference) is named after its task when that is `{Module, :function, args}` (`MyApp.Reports.nightly`: a job name cannot hold the `/` of an arity), and otherwise reported once and not watched. Only active jobs are declared; one deactivated is a job gone. Its schedule is the `Crontab.CronExpression` composed back to text (without its year field, and an extended one with its seconds first, as croner reads six fields; one that names years is not converted), in the job's `timezone` (`:utc` is `UTC`), checked against Quantum's own reading with `Bridge.check_fires/7`: the `crontab` package's next time from the zone's clock, turned back into an instant, a time that does not exist or happens twice in the zone stepped over a minute on, as Quantum's execution broadcaster does (so Quantum runs neither 01:30 of the night clocks go back, where CronWatch expects the first). One that differs is reported once and watched without a schedule. `jobs:` gives options by the Quantum job's name, `defaults:` for every job.
- *Each run a run.* Quantum's `[:quantum, :job, :start]`, `:stop`, and `:exception` events, in the task that runs the job, start and finish a run (trigger `quantum`), with the context in that task's process dictionary.
- *Jobs added and removed at run time.* `[:quantum, :job, :add]`, `:update`, and `:delete` are sent from inside Quantum's job broadcaster, before it has changed its jobs and while a call to it would deadlock, so each only asks the integration's process to read `jobs/0` again, which it does once the broadcaster is free; the jobs are read again every minute besides, which also finds a scheduler started after the instance. A job deleted or deactivated is declared again without its schedule, as the bridge has it.
- *The check.* `Cronwatch.Quantum.check/1`, given to the scheduler as a job's task (`{Cronwatch.Quantum, :check, [[scheduler: MyApp.Scheduler]]}`), runs `sync/1` (the jobs declared again, then `unschedule`, within 30 seconds) and a check; a job whose task it is is never a job.

The tests start a real Quantum scheduler, on schedules that do not fire while they run, and run its jobs with `run_job/1`: the jobs declared (a zone, an extended expression, an unnamed job named after its function, one with an anonymous function reported, one Quantum reads differently reported, an inactive one left out), runs recorded with their output, a raise and an `{:error, reason}` failing, jobs deleted and added at run time followed, and the check unscheduling a job the scheduler dropped; they pass on Quantum 3.5.0 and 3.5.3.

### A plain crontab

A script a crontab runs needs no integration: start the instance, run the job, `System.halt(1)` on failure, and a second crontab line runs a check, both on a store both processes reach. In an Elixir release that is two `eval` lines: `bin/my_app eval "MyApp.Nightly.main()"` and `bin/my_app eval "Cronwatch.Release.check(MyApp.Cronwatch)"`, where `Cronwatch.Release.check/2` starts what the check needs (the repo, the instance, with the configuration the app keeps in `config/runtime.exs` under `config :my_app, MyApp.Cronwatch`) without starting the app's endpoint or queues, runs one check, prints its result (`cronwatch: checked 3 jobs, sent 1 alert`), and exits non-zero on an error, as the Ecto migration helpers apps keep in `MyApp.Release` do. The configuration is found among the loaded applications' environments by the instance's name, or named with `otp_app:`, or given with `config:`; `check_every` and `integrations` are left out, since the process checks once and ends, and the repo is started with at most two connections, as the Ecto migrator starts one, unless it is running already. `halt: false` answers the failure rather than halting, for the tests. Called where the instance is already running (`bin/my_app rpc` into the live node), it checks that instance as it is, starts and stops nothing, and never halts the node. From source, `mix cronwatch.check [MyApp.Cronwatch] [--otp-app my_app]` does the same after loading the project's configuration. `examples/crontab` is that program on SQLite, with a test that runs its built release twice on one file, as two crontab lines would.

A command-line tool of its own (an escript `cronwatch run nightly -- ./backup.sh`) was weighed and left out: an escript cannot carry a NIF, so it could not open SQLite, and the app's configuration lives in the app's own project. It is made only if someone asks, as the Rust port decided.

## Keeping in step

`conformance/` at the repo root holds JSON cases generated from the TypeScript build by `scripts/conformance.mjs`. The Elixir tests replay every case, comparing values as the JSON the SDK writes, byte for byte, reading the files from the repository (`Path.expand("../../conformance", __DIR__)`; the package's `files` keep them and the tests out of the Hex tarball): `duration.json` (103 cases) and `schedule.json` (647) against `Cronwatch.Duration` and `Cronwatch.Schedule`, `output.json` (231) against `Cronwatch.Output`, `evaluate.json` (46 scenarios, every event played through the pure functions, as the script's `Sim` plays them), `format.json` (94) and `health.json` (118) in the core, `store.json` (22) against every store, `channels.json` (602) against the channels, `triage.json` (17) against triage, and `pgcron.json` (29) against the source. A test fails when the SDK writes a fixture file this port does not know. The tests run with `TZ=UTC`, as the fixtures are made; `test_helper.exs` refuses to start otherwise, and the `mix test` alias sets it. A behaviour change lands in TypeScript first, `npm run conformance` regenerates the fixtures, and this package is fixed until they pass. Nothing new is expected in the fixtures for this port: the PHP and Go ports already added what a port without the official clients needs (`triage.json`'s `wire` cases).

Croner parity is also checked against croner itself, as the other ports do: 3,000 expressions from three fixed seeds in zones with and without daylight saving, from times around the clock changes, where the SDK in Node (reading `packages/sdk/dist`) must give the same error message or the same fire times; it skips, with the reason, when `node` or the built SDK is missing. The same generator run against Oban's and the `crontab` package's readings is a report, not a gate, so the reason for porting rather than depending (below) stays measured, as the Rust port's report on the `croner` crate does.

*Why port croner rather than use the `crontab` package.* `crontab` is what Quantum uses and the most downloaded cron parser on Hex, so it was the first thing weighed. It is a separate implementation of Vixie cron with extensions, not a translation of croner 10: its options, its error messages, its reading of some forms (`?`, `W` and `L` combinations, `#`, `+`, a seventh field, the day of the month against the day of the week), and its fire times around clock changes are its own, and nothing holds them to the JavaScript. CronWatch needs the SDK's messages and fire times byte for byte, which four ports already get from a line-for-line translation checked against croner itself; the Rust port's `schedule::cron` is the nearest code to start from.

## Where it cannot match the SDK

What is known before any code, mostly shared with the Go and Rust ports; phase 5 completes the list.

- A bad zone is refused when the expression is read rather than when a fire time is asked for. This is the Go and Rust ports' answer, for the same reason. (A date no month has, `0 0 30 2 *`, never fires, and a one-time date string is refused with `CronPattern: a one-time date is not supported`: these were differences until 0.11, when the SDK took the same answers.)
- Zones come from tz's copy of the IANA database, which is as new as the tz release the app locked, where Node's comes with its ICU; a zone that changed its rules recently can differ until the app updates tz. Without a `timezone`, a cron is read in the zone `$TZ` or `/etc/localtime` names, else UTC.
- Error names are Elixir module names (`RuntimeError`, `DBConnection.ConnectionError`), frames are `Module.function/arity (file:line)`, and a throw, an exit, and `{:error, reason}` have forms of their own (see Rules), not JavaScript's classes.
- `{:error, reason}` and `:error` returned from a job's function fail the run; the SDK has no such convention.
- A run whose process dies while the function runs is recorded as failed at once, with the exit reason; the SDK has no way to kill a running function. With `kill_at_timeout`, a run is recorded as a check would mark it, before any check does.
- A value logged that is not a binary is written with `to_string/1` where it implements `String.Chars` and `inspect/1` otherwise, where JavaScript writes objects as JSON; `Cronwatch.log/2` takes one value, where `console.log` joins its arguments.
- A map given where the SDK keeps an object's order (a `budget` or `floor`, metrics given at once) is written in its keys' term order, since Elixir maps have none; a keyword list or a list of pairs keeps the order given.
- `Console` writes through Logger, not to the console streams, so the line carries Logger's format and metadata.
- The default transport sends no `user-agent` and no `accept-encoding`, where fetch sends its own, and triage's user agent is `cronwatch-elixir/<version>`. It sends `host` first and `content-length` and `connection: close` last, around the SDK's headers in their order; a framing header an app gives (`host`, `content-length`, `transfer-encoding`, `connection`, and the like) is replaced by the transport's own.
- An answer whose head is longer than 64 KiB or 256 lines fails as `<origin>: header_too_long`, and one that is not HTTP as `<origin>: invalid_response`, where fetch says `fetch failed`; a body cut short or badly chunked is read as none, the status kept.
- A webhook URL whose host is outside ASCII is refused as `not this URL`, since OTP has no IDNA to punycode it.
- A redirect is an answer outside 2xx (`... answered 307`), where fetch with `redirect: "error"` throws `fetch failed`; either way nothing is sent where it points. A request that gets no answer fails with `<origin>: <the socket's or the resolver's reason>` (`econnrefused`, `nxdomain`), in place of fetch's `fetch failed`.
- A body past 1 MiB is answered 413; the SDK leaves the limit to the server in front of it. Behind a Phoenix endpoint, the endpoint's `Plug.Parsers` reads the body first: a malformed JSON body is refused by Phoenix (`Plug.Parsers.ParseError`, 400, Phoenix's page) before the dashboard sees it, a JSON body is read by the endpoint's JSON library (a duplicate key keeps the last value, as `JSON.parse` does, but numbers past 2^53 read as integers), and the endpoint's own body limit applies.
- A request target the HTTP server refuses (Bandit's or Cowboy's own 400 for a malformed target) never reaches the plug; the plug answers such a path as the SDK does when it is handed one.
- A dashboard mounted twice with the same options (the instance included) shares one development token and one announcement, where each SDK `routes()` makes its own. An endpoint with `Plug.Head` turns a `HEAD` into a `GET` before the router, so a `HEAD` of a page is answered as a `GET` is, where the SDK answers 404. A body cut short over the wire is read as none, as the SDK has it, but Bandit closes the connection without the answer, having no one to write it to.
- An interval longer than 2^53 ms is held at 2^53 ms, as in the Go and Rust ports. (A silence ends on a whole millisecond, held at 2^53 - 1, as the SDK now has it too.)
- The dashboard's locked page and a handler's 503 name the Elixir options (`token:`, `token: false`, `secret: false`), where the SDK names its own.
- A run failed by an HTTP answer names the status's standard reason (`HTTP 503 Service Unavailable`), from Plug's table, where a `Response` the SDK's function builds itself has none (`HTTP 503`); without Plug loaded (a `Req.Response` in an app with no Plug) there is none here either.
- Two starts with one id at once in one instance answer two handles on the one run, where the SDK hands both callers the same handle (see Decisions, 25).
- JSON nested more than 256 deep is refused, a request body so nested reads as none, and a stored value so nested fails its row's read; a stored `matches /.../` pattern that recurses past 512 frames or runs out of its 10 million steps does not match, and one of more than 4096 characters or with groups nested more than 100 deep is not read. These are the Rust port's bounds, kept for the same answers.
- A job given an expect function with a different function is not declared again by a source (both store `custom function`); the SDK compares the function's source text.
- The SDK has no scheduler integrations, no `delete_run_if`, no isolated runs, and no telemetry.
- An alert's `at` is read as a whole number, as it always was here, so a foreign queued alert whose `at` has a fraction is keyed by its whole part (`health.json`'s one such `alertKey` case is replayed that way); the SDK keys it by the number as JavaScript prints it. Every alert a port composes has a whole `at`.
- A state's `sending` is written after `undelivered`, where the SDK's spread may put it after `version`; the value is the same, only the key's place differs.
- There is no `close()`: an instance stops with its supervisor. Stopping it waits for a check under way (the checker's shutdown is `:infinity`, the wait bounded by the check's own limits) before the store and the rest of the instance stop, as the SDK's `close()` waits; runs being recorded are not waited for, as in the SDK.

## Decisions

The owner settled the draft's open questions before phase 1, taking each recommendation:

1. **The Hex name** is `cronwatch`, claimed by the first batched release after phase 1 works, with no placeholder published. If it is taken first, the package is `cronwatch_sdk` with `app: :cronwatch`, so every module is still `Cronwatch`.
2. **The floor** is Elixir 1.18 on OTP 27, tested there and on the current release (Elixir 1.20 on OTP 29).
3. **Zones** come from `tz`, a required dependency, called directly and never set as the app's database; `time_zone_database:` for an app that wants its own comes with the phase that needs it. Neither `tzdata` nor the system's database.
4. **JSON** is `Cronwatch.JS` for everything that leaves the process; no Jason dependency; the public structs implement `JSON.Encoder` for the app's own use.
5. **HTTP** is `:httpc`, hardened in the one POST function, as the default transport, with a `Cronwatch.Transport` behaviour for Req or Finch; a shipped Req transport only if someone asks. The audit replaced `:httpc` with a POST of the package's own (see 33).
6. **Stores** are Ecto only (`Store.Ecto` over the app's repo, with any of the three adapters); a store over a raw Postgrex or Exqlite connection only if someone asks.
7. **Postgres's JSON casts**: `::text::jsonb` on JSON parameters and `::text` on JSON columns read, the one place the statements differ from `sql.ts`; the schema stays byte for byte.
8. **The instance** is a child spec, `{Cronwatch, opts}`, named `Cronwatch` by default, with jobs declared in its options or at run time; no `use Cronwatch` module.
9. **A run's function** runs in the caller's process by default, with the timeout as the SDK's signal (`cancelled?/1`); `isolate: true` runs it in a supervised task, and `kill_at_timeout: true` (with `isolate`) stops it at the timeout, recorded as a check would mark it.
10. **`{:error, reason}` and `:error` fail a run.**
11. **Wire values stay strings**: statuses, conditions, alert types, and health are the SDK's strings, with functions naming the known ones; no atoms made from stored text.
12. **Telemetry** is a required dependency, with the events above, and `cronwatch_job` and `cronwatch_run` are Logger metadata during a run. Copying a run's Logger output into its recorded output only if someone asks.
13. **Console writes through Logger**: `Logger.info` for a recovery and `Logger.error` otherwise, with the SDK's text.
14. **The step budget** is the Rust port's 50 million steps, with the same fail rule, and the 512 frames, 4096 characters, 100 groups, and 256 JSON levels. Phase 1 measured it on the BEAM (OTP 29, an Apple M-series machine): a stored `\n*\n*\n*\n*\n*x` over 32,000 newlines runs out of its budget in about 1.55 seconds, and `.*x` over 32,000 characters in about 1.43, both under the two seconds the draft set as the line, so the budget stood. The engine kept its character sets as tuples of 2,048 32-bit words to get there; a first version on binary bitmaps took up to 1.97 seconds. The audit lowered it to 10 million: on CI's runner (Elixir 1.18.5, OTP 27.3) two exhausted budgets of 50 million took 22 seconds, some 11 a pattern, which a runaway `expect` would add to a run's finish. At 10 million, over 32,000 characters, `\n*\n*\n*\n*\n*x` gives up in 0.34 seconds, `.*x` in 0.32, `(?:a|b)*x` in 0.37, and `(?:a+a+)+x` in 0.47, on OTP 27 and 29 alike (about 2 seconds on that runner). A pattern that does not backtrack uses some 16,000 steps over the capped output, so only one needing between 10 and 50 million steps answers differently from the Rust port, failing as the fail rule has it. Sets of up to four ranges are now tuples of their ranges, each set held once in a table of the pattern's own.
15. **Oban's scope**: the Cron plugin's jobs by default, other workers only when named, Oban 2.20 or newer (confirmed in phase 4, see 44), snooze given back and cancel failed; Oban Pro's `DynamicCron` not supported until someone asks.
16. **Quantum** is built in phase 4, and dropped from it if Quantum is archived or its telemetry proves too thin to record runs without wrapping jobs. Phase 4 kept it: neither is so (see Quantum).
17. **A command line**: `Cronwatch.Release.check/2` (the instance's name, and options) for `bin/my_app eval` and `mix cronwatch.check` from source; no escript.
18. **Publishing**: the first publish by hand, then `hex.yml` with a publish-only `HEX_API_KEY` in the `hex` environment, off until `HEX_ENABLED` is `true`; trusted publishing, and the key revoked, when Hex ships it. No second package owner for now.
19. **The environment** is read from `CRONWATCH_ENV`, then `APP_ENV`, then `MIX_ENV`.

Phase 1 settled these, which the draft left open:

20. **The store behaviour's shape.** A store is `{module, opts}`; the instance calls `c:new/2` with the options and its own name, and what that answers (the store's handle) is the first argument of every other callback. Callbacks answer `{:ok, value}`, `:ok`, or `{:error, reason}`, and a raise, throw, or exit in one is taken as its error. `init/1` keeps the SDK's name, so a store that is also a process keeps its process in a module of its own: the memory store's is `Cronwatch.Store.Memory.Server`, started under the instance, and `{Cronwatch.Store.Memory, server: name}` shares one started elsewhere (the SDK's tests run several clients on one store).
21. **A run's lines and metrics live in rows of the instance's ETS table** (`Cronwatch.Lines`), one row per line, numbered with `:ets.update_counter/3`, so a log from any process is one write with no message and no lock; the window, the head kept for `expect`, and the metrics' order are the SDK recorder's rules over those rows. A handle's lines use the same rows under the handle's key; `flush/1` takes them and puts back what it could not write.
22. **`current/0` through `$callers`** reads each caller's process dictionary (`Process.info/2`) for the run it is running, rather than keeping a table of processes, so nothing is left to clean up when a run ends.
23. **`Cronwatch.start/1,2`** served both of the SDK's starts by its first argument until 0.11: a job (or its name) starts a run and answers a handle, a keyword list (`every:`) started the interval. From 0.11 the interval is `Cronwatch.start_checking/1`, the SDK's `startChecking()`; `start/0` (`@deprecated`) and `start/1` given a keyword list (which warns when called, since `@deprecated` cannot mark one clause) still start it, and go in 2.0.
24. **The clock** (`clock:`) is a function of no arguments or a module with `now/0`, in epoch milliseconds; the timers (a job's timeout, the interval) are the BEAM's own, so the tests drive time with the clock and use short real timeouts where a timer must fire.
25. **A start with an id** is held to one per job and id within an instance by `Cronwatch.Locks`, keyed by both; a second concurrent start waits, then finds the stored run and answers a handle on it, where the SDK hands both callers the one promise.
26. **A metric that is not a number raises `Cronwatch.Error`**, as the SDK's `metric()` throws, so it fails the run unless the function handles it.
27. **A handle's outcome** is `nil` (success), the run's text, `{:ok, result}` (judged as a job function's result), or `{:error, reason}` (a failure); `Cronwatch.fail/2` is `finish(handle, {:error, reason})`.
28. **`Cronwatch.Store.Ecto` runs its statements through `repo.query/3`**, not `Ecto.Adapters.SQL.query/4`, since only the repo's own function honours a dynamic repo (`dynamic_repo:`), which the Node compatibility and multi-instance tests use for one repo per file or instance.
29. **Zone names** are matched without regard to case against the Zone and Link lines of tz's own copy of the IANA files, read when the package compiles (tz's `:data_dir` and `:iana_version`); a name is confirmed through `Tz.PeriodsProvider`, which tz marks internal, and offsets come from the public `Tz.TimeZoneDatabase`. A tz release that moves its files is caught by the tests.
30. **Credo and Dialyzer.** Credo runs `--strict` with its complexity and nesting checks off, since the croner port, the regular expression engine, the JSON reader, and the client follow their originals line for line; Dialyzer runs with its default warnings.

Phase 2 settled these:

31. **The transport's reach.** `transport:` on the instance reaches every channel through `ChannelContext.transport` and triage through its context's `:transport`; a channel's or triage's own `transport:` wins. The transport is `{module, opts}`, checked when the instance starts.
32. **One `:httpc` profile for the package**, `:cronwatch`, started on first use under `:inets` and set to keep no connections, in place of one per instance. Replaced in the audit (see 33): the transport of the package's own needs no profile and `:inets` is no longer started. Its own 30 second timeout is a backstop; the deadline is `Post`'s, which runs the transport and reads the body in one spawned, monitored process and kills it at the deadline, so nothing is left in the caller's mailbox. Tests shorten the deadline through the application environment's `:post_timeout`.
33. **The default transport is `Cronwatch.Transport.HTTP`**, a small HTTP/1.1 client over `:gen_tcp` and `:ssl` for the one POST, in place of `:httpc`, decided in the audit. Phase 2 left `:httpc` with the limits it has for an answer other than 200 or 206, thought to be 8 MiB; the audit found the bound was not real: `:httpc` streams only 200 and 206, so a close-delimited answer of another status was read whole with no bound at all (a 400 MiB answer from a 500 took 578 MB, and ten seconds of a fast network is far more than 8 MiB), a chunked one past 8 MiB failed with `:httpc`'s raw tuple, and a non-200 still arriving at the deadline failed as timed out where fetch gives the status. The client is some 400 lines: one request per connection (`host`, the headers given, `content-length`, `connection: close`; framing headers an app gives are the transport's own), a head of at most 64 KiB and 256 lines (up to eight interim 1xx passed over), then the body handed to `Post` as it arrives whatever the status and framing, so every answer is read to 1 MiB at most. It connects to the host `Alerts.URL` read (IPv4 addresses first), so no second URL parser can disagree about where a request goes, and verifies TLS as before. `Transport.Httpc` was removed rather than kept beside it, since nothing had been published; an app that wants `:httpc`, Req, or Finch writes a transport.
34. **Channel and triage options are checked at start**, refusals naming the module and the option (`Cronwatch.Alerts.Slack needs :webhook_url`, `Cronwatch.Triage.Anthropic needs :api_key (or ANTHROPIC_API_KEY)`), and unknown options are refused by name. Options that are not a keyword list are refused without being quoted, since they hold credentials. `Cronwatch.Triage` gains an optional `init/1` for this; the key and base URL are still read from the environment each time triage runs, and triage's timeout is the smaller of 24 seconds and one second under the client's triage wait.
35. **Twilio texts each number in a linked task**, so the channel's task stopped at its deadline takes them with it, and a raise or exit in one number's send is that number's failure.
36. **The pg_cron source keeps its cursors in the instance's ETS table**, keyed by the source's options, since sources have no `init`: it ends with the instance, a new instance finds its place again from the store, and it relies on the checker running one check at a time. Its options are therefore checked at each sync, a bad one reported on every check as `source pg_cron`, until sources get an optional `init/1` (a change to `config.ex` left for when the branches settle). A job is declared again when its options changed, compared as the option lists themselves (as the SDK's `keyOf`), and `query:` takes a function in place of a repo, the SDK's `Queryable`, which the fake tests use.
37. **The server tests** read `CRONWATCH_TEST_PG`, `CRONWATCH_TEST_MYSQL`, `CRONWATCH_TEST_MARIADB`, and `CRONWATCH_TEST_PGCRON` as URLs, start an unnamed repo per test over the server, and use tables of a prefix of their own, dropped at the end, so they run at once. Postgrex and MyXQL are test dependencies; MyXQL asks for found rows, and the MySQL readbacks are kept for a server or proxy that does not honour it.

Phase 3 settled these:

38. **The dashboard is framework-free inside.** `Cronwatch.Web.Routes` answers a `Cronwatch.Web.Request` (the method, the path and query as sent, the headers, whether it came over TLS, where a router mounted it, and a body read only when a route wants it) with `{status, headers, body}`, as the Rust port's `Routes::handle` does; `Cronwatch.Web` is the Plug in front of it, so all three replays run the same code. `Cronwatch.Web` and `Cronwatch.Handler` compile only when Plug is loaded; the rest of `web/` compiles without it.
39. **The development token lives in the instance's ETS table**, keyed by the mount's options and written with `insert_new`, rather than in `:persistent_term`: two first requests at once agree on one token, nothing global is written, and it goes with the instance. `Cronwatch.Web.token/1` makes it when it is asked for before the first request; the announcement still waits for the first request, whose origin it may show.
40. **A body Phoenix already read** is taken from `body_params` when the plug's own read comes back empty, and its `Content-Length` is not held to the 1 MiB cap (the endpoint's parsers read it under their own limit). The conn a read leaves is kept for the answer, so the adapter's view of the body stays true.
41. **The handler's run** is the job the instance declares under `job:`, or one declared with no options on the first request; its function is an MFA given the context and the `conn` first. The run it answers with comes from `Cronwatch.Run.Exec` through an internal `recorded:` option. A returned `conn` is the answer: sent, it is passed through; with a response set, it is sent; with none, the run's JSON is sent on it.
42. **Server headers in the replay.** What Bandit adds to every answer (`date`, `vary: accept-encoding` from its response compression, `connection: close` when asked) is left out of the byte comparison, as the Rust replay leaves out hyper's `Date`; the plug itself sets exactly the SDK's headers.
43. **Phoenix and Bandit are test-only dependencies**, Plug an optional one (`~> 1.16`); the formatter knows Plug's and Phoenix's router macros. A run failed by an HTTP answer now names Plug's reason phrase in the tests, where Plug is loaded, and the phase 1 test that expected none says which it expects.

Phase 4 settled these:

44. **Oban's floor is 2.20** (`~> 2.20`): the oldest release whose Cron plugin writes both the expression and the zone into a job's `meta` (`cron_expr` since 2.18, `cron_tz` since 2.20), the rule the design set, though the integration reads only `meta["cron"]` and the crontab and passes its tests on 2.19.0 too. The owner may lower it to 2.18 (the first release with the flag) if a user asks.
45. **Integrations are `integrations:` on the instance**, `{module, opts}` each, refused at start when the module is not compiled (its scheduler not a dependency), started last under the instance and given its name as `instance:`. Each keeps its telemetry handlers under an id of the instance and scheduler, detached when it stops.
46. **A run seen through telemetry is `Exec.open/2` and `close/2`**, `run/3` in two halves, not a handle, so the monitor, `current/0`, and Logger metadata are the same as for any run; the two are paired through a stack in the process dictionary with a placeholder for a start not watched or failed. `discard_when:` asks its predicate about a returned `{:error, reason}` (or `:error`) and a raised exception, never a throw or an exit, as the Go port's `DiscardWhen` asks about a returned error and never a panic.
47. **Oban's reading** is `Oban.Cron.Expression.now?/2` over each minute of UTC in the entry's zone, the plugin's own test, with the walk stepping over whole days and hours only where the zone's offset holds; `Oban.Cron.Expression` is marked internal by Oban, so a change to it is caught by the tests on the newest release. Quantum's reading is the `crontab` package's `get_next_run_date/2` and `get_previous_run_date/2` with Quantum's own rule for a time that does not exist or happens twice (skipped, a minute on), emulated over tz rather than through the app's time zone database, which a library does not set.
48. **The Oban check worker takes its instance from its args** (`instance: "MyApp.Cronwatch"`), found only among running instances and never made into an atom; Oban's own name is the job's `conf.name`. Quantum's check is a function, `Cronwatch.Quantum.check/1`, given to the scheduler as a task, since Quantum has no worker modules; a job whose task it is is never declared, whatever its name.
49. **A Quantum job without a name** is named `Module.function` after its task, without the arity the draft wrote (`MyApp.Reports.nightly/0`), since a job name cannot hold a `/`; two such jobs on one function with different arguments are one job, as two entries of one name are.
50. **The oldest dependencies are pinned by environment variables** read in `mix.exs` (`CRONWATCH_PIN_OBAN`, `CRONWATCH_PIN_QUANTUM`), which change nothing when unset and so nothing in the published package, since Mix resolves only the newest release a requirement allows.
51. **The readings report runs in `mix test`**, forty expressions and a line of output, a few seconds; it asserts nothing about the counts, so a change in either parser's reading shows in the log rather than failing the build.

The audit settled these:

52. **The default transport is the package's own** (see 33), and `:inets` is no longer one of the package's applications.
53. **The step budget is 10 million** (see 14), a fifth of the Rust port's, since a step costs the BEAM some twenty times more.
54. **Oban run ids carry the app** (`oban:<app>:<job id>:<attempt>`, the jobs table's prefix before the job id when it is not `public`), since a job's id is unique only within its table and one store may serve several apps.
55. **`Release.check/2` on a node where the instance runs** checks that instance and never starts, stops, or halts anything, so an `rpc` into a live node is safe.
56. **The API is what the README and the docs name** (from 0.11; before it, what HexDocs showed, with `Cronwatch.Cron.Date` and the SQL dialects left out by `filter_modules` in `mix.exs`, which missed `Store.SQL` for its spelling). Everything else is `@moduledoc false` or `@doc false`, its explanation kept as comments: the modules `Cronwatch.JS`, `JS.Units`, `JSRE`, `JSRE.Match`, `Cron`, `Cron.Date`, `Cron.Pattern`, `Zone`, `Duration`, `Schedule`, `Output`, `Serialize`, `Alerts.Post`, `Store.SQL`, and `StoreCase.Shared`; and the helpers `Alerts.Email`'s `compose/2`, `escape_html/1`, `options/2`, and `parse_address/1`, `Alerts.Twilio`'s `max_segments/0`, `sms_body/3`, and `sms_segments/1`, `Alerts.Discord.embed_description/1`, `Sources.PgCron`'s `hold_ms/0`, `schedule/1`, `job_name/1`, and `run_of/4`, `Transport.check/2` and `resolve/2`, `Triage.Anthropic.default_model/0` and `system/0`, `JS.Object.array_index/1`, `JobState.sending/2`, and `Metrics.lenient/1`. They keep working; none was in the README or the docs. Those that HexDocs showed before 0.11 and no other module calls (`escape_html/1`, `max_segments/0`, `sms_body/3`, `sms_segments/1`, `embed_description/1`, `Alerts.Webhook.body/1`, `hold_ms/0`, `schedule/1`, `job_name/1`, `run_of/4`, `default_model/0`, and `system/0`) are also `@deprecated`, delegating to internal functions under other names (`html_escape/1`, `body_of/3`, `segments_of/1`, `description_of/1`, `payload/1`, `schedule_of/1`, `default_name/1`, `to_run/4`) or to the module attribute, and go in 1.0, since they were public by accident (the 1.0 plan, D11); the rest are called across the package, so they stay public, hidden. `JS.Object` stays documented, since a definition and a run's metrics are one, and it now holds the JSON `value()` type. `Cronwatch.Bridge`, `Bridge.Watch`, and `Bridge.Entry` stay documented as for integration authors, outside the 1.x promise. `Cronwatch.StoreCase` promises only `use Cronwatch.StoreCase`; its `contract/1`, `replay_fixture/2`, `make/1`, `scenarios/0`, `new_run/4`, and `canonical/1` are `@deprecated`, delegating to internal functions the template calls, and go in 1.0, as test-kit internals public by accident. `Oban.Cron.Expression` (see 47) and `Tz.PeriodsProvider` (see 29) are internal to their packages, so an Oban or tz release may need a patch release; the docs say so.
57. **Plug's floor stays `~> 1.16`** though Plug before 1.16.6 has advisories, since the package calls none of the affected functions and an app's Plug is its own lock's; `elixir-oldest` tests 1.16.0.
