# The .NET port

`packages/dotnet` is to be a .NET solution whose main package is `Cronwatch` on NuGet: the same library as `@cronwatch/sdk`, for services on .NET, from a console program a crontab runs to an ASP.NET Core app with Hangfire or Quartz.NET inside it. It is a port, not a new design, made the way the Ruby gem and the Python, PHP, Go, Rust, Elixir, and Java ports were (see their `DESIGN.md`), and like the last six it is made in phases. The Java port is the nearest model: C# and Java are both typed, garbage collected, and threaded, both hold strings as UTF-16 as JavaScript does, and much of what the Java port carried over from Go and Rust (the croner port, the JavaScript regular expression engine, the JSON writer and reader, the store dialects, the WHATWG URL and origin readers, the POST hardening, the bridge) is carried over again nearly line for line from `packages/java`. The Elixir and Java ports are the models for a draft written against every audit that came before it. The TypeScript SDK is the source of truth for every behaviour, message, and stored byte; when the two disagree, the .NET side is wrong.

Phases 1 to 5 are done (see Phases). The owner took every recommendation of the draft's open questions before phase 1, and the Decisions at the end record them with what phases 1 to 5 settled besides. Where this file says something was checked, it was checked on 2026-09-30, and where it names .NET's own behaviour it was run on the .NET 10 SDK (10.0.12) in its Linux container unless it says otherwise.

## Rules

- .NET 10 or newer: every package targets `net10.0` alone, tested on .NET 10 and on the newest release (.NET 11, released in November 2026; its RC1 is out) in CI. .NET 10 is the current long-term release, supported to 2028-11-14. .NET 8, the previous one, and .NET 9 both leave support on 2026-11-10, some six weeks from now and before any phase of this port can ship, so a library first published after that has no reason to target a runtime Microsoft no longer patches (see Decisions, 2). The floor also gives the port what it would otherwise build or take a package for: `System.Threading.Lock` (9), `Base64Url` (9, the development token), `TimeProvider` with its timers and `CancellationTokenSource(TimeSpan, TimeProvider)` (8, the fake clocks), `UriCreationOptions.DangerousDisablePathAndQueryCanonicalization` (6, the POST), `TimeZoneInfo.TryConvertWindowsIdToIanaId` (6, Hangfire's and Quartz's Windows zones), `DbDataSource` and `DbProviderFactory.CreateDataSource` (7, the stores), and C# 14, the language version .NET 10's SDK defaults to. Quartz.NET 4, the current line of the one scheduler here with a net10-only release, targets `net10.0` alone too.
- One solution, `packages/dotnet/Cronwatch.slnx` (the XML solution format the .NET 10 SDK makes by default), several projects, one package each (see Package IDs and releases). The core, `Cronwatch`, has no package dependencies at all: everything it uses is in the shared framework every .NET app has (`System.Data.Common` for the stores, `System.Net.Http` for the channels, `System.Security.Cryptography` for SHA-256, HMAC, MD5, `RandomNumberGenerator`, and `CryptographicOperations.FixedTimeEquals`, `System.Diagnostics` for tracing and metrics). A test holds the core's `.nuspec` to no `<dependency>`, the counterpart of the Go core's empty `go.mod` and the Java Enforcer rule. Cron parsing and fire times are a port of croner 10 (`Cronwatch.Internal.Cron`, carried over from the Java port's `internal/cron`, itself Rust's and Go's), zones come from `TimeZoneInfo` (see Zones), JSON is written and read by `Cronwatch.Internal.Js` (not `System.Text.Json`; see below), and secret redaction runs on `Cronwatch.Internal.Jsre`, the Go, Rust, and Java ports' small backtracking engine with JavaScript's semantics (see Redaction).
- `<Nullable>enable</Nullable>`, `<ImplicitUsings>disable</ImplicitUsings>`, `<IsAotCompatible>true</IsAotCompatible>` on the core, `Cronwatch.Hosting`, and `Cronwatch.AspNetCore` (which turns on the trimming, single-file, and AOT analyzers and marks the assembly trimmable), `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`, deterministic builds, SourceLink (built into the SDK) with embedded portable PDBs and no separate symbols package (see Decisions, 25), and `<IncludeSourceRevisionInInformationalVersion>false</IncludeSourceRevisionInInformationalVersion>`, so the version the library reports is the release's and not `0.9.0+<commit>`. The core uses no reflection, no `System.Text.Json` reflection serializer, no `dynamic`, and no runtime code generation, so an app published with Native AOT or trimmed carries it without warnings, which a CI step holds by publishing `examples/aot` with Native AOT and warnings as errors (see Testing and CI). `Cronwatch.Hangfire` is not AOT compatible, since Hangfire itself is not (it serializes jobs with Newtonsoft.Json by reflection), and says so; `Cronwatch.Quartz` is marked only if Quartz.NET 4 is.
- The root namespace is `Cronwatch`, and the client is `CronwatchClient`: .NET's design guidelines and the analyzers (CA1724) refuse a type named as its namespace, which would make every app write `Cronwatch.Cronwatch` or an alias. `Cronwatch.Internal.*` is `internal`; nothing in it is reachable from an app, so the croner port, the engine, and the JSON reader can change in any release. Shipped assemblies carry no `InternalsVisibleTo` but to the tests; what the integrations need from the core is public (see Scheduler integrations), as the Java port's bridge is.
- Times are `long` epoch milliseconds everywhere, as in the SDK and the other ports, so `evaluate` ports line for line and stored rows are identical. Durations are `double` milliseconds inside (a definition may hold `1.5`, which the SDK keeps), and the public API takes the SDK's text, a `TimeSpan`, or plain milliseconds through one small struct (see The .NET API). A run's written duration is `RunDuration(startedAt, finishedAt)`, the SDK's: the difference taken without overflow, 0 when the start is later, and at most 2^53 - 1. A state's version counts as `stateVersion` reads it: a JSON number that is a whole number from 0 to 2^53 - 1 (so `2.0` is 2), else 0, in the client, the memory store, and the SQL of every dialect.
- Anything that leaves the process (store rows, JSON columns, alert JSON) uses the SDK's exact field names, key order, and values, so a Node, Ruby, Python, PHP, Go, Rust, Elixir, Java, and .NET process can share one database and `@cronwatch/mcp` works against any of them. `Js.Stringify` is `JSON.stringify` byte for byte: numbers as JavaScript prints them (`2` not `2.0`, `1e-7`, `1e+21`, `123456789012345680000`; the shortest round-trip digits come from `double.ToString("R", CultureInfo.InvariantCulture)` and are laid out as `Number.prototype.toString` lays them out, since .NET writes `1E+21` and `1E-07`), `-0` written `0`, a `long` beyond 2^53 written as the double JavaScript would hold, a value that is not finite written `null`, keys in JavaScript's order (array-index keys first in ascending order, then the rest as inserted; `JsObject` keeps that order), only control characters, quotes, and backslashes escaped, a lone surrogate written `\ud83d`. `System.Text.Json` was run against each of these and left out of everything that leaves the process: it writes `1E+21`, `1E-07`, and `1.2345678901234568E+20`, writes `-0`, throws on `NaN`, escapes `<`, `>`, `&`, `'`, `+`, and everything outside ASCII by default, writes a lone surrogate as `�`, keeps a `JsonObject`'s keys in insertion order without putting array-index keys first, and reads `{"a":1,"a":2}` into a node that writes both keys back where JavaScript keeps the last. Its reader could serve the parse, but the JSON reader must refuse nesting past 256 and keep key order and duplicates as JavaScript does, which is some two hundred lines of the Java port's own. Each public record has `ToJson()` for an app returning a `JobSummary` from its own endpoint; the stores and channels never touch `System.Text.Json`, and nothing is registered with the app's serializer options.
- .NET strings are UTF-16, as JavaScript's are, so `string.Length`, `Substring`, and the indexer count and cut exactly as the SDK does, a lone surrogate can be held, and `string.CompareOrdinal` is JavaScript's default sort. The way out agrees too: `Encoding.UTF8` writes a lone surrogate as U+FFFD (checked: `EF BF BD`), as a JavaScript string written as UTF-8 does, so no encoder of the port's own is needed where Java needed one; Npgsql encodes strictly and throws instead, so every string bound to a store goes through `Js.WellFormed` first (see Storage). What differs is whitespace: `string.Trim()` trims U+0085 and leaves U+FEFF (checked), where JavaScript's `trim` does the opposite, so trims go through `Js.Trim`.
- Culture never changes a byte. `double.ToString()`, `string.Compare`, `ToLower()`, and `StartsWith(string)` read the thread's culture in .NET (a `de-DE` app writes `1,5`, a `tr-TR` one lowercases `I` to a dotless `ı`), so every format and comparison names `CultureInfo.InvariantCulture` or `StringComparison.Ordinal`, the analyzers that catch the rest (CA1304, CA1305, CA1307, CA1309, CA1310, CA1311) are errors, and the whole suite runs a second time under `tr-TR` (see Testing and CI).
- A definition keeps its fields in the order they were given. The SDK writes `{ ...defaults, ...options, name }` with `expect` moved last, so the stored JSON follows the object literal an app wrote. C#'s object initializer calls setters in the order they are written, so `JobOptions` is a class whose `init` accessors append the key to an ordered list the first time each is set (a key set twice keeps its first place and its last value, as a JavaScript object does), and `new JobOptions { Schedule = "0 2 * * *", Grace = "15m" }` stores `schedule` before `grace` with no builder. `Budget` is an ordered collection whose `Add` appends, so a collection initializer (`Budget = { ["cost"] = 2 }`) keeps its order too; a `Dictionary` handed in whole is written in its enumeration order, which .NET does not promise. Fields a newer writer added are kept.
- Alert titles and messages are the SDK's text, character for character, with numbers as `toLocaleString("en-US")` writes them (the Go port's `format.go`, through Rust and Java): ICU's rounding, from the shortest decimal digits of the double, half away from zero. .NET's `"N"` format rounds from the binary value and is not used.
- Every condition opens once and closes with a recovery. No repeat alerts. A job whose schedule is removed while missed is open has missed closed by the next check with a recovery of its own (`reason: "unscheduled"`).
- A job's function may throw any exception, and each is a failed run: `OperationCanceledException` included, since a JavaScript function that rejects with an `AbortError` fails its run. After the recording the exception is thrown again as it came, its type and stack intact (`ExceptionDispatchInfo.Capture(e).Throw()`), so no run is left `running` to be reported stuck later. A function that returns a faulted or cancelled task, and one that throws before it returns a task at all, are the same. The store failing never stops a job: store errors go to the error handler, and the job's own outcome is returned.
- An exception is written `Name: message` and up to five frames, innermost first, each `    at Example.Reports.Build (Reports.cs:42)`, as a JavaScript stack reads. The name is the type's simple name (`IOException`, `NpgsqlException`, `HttpRequestException`), as JavaScript's `error.name` is short; a generic type's is written without its arity (`MyError`, not ``MyError`1``). Frames come from `new StackTrace(exception, true)`, with the compiler's async state machines written as the methods a person wrote (`<BuildAsync>d__4.MoveNext` is `Example.Reports.BuildAsync`) and the runtime's own plumbing (`ExceptionDispatchInfo`, `AsyncMethodBuilderCore`, `TaskAwaiter`) left out, as .NET's own `Exception.ToString()` leaves it out since .NET Core 2.1. A frame without a file (no PDB, or an app published with Native AOT, which keeps method names but no lines) is written without its parentheses. An `AggregateException` holding one exception is written as that exception, as `await` hands it over. The message is `Message`; inner exceptions are not written, since the SDK writes only the error's own stack.
- The environment is read in one place, `Env`: `CRONWATCH_ENV`, else `APP_ENV`, else the environment the app gave (`CronwatchOptions.Environment`), else `ASPNETCORE_ENVIRONMENT`, else `DOTNET_ENVIRONMENT`, trimmed and lowercased (the SDK reads `NODE_ENV`; the last two are .NET's own, which every Generic Host and ASP.NET Core app already sets, as the Elixir port reads `MIX_ENV`, read in ASP.NET Core's order); `development`, `dev`, and `local` are development and `prod` is production, as in every port, so ASP.NET Core's `Development` counts and its `Staging` does not. `test` and `testing` are not development: a test run or CI needs `CRON_SECRET` or a token, as production does. In `Cronwatch.Hosting`, the environment given is `Cronwatch:Environment`, else the host's `IHostEnvironment.EnvironmentName`, which has already read .NET's variables and `--environment`, so a stale `ASPNETCORE_ENVIRONMENT=Development` never outranks a host run with `--environment Production` (see Decisions, 10 and 45). An unset environment is not development: the Generic Host itself calls that `Production`. The other reads are the SDK's own: `CRON_SECRET`, `CRONWATCH_TOKEN`, and triage's `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL`. All are read when used.
- Thread safe throughout, and async first: the client, a job, a run handle, a job context, and every store may be used from any number of threads and tasks at once. Every call that reaches the store or the network is `async` and returns `Task` or `Task<T>` (see The .NET API), takes a `CancellationToken` last, and awaits with `ConfigureAwait(false)` (CA2007 is an error in the library's projects), so no call captures an app's `SynchronizationContext` and a WinForms, WPF, or classic ASP.NET caller that blocks on one cannot deadlock it. No lock is held across an `await`: a job's state is serialised by an async FIFO queue of the port's own (`SemaphoreSlim` does not promise FIFO, and the SDK's `serial()` is FIFO), and short sections under `System.Threading.Lock`.
- Nothing prints a secret. A C# record's generated `ToString` prints every public property, and so does a debugger's view and a structured logger that destructures an object (Serilog's `{@Options}`, a JSON dump of configuration). So nothing that holds a token, a secret, a webhook URL, or an API key (each channel's options, triage's, the dashboard's and the handler's, the client's options, a web request's headers, cookie, and query) is a record: each is a sealed class whose `ToString` and `[DebuggerDisplay]` name what is set, never its value, and whose secret properties have an `init` accessor and an `internal get`, so a logger that walks public getters finds nothing to print. A test walks every public type of every package with reflection and holds it to that. This is the Rust audit's `Debug` rule, the Elixir audit's `Inspect` rule, and the Java port's `toString` rule, and in C# it must be written from the start, since the default is the leak.
- No em or en dashes anywhere, as in the rest of the repo.

## Package IDs and releases

The packages, all released together at the release's version, each targeting `net10.0`:

- `Cronwatch`, the core: the client, runs and handles, check, the memory store and the SQL store over ADO.NET (`System.Data.Common`, part of the shared framework), the pg_cron source, the alert channels, triage, the dashboard and a job's handler, framework-free, the bridge the integrations share, the command-line entry, and the store contract for a store of the app's own. No package dependencies.
- `Cronwatch.Hosting`: the client in the container (`services.AddCronwatch(...)`, and `AddCronwatchJob`, both in the namespace `Microsoft.Extensions.DependencyInjection`, and `RunCronwatchCommandAsync` in `Microsoft.Extensions.Hosting`, as Microsoft's own registration methods are, so they need no `using`; `CronwatchHostOptions` and `ICronwatchJob` in `Cronwatch.Hosting`), options from `IConfiguration`, the check as a hosted service, the error handler and log scopes through `ILogger`, the host's environment, `AddCronwatchJob` for jobs on a schedule inside the host (see Hosted jobs), and `cronwatch check` from the app's own command line. It depends on `Microsoft.Extensions.Hosting.Abstractions`, `Microsoft.Extensions.Options.ConfigurationExtensions`, and `Microsoft.Extensions.Logging.Abstractions` at their 10.0 releases, which every Generic Host app already has.
- `Cronwatch.AspNetCore`: the dashboard and a job's handler on ASP.NET Core (`app.MapCronwatch()`, `app.UseCronwatch()`, `app.MapCronwatchHandler()`, in the namespace `Microsoft.AspNetCore.Builder` as `MapHealthChecks` is), through a `FrameworkReference` to `Microsoft.AspNetCore.App` rather than a package, as every ASP.NET Core library does. It depends on `Cronwatch.Hosting`.
- `Cronwatch.Hangfire`: the Hangfire 1.8 integration (see Hangfire).
- `Cronwatch.Quartz`: the Quartz.NET 4 integration (see Quartz.NET).

The names are free on nuget.org: the registration API (`https://api.nuget.org/v3/registration5-semver1/<id>/index.json`) answers 404 for `cronwatch`, `cronwatch.hosting`, `cronwatch.aspnetcore`, `cronwatch.hangfire`, `cronwatch.quartz`, `cronwatch.sdk`, `cronwatch.core`, `cronwatch.coravel`, and `cronwatch.extensions.hosting`, where it answers every package this file names as a dependency, and a search for `cronwatch` finds no package at all. NuGet IDs are compared without regard to case, so `Cronwatch` and `CronWatch` are one ID and cannot both exist; the casing the first push uses is the one nuget.org shows. The IDs take `Cronwatch`, not the product's `CronWatch`, so the package, its namespace, and every other port's name for the library agree (the PHP namespace `Cronwatch\`, the Elixir modules, the Java group `dev.cronwatch`, the Ruby, Rust, and Python imports); see Decisions, 1. The integration packages follow the convention of the ecosystem's own (`Serilog.AspNetCore`, `Npgsql.EntityFrameworkCore.PostgreSQL`, `Hangfire.PostgreSql`): the library's name first, then what it plugs into. `Cronwatch.Hosting` is not `Cronwatch.Extensions.Hosting`, since `*.Extensions.*` reads as Microsoft's naming and adds nothing.

nuget.org has no rule against a placeholder package, but a placeholder is a public, immutable package every search then shows, so nothing is published to hold the names. They are protected instead by an ID prefix reservation, which the owner asks for as soon as the owner decides to make this port: it makes nuget.org refuse any push of a matching ID from another account, and shows a verified mark beside the owner's packages on nuget.org and in Visual Studio. The owner emails `account@nuget.org` from the nuget.org account (its profile name, not only its email address), asking for the prefixes `Cronwatch` and `Cronwatch.*`, private (a public prefix only marks packages; it blocks no one), with the evidence the reviewers ask about: that the prefix names the owner's project (cronwatch.dev, the GitHub repository, the library on npm, RubyGems, PyPI, crates.io, Hex, and Maven Central under the same name) and that it is not a common word. They reply with an acceptance or with the criterion that failed, and may ask identifying questions first; the documentation promises no time. A reservation leaves packages already pushed under the prefix by others alone, which is why it should come before any other `Cronwatch.*` appears. The prefix rules also ask that packages under it carry a license expression (`<PackageLicenseExpression>MIT</PackageLicenseExpression>`, the repository's license) and an embedded icon rather than an icon URL, which the packages do anyway. If the reservation is refused, or `Cronwatch` is taken before either happens, the fallback is `Cronwatch.Sdk` for the core, the PyPI package's name, with the other packages under it (`Cronwatch.Sdk.AspNetCore`), the namespace staying `Cronwatch` as the Python package is imported as `cronwatch`.

The version lives in one place, `<Version>` in `packages/dotnet/Directory.Build.props`, which every project inherits; `CronwatchClient.Version` reads it from the assembly's `AssemblyInformationalVersionAttribute`, so it needs no row of its own, and triage's user agent is `cronwatch-dotnet/<version>`. The packages depend on each other at the release's version (`Cronwatch.AspNetCore` 0.9.0 needs `Cronwatch.Hosting` 0.9.0 or newer, NuGet's ordinary minimum), and are published together, so an app that takes one integration gets a core of the same release. Central package management (`Directory.Packages.props`) pins every dependency and test dependency in one file, and `global.json` pins the SDK's feature band (`10.0.100`, rolling forward to the newest patch and feature band), so CI and a contributor build with the same compiler.

`scripts/release.mjs` gets its two rows in phase 1, with the solution (the script refuses to run while a directory under `packages/` lacks them, so until then this file alone holds up a release, as the Rust, Elixir, and Java designs did before their phase 1): in VERSIONED, `{ file: "packages/dotnet/Directory.Build.props", pattern: /^(\s*<Version>)([^<]+)(<\/Version>)/m }`, and the README's install line (`dotnet add package Cronwatch --version X`); in PUBLISH, the line that says the pushed tag publishes the packages through `nuget.yml`, and the command to do it by hand. NuGet reads a package from the `.nupkg` pushed to it, not from a repository, so a solution in a subdirectory of a monorepo needs no split repository (the PHP package's case) and no tag prefix (the Go module's); the release's own tag `vX.Y.Z` is the only tag, and each package's `<RepositoryUrl>`, `<RepositoryCommit>` (SourceLink fills it), and `<PackageProjectUrl>` name the repository, the commit, and cronwatch.dev. A published version cannot be deleted or replaced, only unlisted or marked deprecated, which is one more reason nothing is published before phase 1 works. See Releasing.

## The .NET API

```csharp
await using var cw = new CronwatchClient(new CronwatchOptions
{
    Store = SqlStore.Postgres(dataSource),                          // default: a MemoryStore
    Alerts = { SlackChannel.Webhook(Environment.GetEnvironmentVariable("SLACK_WEBHOOK_URL")!) }, // default: the console
    Retention = "30d",
});

Job nightly = cw.Job("nightly-report", new JobOptions
{
    Schedule = "0 2 * * *", Timezone = "UTC",
    Grace = "15m", Timeout = TimeSpan.FromMinutes(30),
    Expect = "Report written", Budget = { ["cost"] = 2 },
    FailuresBeforeAlert = 1,
});

string path = await nightly.RunAsync(async (job, ct) =>
{
    string p = await reports.BuildAsync(ct);    // ct is cancelled at the job's timeout
    job.Log($"Report written: {p}");
    job.Metric("cost", 1.2);
    return p;                                   // an IOException thrown here is thrown from RunAsync
}, cancellationToken);

CheckResult result = await cw.CheckAsync(); // missed and stuck runs, retries, pruning
cw.Start(TimeSpan.FromMinutes(1));          // a check every minute, for a long-running process
await cw.SilenceAsync("nightly-report", "2h");
```

In a Generic Host or ASP.NET Core app the same client is a singleton from `builder.Services.AddCronwatch(o => ...)`, which also checks every minute as a hosted service, and the dashboard is `app.MapCronwatch()` (see Hosting and Dashboard). The shape follows .NET's conventions while keeping the SDK's names recognisable: `cronwatch({...})` is `new CronwatchClient(options)`, `cw.job(name, options)` is `cw.Job(name, options)`, `job.run(fn)` is `job.RunAsync(fn)`, and `recordRun`, `resumeRun`, `jobsWithRuns`, and `jobSummary` are `RecordRunAsync`, `ResumeRunAsync`, `JobsWithRunsAsync`, and `JobSummaryAsync`, with .NET's `Async` suffix on everything that returns a task. There is one API and it is async, since every host .NET runs a scheduled job in (a console `Main`, a `BackgroundService`, a Hangfire or Quartz job, a request) can await; a caller that cannot writes `.GetAwaiter().GetResult()`, which the library's own `ConfigureAwait(false)` makes safe (see Decisions, 7).

- *Options are classes with `init` properties*, checked when the client or job is made: a bad option, schedule, or zone is a `CronwatchException` from the constructor or `Job()` with the SDK's message, never from the first run. The SDK's three-way options are nullable properties with an explicit opt-out: `CronSecret = "..."`, `CronSecret = CronSecret.None`, or neither (reading `CRON_SECRET`), where the SDK has a string, `null`, and absent; `Redact = text => ...` or `Redact = Redaction.None` where it has a function and `false`; `Deliver = Deliver.AtCheck`. `Defaults` takes a `JobOptions` of `Grace`, `Timeout`, `Timezone`, and `FailuresBeforeAlert` and refuses others. `Clock` takes a `TimeProvider` (by default `TimeProvider.System`), which is the fake clock the tests drive, where every timer the client arms comes from, and whose `LocalTimeZone` is the zone a cron without a `Timezone` is read in.
- *Durations* are `Duration`, a small readonly struct with implicit conversions from `string` (the SDK's text, `"15m"`, `"1h30m"`), `TimeSpan`, and `double` milliseconds, so a property takes all three without overloads; text is stored as written and everything else as its milliseconds, as the Go, Python, Rust, Elixir, and Java ports store theirs. Text longer than 64 characters is refused before it is read, quoting its first 32, the SDK's `duration.ts` rule, which `duration.json` holds every port to. A `TimeSpan` is whole ticks, so its milliseconds may carry a fraction, which is stored as the SDK stores `1.5`.
- *Expect* is `Expect`, with an implicit conversion from `string` (contains), `Expect.Matches(source, flags)` for a JavaScript pattern (stored as `matches /source/flags`, run by the engine), and `Expect.That(Func<string, bool>)` (stored as `custom function`; a throw in it fails the run with `Output check threw: ...`). A `System.Text.RegularExpressions.Regex` is not taken: it reads a pattern differently from JavaScript (see Redaction), and a stored pattern must read the same in every port.
- *Job functions* are `Func<JobContext, CancellationToken, Task>` and `Func<JobContext, CancellationToken, Task<T>>`, given to one overloaded `RunAsync`: C# chooses the `Task<T>` overload for an async lambda that returns a value and the `Task` one for one that does not, as it does for `Task.Run`, so the Java port's ambiguity (its Decision 22) does not arise. No `ValueTask` overloads are offered beside them, since an async lambda converts to both and C# then refuses the call as ambiguous. The token is the run's (`job.CancellationToken`), the SDK's `signal`: it is cancelled at the job's timeout and when the token given to `RunAsync` is, so a function that honours it stops at either; the function decides, as a JavaScript function decides what to do with an aborted signal. `JobContext` has `Log(string)`, `Metric(string, double)`, and the token. A `string` the function returns is the output when nothing was logged (and what `expect` checks).
- *Channels, triage, and sources are interfaces*: `IChannel` (`Name`, `SendAsync(Alert, ChannelContext, CancellationToken)`), `ITriage`, and `ISource` (`Name`, `SyncAsync(CronwatchClient, CancellationToken)`), each with a static factory for a lambda (`CustomChannel.Create("pager", (alert, ctx, ct) => PageAsync(alert, ct))`, named apart from `System.Threading.Channels.Channel`). A throw is that channel's failure only.
- *Stores* are `IStore`. The SDK's two optional methods, `updateRunIf` and `compareAndSetState`, and the Go, PHP, Rust, Elixir, and Java ports' `deleteRunIf` (which a run given back needs, below) are three capability interfaces (`IUpdateRunIfStore`, `ICompareAndSetStateStore`, `IDeleteRunIfStore`, named after their methods; see Decisions, 63) the client finds with a type test, as Go finds an optional interface, rather than default interface methods that throw, which the Java port had to catch; without them the client falls back to a read and a write, as the SDK does. `MemoryStore` and `SqlStore` implement all three. A store is `IAsyncDisposable` when it holds something.
- *Value types are records*: `Run`, `StoredJob`, `JobState`, `Alert` and its details, `JobSummary`, `CheckResult`, `Metrics`, each a `sealed record` with `init` properties, nullable where the SDK's field may be `null`, so a store of the app's own builds them from rows with `with` expressions. A state's `PendingRecovery` and `Undelivered` are `null` for a state written before the fields existed, and its `UnderFloor` is `null` while no metric is under its floor, and unknown keys a newer writer added are kept in their places and written back, in an `Extra` property holding a `JsObject`. An alert held in `undelivered` or `sending` keeps the keys of the alert, its run, its details, its budget breaches, and its `sending` entry that this release does not know, held privately as JSON and written back after its own, and the details of an alert of a type it does not know are kept whole, so a queued alert a newer release wrote is stored and retried as the SDK keeps it, as plain JSON (the cross-port check's). Lists and dictionaries in a record are immutable (`ImmutableArray`, an ordered read-only map of the port's own), and a record's value equality compares them by content. None holds a secret.
- *Wire values stay strings*: `RunStatus`, `Condition`, `AlertType`, and `JobHealth` are `readonly record struct`s around the SDK's string, with static properties for the known values (`RunStatus.Ok`, `Condition.OverBudget`) and an implicit conversion from any other string, compared by value, not C# enums: stored values come from other writers, a newer SDK adds values that must pass through unharmed, and an enum cannot hold a value it does not name, as the Java port decided (its Decision 9). A `switch` over them matches by value.
- *A run given back*: `job.RunAsync(fn, new RunOptions { DiscardWhen = e => ... })` takes a run back rather than judge it when the function throws an exception the predicate answers true for, for an attempt a scheduler gives back without failing (a Hangfire job aborted by its server's shutdown, below). It is the Go port's `DiscardWhen`, the Rust port's `run_or_discard`, the Elixir port's `discard_when:`, and the Java port's `discardWhen`, rule for rule, with their audits' fixes: the running row is deleted with `DeleteRunIfAsync`, nothing is judged or alerted, the job's state is left as it was (missed and stuck are closed only once the run is known not to be given back), the exception is still thrown, a row a check marked stuck is left as it is, a store without the capability records the run as it ended, and a predicate that throws is reported (`discarding <job>`) and the run recorded.
- *Writing a declaration now*: `cw.SyncJobAsync(name)` writes the job declared in this client to the store unless the store already holds that definition (compared as JSON, keys in any order), and says whether it wrote, as the other ports' do; the integrations use it.
- *Errors* are `CronwatchException` with a `Kind`: `Invalid` (what the SDK refuses, with its message), `Store` (the store's own exception as `InnerException`), and `Other`. A read (`JobsAsync`, `JobSummaryAsync`, `RunsAsync`) throws it when the store fails; `RunAsync`, `Start`, `FlushAsync`, and `FinishAsync` never do (see Runs).

There is no global client: an app keeps its `CronwatchClient` where it keeps its data source (a field, a DI singleton) and disposes it at shutdown. `CronwatchClient.Current` is static, since it answers for the calling flow (see Runs).

## Tasks and state

The client never blocks a job on anything but its own store writes. Every read-modify-write of a job's state goes through `UpdateStateAsync`: holding the job's queue (an async FIFO lock of the port's own, the SDK's `serial()`, dropped once no one holds or waits for it, the Java audit's fix for a lock kept per name for good), it reads the state, works out the next one, and writes it only when it changed, with `version` one higher, through `CompareAndSetStateAsync` against the version read; a refused write is worked out again from a fresh read, up to 10 times, as in every port. Only store calls happen under the queue; alerts are sent after it is released. A cluster of processes is a set of processes sharing one store, as several Node processes are, and `CompareAndSetStateAsync` keeps them honest.

The client's own work runs as tasks on the thread pool it owns no part of: the recording after a run's function returns, each channel's send, triage, the closing of missed and stuck at a run's start, the shared check, and the interval. Each is started with `Task.Run` from inside `ExecutionContext.SuppressFlow()`, so an app's `AsyncLocal` values (its log scope, its current run, an `Activity`) do not leak into work that outlives the call that started it. The client tracks what it started so `DisposeAsync` can wait for it.

`CheckAsync()` joins the check in flight or starts one, and every caller waiting gets the same answer through one `TaskCompletionSource` made with `RunContinuationsAsynchronously`. The field that holds the check in flight is cleared (with `Interlocked.CompareExchange`, only if it still holds this check) before that source is completed, never after: a continuation that runs as the check completes and calls `CheckAsync()` again must start a new check, not be handed the one that just finished, which is the race the Java port's audit found in its `CompletableFuture`, whose dependents run inside `complete`. A caller's `CancellationToken` ends its own wait (`WaitAsync(ct)`) and never cancels the check for the others or leaves a job half checked; a throw in the check (a store's) is that check's `CronwatchException` and the next call starts a new one. `Start(every)` runs the first check after a second and then on the interval (a minute by default, five seconds at least, at most the SDK's 2^31 - 1 ms), on a timer from the client's `TimeProvider`; each tick asks for a check without waiting on it, as setInterval does, so a tick while a long check runs shares that check and the ticks it outlasted are not run back to back after it; a second `Start` does nothing, and `Stop` ends it.

`DisposeAsync()` stops the interval, records the runs still open in this process as the process-exit hook does (below), waits up to five seconds for sends and recordings in flight, then cancels what is left, and removes the hook. It records before it lets go of the store, which is the Java audit's finding that a client closed while its process stops (a DI container disposing its singletons at shutdown) must write the open runs first. The client is `IDisposable` too, for a container that disposes synchronously, and then does the same on the calling thread.

## Runs

`job.RunAsync(fn)` runs the function in the caller's flow, awaited by the caller, where the app's context lives: its log scope, its `Activity`, its DI scope, the Hangfire or Quartz job it is inside. It declares the job if needed, inserts the running row (a store failure goes to the error handler and the job still runs), makes the run current, starts an `Activity` from the `Cronwatch` source (see Telemetry), calls the function inside `try`/`catch (Exception)`, and awaits it. Then:

- *What counts as failed.* Any exception, as the Rules have it, including one thrown synchronously by a function that never returned a task. Anything returned succeeds, as a JavaScript function's return does. After the recording, the exception is thrown again unchanged, so the caller's own handling (Hangfire's retry, Quartz's `JobExecutionException`, the host's `BackgroundServiceExceptionBehavior`) sees exactly what it would have without CronWatch.
- *Recording outlives the caller.* Everything after the function returns (the finish, the state, the alerts) runs as a task of the client's that `RunAsync` awaits with the caller's token: a caller whose token is cancelled while it waits stops waiting, not the recording, which completes on its own, since a store write cut part way would leave the run `running`. It is the Rust port's rule for a dropped future and the Java port's for an interrupt, which .NET meets through cancellation.
- *A process that stops inside the function.* A process can end while a run is open: a container's `SIGTERM`, `Environment.Exit`, the host stopping. In a Generic Host a `SIGTERM` becomes `IHostApplicationLifetime.ApplicationStopping`, the stopping token a `BackgroundService` or Hangfire job is given is cancelled, the job throws `OperationCanceledException`, and its run is recorded failed through the ordinary path before the host's shutdown timeout. For what that does not reach (a console program, a function that ignores its token), the client registers one handler on `AppDomain.CurrentDomain.ProcessExit` (unless `ProcessExitHook = false`) which marks each run still open in this process failed (`Shutdown: the process stopped while the run was in progress`), writing each through `UpdateRunIf` only over a row still `running`, so a function that finishes on its own wins and nothing is judged twice; it spends at most five seconds, all runs at once, and sends the alerts it can in what is left. This is the Java port's shutdown hook (its Decision 8) and the Elixir port's monitor as far as .NET allows: a `SIGKILL`, a `StackOverflowException` (which .NET cannot catch and which ends the process), `Environment.FailFast`, or a machine lost runs no handler, and that run is reported stuck at its timeout, as a killed Node process's is.
- *Timeouts.* The SDK aborts a signal at the job's timeout and lets the function decide; it never stops the function, and a function that runs on is marked stuck by a check. So does this port: the run's token is cancelled at the timeout by a `CancellationTokenSource` on the client's `TimeProvider`, and a function that honours it throws what the cancelled call throws, a failed run written as that exception (`TaskCanceledException: A task was canceled.` for an awaited `Task.Delay`, `OperationCanceledException: The operation was canceled.` for `ThrowIfCancellationRequested`), as the SDK writes the `AbortError` a JavaScript function rejects with. .NET, like the JVM and unlike the BEAM, cannot stop a running function, so there is no counterpart of the Elixir port's `kill_at_timeout`, and none is needed of the Java port's `interruptAtTimeout`, since the token is how .NET code is asked to stop (see Decisions, 8).
- *`Current`.* `CronwatchClient.Current` answers the current flow's run from an `AsyncLocal<JobContext?>`, which is .NET's `AsyncLocalStorage`: it is set inside `RunAsync`, an async method, so it flows into everything the function awaits and every task, `Parallel.ForEachAsync` body, and thread it starts (all capture the `ExecutionContext`), and it is gone when `RunAsync` returns, since an async method restores its caller's context, so no pooled thread keeps a run that has finished, the class of bug the Java audit looked for in its `ThreadLocal`. Work started with `ExecutionContext.SuppressFlow` or `UnsafeQueueUserWorkItem` has no run, as a callback registered outside `AsyncLocalStorage` has none. The one place this bites is an integration that learns of a run's start in a callback of its own: a value set in an async callback is undone when that callback returns, so it never reaches the job, and one set in a synchronous callback on a pooled thread stays there until it is cleared. Each integration below says how it makes the run current and takes it off again.
- *HTTP answers.* A function that returns an `HttpResponseMessage` whose status is 400 or more fails the run with `HTTP <status> <reason>`, the reason from the message's `ReasonPhrase`, else RFC 9110's table, as the SDK fails a run for a fetch `Response`; in `Cronwatch.AspNetCore`, so does an `IResult` that is an `IStatusCodeHttpResult` of such a status.

## Runs that span calls

`job.StartAsync(StartOptions)`, `job.ResumeAsync(runId)`, and `cw.ResumeRunAsync(name, runId)` are the SDK's `start()`, `resume()`, and `resumeRun()`, and return a `RunHandle`: `Id`, `Job`, `StartedAt`, `IsActive`, `Log`, `Metric`, `FlushAsync()`, `FinishAsync()`, `FinishAsync(result)`, and `FailAsync(exception)`, following `client.ts` and the Java port's handle rule for rule: a start with an id holds a per-client entry keyed by the job and the id while it reads the store and inserts (a second start with the same id at once waits, then finds the stored run and answers a handle on it); `FinishAsync` reads the stored run again, joins its output with the handle's (capped), and merges metrics (the handle's win); `FlushAsync` writes only over a row still running and of this job; the store never fails out of start, resume, flush, or finish (failures go to the error handler as `recording <job>`, `starting <job>`, `resuming <job>`, `flushing <job>`, or `finishing <job>`); and a store that fails during finish leaves the handle active, lines kept, so it can be called again. A run id holding a NUL is refused by `StartAsync`, `ResumeAsync`, `RunAsync`, and `RecordRunAsync`, the SDK's rule since 0.8.0. A handle is not disposable: a handle left unfinished is what the stuck check is for, and one collected while active records nothing.

A run is judged once, however many processes finish it: the finish is written only over a stored row still `running`, else over one still `timeout`, through `UpdateRunIfAsync`, one conditional `UPDATE`, and only the process whose write lands evaluates. `InsertRunAsync` refuses an id already stored. The SDK's multi-process scenarios (`finish once`) run against the memory store and against SQLite, Postgres, MySQL, and MariaDB, each process a client of its own over one database.

## Telemetry

The core writes .NET's own telemetry with nothing added, since `System.Diagnostics.ActivitySource` and `System.Diagnostics.Metrics.Meter` are in the shared framework and are what OpenTelemetry's .NET SDK, Application Insights, and `dotnet-counters` read: an app adds `.AddSource("Cronwatch")` and `.AddMeter("Cronwatch")` to its OpenTelemetry setup and sees them, and an app that listens to neither pays for an `if` per run.

- An activity `cronwatch.run` around each run's function (tags `cronwatch.job`, `cronwatch.run_id`, `cronwatch.trigger`, and the run's status when it ends), a child of whatever activity the caller had, so a job's database calls nest under it; and `cronwatch.check` around each check.
- Counters `cronwatch.runs` (by job and status), `cronwatch.alerts` (by channel, type, and outcome: sent, failed, queued, dropped), and `cronwatch.checks`, and a histogram `cronwatch.run.duration` in milliseconds.

The error handler is the SDK's `onError`: `OnError = (exception, where) => ...`, by default a line to `Console.Error` with the SDK's text (`[cronwatch] recording nightly-report: ...`); `Cronwatch.Hosting` sets it to an `ILogger<CronwatchClient>` at `Error`, so the line arrives where the app's other logs go. `ConsoleChannel`, the default channel, writes the SDK's line to `Console.Out` for a recovery and `Console.Error` for anything else, where the SDK writes `console.info` and `console.error`, since a crontab's mail and a container's log collector read those streams, as the Java port decided (its Decision 11). Lines end with `\n` on every system, as Node writes them, not `Environment.NewLine`. The in-memory store's warning and `Start()` with `Deliver.AtCheck`'s warning go to the same handler as a warning, with the SDK's text. In a host, `Cronwatch.Hosting` also opens an `ILogger` scope holding `cronwatch_job` and `cronwatch_run` around each run's function (the MDC keys of the Java port), through a hook the client offers for it, so every line the app logs inside a job carries them.

## Delivery

`Deliver.Now` (the default) sends each alert from the process that produced it; `Deliver.AtCheck` queues it in the job's state (`undelivered`, at most 20, the oldest dropped first and reported) for the next check in a process that delivers now. An alert some channel refused is queued the same way and retried once per check, oldest first, to the channels that refused it and no others: the held copy carries `owed` (`Alert.Owed`), the keys of the channels that still owe it, each a channel's name with `#2`, `#3`, and so on for later channels of the same name (`Evaluate.ChannelKeys`), and one without `owed` (never sent, or held by an older release) is owed by every channel configured now; a key no longer configured drops out, so an alert whose owing channels are all gone is done, sent to none; a channel never sees `owed`; `lastAlertAt` moves only when some channel accepted an alert on that attempt; one that no longer describes the job (`staleAlert`) is dropped; one check spends at most 20 seconds retrying across all jobs. Triage is tried once per alert.

The outbox, the SDK's: the state write that opens a condition also holds its alerts, composed, in `sending` (`SendingAlert`: the alert without triage, and `Until`, five minutes on, when the sender's lease runs out), or with `Deliver.AtCheck` straight in `undelivered`, before anything is sent; once the sends are done one write records them (`Evaluate.RecordSent`), taking them out of `sending` and queueing the failed. A check moves an entry whose lease ran out (its process stopped part way) to `undelivered`, where the retry sends it, triaged then, or drops it as stale. So a process that dies between the write and the send loses nothing, and one whose channel took the alert just before it died has it sent a second time, the one duplicate a crash can cause. Every alert held in state is a trimmed copy (`Evaluate.HeldAlert`): its run's error keeps its first 2048 UTF-16 units and its output its last 2048, its message its first 4096, each cut so as not to split a surrogate pair and marked with how many units went, and a text within 64 units of its cap is kept whole, so trimming again changes nothing; the first send uses the alert as composed, and only a retry sends the trimmed run. The pure parts (`QueueUndelivered`, `HoldAlerts`, `ReleaseSending`, `RecordSent`, `HeldRun`, `HeldAlert`, `ChannelKeys`, `OwedChannels`, `AfterSend`, `WithoutOwed`) are held by `conformance/health.json`'s `delivery` cases, and the client's sends by `conformance/client.json`'s `outbox` scenarios. The key is written only while it holds an entry, and an older port sharing the store keeps it as an unknown key or drops it, never sending what is in it.

Each channel sends as a task of its own with a token cancelled after 15 seconds, and triage after 25. Past its time the send is cancelled: the token cancels the `HttpClient` exchange, which closes its connection, and the next alert is sent to the channel as the SDK sends it. A channel of the app's own that ignores its token keeps its task until it returns, harmlessly, as the Go port's abandoned sends did; the `IChannel` documentation says so.

## Channels

`Cronwatch.Alerts` holds the SDK's channels, request for request: Slack, Discord, the webhook, Resend, Postmark, SendGrid, Mailgun, SES, Twilio, Sentry, Honeybadger, Datadog, Rollbar, Bugsnag, and New Relic, each made from an options class with the SDK's option names in PascalCase (`new ResendChannel(new ResendOptions { ApiKey = ..., From = ..., To = ... })`, with `SlackChannel.Webhook(url)` and `DiscordChannel.Webhook(url)` for the common case), and the SDK's refusal in .NET's words (`Resend needs an ApiKey`) from the constructor, never quoting a value. A boolean is given as the SDK names it, with the SDK's default when left out. The requests are the SDK's: the same URL, header names and values, and body written by `Js`, so the bytes are identical; the same stable alert id (the first 32 hex characters of SHA-256 over job, type, and time); the same error text. The webhook's extra headers are an ordered list of pairs. Twilio texts every number at once (`Task.WhenAll`) and follows the SDK's segment fitting and partial-delivery report.

Every request goes through `Post` (`Internal/Post`), a transport-free port of the Java port's `internal/post`, with the Go, Rust, Elixir, and Java audits' hardening, over an `ITransport` (one POST: a `TransportRequest` of a URL, headers in order, and a body; it answers a `TransportResponse`, a status and a body stream `Post` reads a chunk at a time, so `Post` holds every transport to the deadline and the cap). The default transport is `HttpClientTransport`, over one `HttpClient` per `CronwatchClient` on a `SocketsHttpHandler` the client makes on its first send and disposes with itself; a channel reaches it through `ChannelContext.Transport`, triage through its context. An app that wants its `IHttpClientFactory` client, a proxy, or its own trust store writes a transport (a dozen lines) and gives it on the channel or the client. The questions this port has to answer about .NET's client, and the answers phase 2 must confirm against real local servers:

- *The 1 MiB cap as the body arrives.* The request is sent with `HttpCompletionOption.ResponseHeadersRead`, so `SendAsync` returns at the answer's head and nothing of the body is buffered; `Post` reads the content stream into a buffer of its own, stops at 1 MiB whatever the status and however the answer is framed (a `content-length`, chunked, or up to the connection's close), and disposes the response. `SocketsHttpHandler` drains an unread body to reuse its connection, up to `MaxResponseDrainSize` (1 MiB by default) for `ResponseDrainTimeout`, so the handler is made with `MaxResponseDrainSize = 0`, which closes the connection instead, and nothing past the cap is ever read. `AutomaticDecompression = None` and no `accept-encoding` is sent, so a gzip answer cannot grow in memory. The answer's head is held to `MaxResponseHeadersLength` (64 KiB, the handler's default and the Elixir port's cap).
- *One deadline for the whole request*: ten seconds inside the channel's own, connecting, sending, and reading the answer. `HttpClient.Timeout` covers only `SendAsync` (and throws a `TaskCanceledException` of its own wording), so it is set to `Timeout.InfiniteTimeSpan` and the deadline is a linked `CancellationTokenSource` of `Post`'s, spanning `SendAsync` and every read of the body. `ConnectTimeout` is ten seconds too. Past the deadline before an answer is `The operation was aborted due to timeout`, fetch's message; past it while the body arrives is the answer with no body, the status kept.
- *A redirect is refused, not followed*: `AllowAutoRedirect = false`, and a 3xx is an answer outside 2xx like any other, so credential headers never go where it points.
- *TLS is always verified*: the handler's default validation, with the system's trust store and its host name check (a certificate for an IP address checked against the address; .NET sends no SNI for an address and still checks), and `SslOptions.RemoteCertificateValidationCallback` is never set; an app's own trust is its own transport.
- *No proxy*: `UseProxy = false`, since `HttpClient.DefaultProxy` reads `HTTPS_PROXY` and the system's settings where Node's fetch reads none, and a proxy the app did not name would see every credential header. `UseCookies = false`, so no cookie container carries anything between sends.
- *The URL* is read by the Java port's WHATWG reader (a space inside is encoded and posted, `javascript:` is refused as `not javascript:`, a user name is refused), not by `System.Uri`, which reads backslashes, spaces, and hosts its own way. It must be `http` or `https` with a host, and is never quoted in an error, since a webhook URL's path is its credential. The parsed URL is written out and given to `HttpClient` as a `Uri` made with `UriCreationOptions { DangerousDisablePathAndQueryCanonicalization = true }`, so the path and query are sent as written and not unescaped or re-escaped by `Uri`; the host the `Uri` reads back must be the host the reader read, or the URL is refused, so what the URL names and what is reached cannot differ. A host outside ASCII is refused as `not this URL`, since .NET's IDN mapping is the platform's (ICU's on Linux and macOS, Windows' own there) and WHATWG's is UTS 46 with rules of its own; an IPv6 host with a zone is refused, as fetch refuses it.
- *Only the URL's origin appears in any error*: every exception the transport throws is rewritten to the origin and the exception's simple name and message, with every spelling of the URL taken out and every header value of four characters or more (but `accept`, `content-type`, and `user-agent`) cut out, the Java audit's fix for a client that quotes a header it refused. `HttpRequestException`'s messages name the host and port (`Connection refused (hooks.example.com:443)`), not the path, but a transport of the app's own might quote anything.
- *Headers.* Credentials are trimmed of the spaces and newlines a paste leaves, and a header value with a CR, LF, or NUL left inside is refused before the request is made, naming the header, never its value. Headers are added with `TryAddWithoutValidation`, so their values are sent as given; `content-type` belongs to the content in .NET, and `HttpClient` writes `Host` first and `Content-Length` itself. It sends no `User-Agent` unless one is given, so the channels send none where fetch sends its own, and triage sends `cronwatch-dotnet/<version>`. Phase 2 pinned what goes on the wire with a test against a raw server: `Host` first, then the request's headers in the order given, then the content's headers, then `Content-Length`; a header name .NET knows is written in its own casing (`authorization` as `Authorization`, `content-type` as `Content-Type`) and any other as given; a `host`, `content-length`, `connection`, `expect`, `upgrade`, `transfer-encoding`, `keep-alive`, `te`, or `trailer` header a request names is dropped, as fetch drops a forbidden header; and no `Accept-Encoding`.
- *Every secret the channel holds* is cut out of a quoted answer before the answer is cut to 200 UTF-16 units on a code point.

The tests replay every case of `conformance/channels.json` (`sends` 90, `failures` 18, `providerSends` 435, `providerFailures` 116, `twilioPartial`, `textCuts`) through a recording transport, and a hardening suite runs the channels against real local servers (raw `TcpListener`s and `SslStream`s in the tests, so no server is a test dependency and one can misbehave as a test needs, with certificates made at run time by `CertificateRequest`, no key committed): a redirect refused by all fifteen, the deadline before an answer and while a body drips in, a large answer read to exactly 1 MiB in each framing with the connection closed after it, a gzip answer read as its compressed bytes, the URL and header refusals, only the origin in an error whatever a transport quotes, TLS verified for a name and for an address, the headers .NET sends and their order, a secret straddling the cut, a lone surrogate on the wire, no proxy used with `HTTPS_PROXY` set, and Twilio's partial delivery through a client. ## Storage

`MemoryStore` is `stores/memory.ts`: one lock, copies in and out, names sorted by `string.CompareOrdinal` (UTF-16 code unit order, JavaScript's default sort), the same prune rule.

`SqlStore` keeps the same three tables in the app's database through ADO.NET: `SqlStore.Sqlite(dataSource)`, `SqlStore.Postgres(dataSource)`, and `SqlStore.MySql(dataSource)` (MySQL and MariaDB), or `SqlStore.For(dataSource)`, which reads the provider from the connection's type name (`SqliteConnection`, `NpgsqlConnection`, `MySqlConnection`) without referencing any of them; `WithPrefix("cw_")` answers a store whose tables take that prefix (the SDK's rule and message). The store takes a `System.Data.Common.DbDataSource`, the provider-neutral pooled source .NET 7 added: Npgsql's `NpgsqlDataSource` and MySqlConnector's `MySqlDataSource` are ones, and any provider becomes one through `DbProviderFactory.CreateDataSource(connectionString)` (Microsoft.Data.Sqlite's `SqliteFactory.Instance.CreateDataSource(...)`), so the store shares the app's credentials and pool and no driver is a dependency of any package. ADO.NET over a store per driver because it is the one interface to all four databases, part of the shared framework, and what every .NET data library sits on; an app on EF Core or Dapper gives the store the data source underneath (see Decisions, 5). The tables are made when the client first calls `InitAsync`.

- *The schema, byte for byte.* The SQLite and Postgres `CREATE` statements are `stores/sql.ts` text for text: the same `CREATE TABLE IF NOT EXISTS` text for `jobs`, `runs` (with `seq BIGSERIAL` first on Postgres), and `state`, the same two indexes, so `sqlite_master` reads the same whoever created the tables; `INTEGER` or `BIGINT` times, `TEXT` or `JSONB` JSON, `rowid` or `seq` breaking ties, names sorted `COLLATE "C"` on Postgres; init under `pg_advisory_xact_lock(hashtext('cronwatch:<prefix>'))`, in one transaction of the store's own, so many processes can start at once. The MySQL dialect is the PHP, Go, Rust, Elixir, and Java ports' (MySQL 8.0.13 or MariaDB 10.6 or newer: `utf8mb4_bin`, JSON as `LONGTEXT` holding the SDK's bytes, never MySQL's `JSON` type, `ON DUPLICATE KEY`, the prune's newest start per job as a derived table, compare-and-set from version 0 in two steps, a landed write read back when the server counts changed rather than matched rows, `trigger` as `VARCHAR(255)`, a longer trigger cut on a code point), copied from the Java port's `internal/sql`. On every dialect the version compare-and-set reads is a `CASE` that tests the JSON type before any cast, the SDK's text.
- *Parameters.* `sql.ts` writes its statements with `?` and numbers them `$1`, `$2` for Postgres. Npgsql takes `$n` with unnamed parameters and MySqlConnector takes `?` with unnamed ones, so those dialects keep `sql.ts`'s text. Microsoft.Data.Sqlite binds by name only and refuses an unnamed `?` (checked: `ParameterName must be set`), so the SQLite statements number their parameters in SQLite's own form, `?1`, `?2`, and name each parameter to match; that is the one change to `sql.ts`'s text on SQLite, and the schema is untouched.
- *JSONB.* node-postgres sends parameters untyped and Postgres infers `jsonb`. Npgsql types a `string` parameter as `text`, which a `jsonb` column refuses, and the only way to send it untyped or as `jsonb` is `NpgsqlParameter.NpgsqlDbType`, a type from Npgsql the core cannot name. So each JSON parameter is written `$n::jsonb` in the Postgres statements, as the Elixir port writes `$n::text::jsonb` for the same reason (its Decision 7); a JSON column is read with `GetString`, which Npgsql answers with the text, and parsed with `Js` in the order Postgres gives the keys. The schema does not change.
- *Text as JavaScript writes it.* Microsoft.Data.Sqlite writes a lone surrogate as U+FFFD (checked), as better-sqlite3 does; Npgsql and MySqlConnector encode with strict UTF-8 and throw, which would lose the run, so every string is bound through `Js.WellFormed` (U+FFFD for a lone half), as the Java port binds through `Js.wellFormed` (its Decision 28). Every store, in every dialect and in memory, writes a run's trigger, output, error, and metric names, and every key and string of a definition and a state, without U+0000 (a NUL dropped from the JSON text), since Postgres text cannot hold one and one NUL made the whole run's write fail there; `store.json`'s `nul` steps replay it.
- *Not the app's transaction.* ADO.NET has an ambient transaction the other ports' drivers do not: a `System.Transactions.TransactionScope` flows with the async context, and Npgsql and MySqlConnector enlist a connection opened inside one by default. A store write from a job's function inside the app's scope would join it and vanish with the rollback the failure caused. So every store call opens its connection inside `new TransactionScope(TransactionScopeOption.Suppress, TransactionScopeAsyncFlowOption.Enabled)`, and each statement runs on a connection of the store's own in autocommit; an EF Core `DbContext`'s transaction is on the context's own connection and never reaches the store's. The tests hold it on every server with both: a `TransactionScope` whose own write (on a connection the driver enlists) is rolled back while the failed run it surrounded stays, and a `DbTransaction` on the app's own connection, which is what an EF Core transaction is, so EF Core is not a test dependency (see Decisions, 37).
- *SQLite.* The store holds one connection for its statements, in turn, opened from the data source once and kept, as the SDK's, Go, Rust, and Java stores hold one: a pool's connections would each need the pragmas, an in-memory database is one per connection, and SQLite has one writer at a time anyway. That connection is put in WAL mode with the SDK's retry of a busy database while switching (`busy.ts`), then `busy_timeout` 5000 and `synchronous` NORMAL. Microsoft.Data.Sqlite, with the `SQLitePCLRaw.bundle_e_sqlite3` native builds it brings, is the driver the tests use and the README names; it runs under Native AOT.
- *MySQL.* MySqlConnector counts matched rows by default; the store reads back a conditional write that answered 0 anyway (a run's update, and the compare-and-set from version 0 in two steps), so a connection string with `UseAffectedRows=true` cannot make a write that landed read as refused, which a test runs both ways.
- *Foreign rows.* A row of another shape than the SDK writes, valid JSON all the same, is read as the SDK reads it rather than failing every read it is part of, with every audit's fixes from the start: metrics that are not all numbers keep the ones that are (one that reads as Infinity, `1e400`, is kept but left off the job page, as the SDK leaves it off), a queued alert that is not an alert is dropped, times near the limits saturate, a duration is held from 0 to 2^53 - 1, a state's version that is not a whole number from 0 to 2^53 - 1 counts as 0 (in the SQL of every dialect, the client, and the memory store alike), a MySQL write whose answer was lost counts as written when the stored row equals what was sent, SQLite text that is not UTF-8 reads with U+FFFD, and a time before the year 1 or after 9999 is written in words wherever the SDK writes a date (see Keeping in step). .NET's `DateTime` cannot hold a year outside 1 to 9999 at all and throws, so the date code is the port's own over `long` milliseconds (`Date.UTC` and `toISOString` in `Internal/Js`), never `DateTimeOffset.FromUnixTimeMilliseconds`, which throws for such a time.

The drivers are test dependencies only: `Microsoft.Data.Sqlite`, `Npgsql`, and `MySqlConnector` (which serves MariaDB too), so none reaches an app through the core. `Cronwatch.StoreTesting` is the SDK's `store-conformance.ts`, the `store.json` replay (with its `foreignVersion` cases, each state text written raw, and its `nul` steps), and the finish-once scenarios, for a store of the app's own, the Go, Rust, and Java ports' `storetest`: it depends on no test framework (it throws `StoreContractException`, which every framework reports), and is handed the fixture's text by the caller, since a published package cannot read the repository. The core's own tests run it per database, with a check over a run that started at `long.MinValue`, the finish-once scenarios over several clients on one database, a client end to end, the rollback test, and rows of another shape: SQLite always, Postgres, MySQL, and MariaDB when `CRONWATCH_TEST_PG`, `CRONWATCH_TEST_MYSQL`, and `CRONWATCH_TEST_MARIADB` are set (as URLs, `postgres://postgres:pw@127.0.0.1:5432/cw`, turned into each driver's connection string by the tests), each test on tables of its own prefix, dropped at the end. A node-compat test has the built SDK and the .NET store replay the same calls into two SQLite files and compares what each reads of the other's and every column's bytes and SQLite type, and has a Node client and a .NET client take turns on one file and one job's state version.

## Zones

Zones are `TimeZoneInfo`, which since .NET 6 finds IANA names on every system: on Linux and macOS it reads the system's IANA database (`/usr/share/zoneinfo`, as the Go and Rust ports read it), and on Windows it maps an IANA name to a Windows zone through ICU, which Windows 10 1903 and later carry. The croner port asks `TimeZoneInfo` for the offset at an instant and walks its adjustment rules for the transitions around one (croner's `fromTZ` rule is the port's own).

- *Names without regard to case.* `Intl` matches zone names without regard to case; `FindSystemTimeZoneById` on Linux does not (checked: `america/new_york` is not found, `America/New_York` is, and only `utc` is special-cased). So the core carries the list of IANA names, aliases included (some six hundred short strings, from the tz release `scripts/conformance.mjs` records, refreshed with a script), matches a name against it ordinally ignoring case, and asks `TimeZoneInfo` for the name as the list spells it. Fixed offsets (`+05:30`) are zones too, as croner accepts them, made with `TimeZoneInfo.CreateCustomTimeZone`. A name the list has and the system lacks is refused with the SDK's message, since croner would refuse a zone its `Intl` does not know.
- *Windows' own rules.* On Windows, a zone found by its IANA name still has the Windows registry's rules, which keep less history than the IANA database and group some zones together; fire times in a year a zone changed its rules can differ from Node's (whose ICU carries the IANA data). CronWatch's schedules are about now, where the two agree for every zone `schedule.json` names, which the `dotnet-platforms` CI entry holds on Windows. Hangfire and Quartz on Windows name zones by their Windows ids (`Eastern Standard Time`); the integrations convert them with `TimeZoneInfo.TryConvertWindowsIdToIanaId` before declaring, and a Windows id with no IANA name is watched without a schedule and reported once.
- *Where there is no database.* The .NET chiseled and distroless container images carry no `tzdata` unless the app picks an `-extra` image or installs it, and an app set to `InvariantGlobalization` on Windows has no ICU to map names through. In either, a named zone is not found, and the job is refused with the SDK's message when it is declared, not at its first fire, and the README says which image to use. Without a `Timezone`, a cron is read in the client's `TimeProvider.LocalTimeZone`, which is `TimeZoneInfo.Local` for the system clock: on Linux and macOS that follows `TZ`, else `/etc/localtime`; on Windows it is the system's zone, and `TZ` is not read.
- *Weighed.* NodaTime carries its own IANA database in the assembly and would make every system give Node's answers, but it is the core's first dependency (about a megabyte) and apps already have `TimeZoneInfo`; embedding a compiled database of the port's own, as Java's `tzdb.dat` and Elixir's `tz` are, means a release per IANA update. Neither is needed for the schedules CronWatch reads, so both wait until someone meets a difference (see Decisions, 6).

## Redaction and expect patterns

Secret redaction uses the SDK's patterns, copied verbatim as JavaScript source into `Internal/Output` and run by `Internal/Jsre`, the Java port's engine (the Go port's, as hardened by the Rust, Elixir, and Java ports) carried over, over the string's own UTF-16 code units, since a .NET string is one: a quantifier counts an emoji as two, `\s` is JavaScript's set, `\b` and `/i` are ASCII-only as they are in JavaScript without the `u` flag (letters fold as JavaScript's Canonicalize, the Elixir audit's fix), a class holding a character outside the BMP is read as its two code units, as V8 reads it without the `u` flag, and every one of `conformance/output.json`'s 204 redaction cases gives the SDK's bytes. It refuses what it does not implement rather than read it as something else, with the Java port's messages (a `\0` followed by a digit, a quantified lookbehind).

`System.Text.RegularExpressions` was run and left out for both redaction and stored patterns, though it counts in UTF-16 units, has lookbehind and a match timeout: its `$` matches before a final newline (checked: `a$` matches `"a\n"`), its `\s` leaves out U+FEFF and takes U+0085 (checked), the reverse of JavaScript's, its `\w`, `\d`, and `\b` are Unicode's unless `RegexOptions.ECMAScript`, which in turn refuses options and constructs JavaScript has and still reads backreferences, named groups, and character class subtraction its own way, `[^]` is an error, and its case folding is culture's or invariant, not Canonicalize. `RegexOptions.NonBacktracking` bounds the time but has no lookaround or backreferences. The Python port showed the SDK's patterns can be rewritten for another engine, but a stored `matches /.../` pattern is JavaScript source that no rewrite can foresee, and one engine in seven ports means one answer.

The Rust audit's bounds come with the engine, as rules rather than findings: a pattern longer than 4096 characters or with groups nested more than 100 deep is not read; a match gives up past 512 frames of recursion (a .NET thread's default stack of 1 MiB, the thread pool's, holds it with room to spare, which a test runs on a pool thread, since a `StackOverflowException` cannot be caught and would end the app); and a stored expect pattern counts its steps (each attempt at a node, and each code unit a repeat scans) and gives up past 50 million, the Rust and Java ports' budget, lowered in phase 1 if an exhausted budget takes more than two seconds on CI's runner, with the measured number written here. A stored pattern that runs out of its bound fails, with the ordinary `Output did not match /source/flags`: a pattern is slow because it is searching an output it does not match, so failing is the answer an engine that finished gives in nearly every case, and a guard that passed when it could not tell would hide the broken job it is there to catch (the Rust port's decision 36, the rule every bounded port keeps). The SDK's own redaction patterns are bounded and run without a budget. The JSON reader refuses nesting past 256, as the Rust, Elixir, and Java ports' do; objects are read into an order and a map of values, never by a scan per key, the Elixir audit's fix for a JSON object of many keys, and a run's metrics are set in place, never copied per metric, the Java audit's.

## Dashboard

`cw.Routes(RoutesOptions)` is the SDK's `cw.routes()`: a `Routes` whose answers are `routes/index.ts` line for line and whose pages are `routes/html.ts` and `routes/timeline.ts` byte for byte, the CSS, the app shell, the icons, the sign-in form, and the `<wbr>` after a name's separators included; `Internal/Web` is the Java port's `internal/web`, carried over. The options are the SDK's, in the three-way form: `Token = "..."`, `Token = DashboardToken.None`, or neither (reading `CRONWATCH_TOKEN` when the routes are made); a token or secret, from the environment or the options, is trimmed by JavaScript's `trim` (a value read from a file often ends in a newline no header can carry), and one that is then empty counts as unset, `BasePath`, `Origin` (read as `new URL(value).origin` reads it, through `WhatwgUrl` with its host step writing a host outside ASCII in punycode, see Decisions, 47; anything but http or https is refused with the SDK's message), and `TrustProxy`.

The core is framework-free: `Routes.HandleAsync(CronwatchRequest, CancellationToken)` answers a `CronwatchResponse`, over plain values (the method, the request target as sent, the headers as sent, a body read only when a route wants it, whether it came over TLS, and where an adapter found the mount), as the Rust, Elixir, and Java ports' routes are, so the golden replay tests the same code every adapter runs. `Cronwatch.AspNetCore` is the adapter:

- *`app.MapCronwatch("/cronwatch")`*, on endpoint routing, which minimal APIs, MVC, Razor Pages, and Blazor all use: it maps the pattern and everything beneath it (`{**rest}`) for every method, and answers the convention builder, so an app can add its own conventions. The endpoints are `.DisableAntiforgery()` (the dashboard has its own cross-site check and cookie; ASP.NET Core's antiforgery would refuse its forms, as Phoenix's CSRF plug and Spring Security's would) and `.ExcludeFromDescription()`, so no OpenAPI document lists them. While the dashboard has a token they allow anonymous requests, so an app whose fallback policy requires a signed-in user still reaches the dashboard's own sign-in, the Java port's Decision 17, but only when nothing on the endpoint asks for authorization: the `AllowAnonymousAttribute` is added by a `Finally` convention that looks first for `IAuthorizeData`, `AuthorizationPolicy`, or `IAuthorizationRequirementData` metadata, so a policy the app puts on the dashboard (`.RequireAuthorization("Admins")` on the answer) or on a route group around it is enforced ahead of the token (see Decisions, 70); `Open = true`, a dashboard with no token meant to sit behind the app's own sign-in, adds no `AllowAnonymous`, so the app's policy applies, which is the Java audit's finding (an open dashboard ahead of Spring Security was open to anyone) written in from the start; since the SDK audit's port it also adds `.RequireAuthorization()`, so an app with no fallback policy does not serve it to anyone, and an app that wants it open chains `.AllowAnonymous()`. Route groups (`app.MapGroup("/admin").MapCronwatch()`) set the base path as they set the route.
- *`app.UseCronwatch("/cronwatch")`*, middleware, for an app that wants the dashboard ahead of its other middleware or has no endpoint routing: a branch on the path, which sets `PathBase`, answering everything under it and passing every other request on. Being middleware, not an endpoint, it carries no endpoint authorization, so an open dashboard served this way sits behind the app's sign-in only when `UseAuthentication` and `UseAuthorization` (with a fallback policy) come before it, which the README says and `UseCronwatch` logs as a warning, once, when it is added. Options given to either that name no token take the container's (`Cronwatch:Token`) through `RoutesOptions.WithDefaultToken`.
- *The target* comes from `IHttpRequestFeature.RawTarget`, the request line as sent, not `HttpRequest.Path`, which ASP.NET Core decodes and in which it resolves dot segments (checked on Kestrel: `/cronwatch/jobs/%C3%A9` arrives in `Path` as `é` and `/cronwatch/../x` as `/x`, while `RawTarget` keeps both; a `%2F` is kept in both). The base is `BasePath` when given, else `PathBase` and the route's prefix, else the SDK's `/cronwatch`.
- *The body* is read from `Request.Body` only when a route wants it, to at most 1 MiB and one byte (413 past it, as every typed port answers); a form something ahead of the dashboard already read (`Request.Form`, `ReadFormAsync`) is taken from `IFormFeature`'s parsed form when the body reads back empty, as the Java port takes a servlet container's parameters and the Elixir port Phoenix's `body_params`.
- *The answer* is written with its `content-length` always, so Kestrel never frames it as chunked (checked: without one it does). What Kestrel changes, as `KestrelTests` holds it on .NET 10: it writes `Content-Length` first, then `Connection`, then the headers it knows in an order of its own and in their registered casing (`Content-Type`, `Date`, `Server`, `Cache-Control`, `Location`, `Set-Cookie`, `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`), and last the ones it does not know, lowercase as the routes wrote them (`referrer-policy`, `x-robots-tag`, `service-worker-allowed`); it adds `Date` and `Server: Kestrel`; and a 303 carries `Content-Length: 0`. Header names are not case sensitive and their order carries no meaning here, so the replay through a server compares names without case and order as a set, with `Date`, `Server`, `Content-Length`, `Connection`, and `Transfer-Encoding` aside, as the Java replays set aside what each server adds. Straight into the routes the answer carries no `content-length`, as the SDK's does, and matches header for header.

What a request says is read as the SDK reads a fetch `Request`, carried over from the Go, Rust, Elixir, and Java ports: the path from the target as sent, the query as `URLSearchParams` parses it, headers joined as `Headers.get` joins them and compared as Latin-1, the body as `request.json()` and `request.formData()` read it, and the origin from the scheme the adapter reports and the raw `Host`.

- *The development token.* With no token set, in development (see Rules), the dashboard makes one (32 bytes from `RandomNumberGenerator`, written with `Base64Url`) and announces it once per `Routes` on `Console.Out`, ending `\n`, where `console.info` writes it (a closed or failing output is ignored, as `console.info` never throws, the Rust audit's case). The line shows the host only when `Origin` is set or the request's origin is loopback (`localhost`, `*.localhost`, 127.0.0.0/8, `[::1]`), the SDK's `developmentSignInLine` and `isLoopbackOrigin`, and the origin is read as a URL by the origin reader before its host is tested, as the Rust audit found it must be: a `Host` of `evil.example/.localhost` or `localhost:1@evil.example` is not loopback, and a string test took both for it. Kestrel refuses both of those `Host` headers itself with a 400 (checked, and one outside ASCII too), but HTTP.sys, IIS, the test server, and a proxy's `X-Forwarded-Host` read under `TrustProxy` do not all refuse them, so the parsed URL stays the guard. The token is made when the routes are made, so two first requests at once agree on it, and it is announced once; `Routes.Token()` is the token in use, the generated one included.
- *Carried over from the audits.* A `Host` outside ASCII longer than 1024 bytes is not punycoded or read as a URL; a body that could not be read to its end is read as none, never as the part that arrived (`for=7d` cut short is not a 7 ms silence); a request whose client went away (`RequestAborted`) reports nothing; a body nested deeply reads as none; huge durations and a foreign row's far times are answered; the token, the cookie, and the bearer are compared in constant time with `CryptographicOperations.FixedTimeEquals` over their bytes; every value on the pages is escaped; the routes answer an exception with the SDK's 500 and report it as `routes`.

The style sheet, scripts, and icons are the SDK's files copied into `packages/dotnet/src/Cronwatch/Web/Assets`: `scripts/make-dashboard-icons.mjs` writes the icons there beside the other ports' copies, and `packages/ruby/test/web/golden.mjs` writes `style.css`, `app.js`, and `sw.js` from its captures, and both, run with `--check` by `npm run check:conformance`, fail when a copy differs from the SDK's. Each script gets its .NET destination in phase 3.

`GoldenTests` replays the gem's fixture, `packages/ruby/test/web/golden.json` (105 captures of the SDK's routes over a fixed seed, PNGs as base64; `GET /api`'s two answers hold `<library>`, `<language>`, and `<version>`, which the replay fills with `Cronwatch`, `dotnet`, and `CronwatchClient.Version`), three ways: straight into `Routes.HandleAsync` (all 105); through ASP.NET Core's in-memory `TestServer` (`Microsoft.AspNetCore.TestHost`), once behind `MapCronwatch` in a route group and once behind `UseCronwatch`; and through a real Kestrel over a socket, with a raw HTTP/1.1 client of the tests' own (`HttpClient` will not send a `Host` of the test's choosing). Kestrel passes a target that is not a valid percent-encoding (`/cronwatch/jobs/%zz`) through to the app, so unlike the Java servers it replays every capture, which phase 3 confirmed; the three captures outside the base (`/cronwatchapi/jobs`, `/api/jobs`, `/cronwatch-x/api/jobs`), which no server routes to the dashboard, are answered straight by the routes in the replays through a server. Kestrel refuses with a 400 of its own, before the routes see it, a `Host` that is not a host (`evil.example/.localhost`, `localhost:1@evil.example`), a `Host` or any header value outside ASCII, and a request target with a byte outside ASCII; the test server does not, which is where the routes' own guards are held. The replay, the seed, and the raw client are `test/Cronwatch.WebTest`, a project that is never packed, which the adapter's tests depend on. The SDK's routes tests are ported as the Go, Rust, Elixir, and Java ports have them (the token, the cookie, the forms, the cross-site check, the origin and the forwarded headers, the silence durations and the 64 character cap, the body cap, the app shell, the base path from the mount, the audits' cases), and what depends on the environment (locked, the development token and its sign-in line, a handler without a secret) runs in child processes, each with its own variables, since the process's environment is shared by every test running at once. A behaviour change lands in TypeScript first, and `TZ=UTC node packages/ruby/test/web/golden.mjs` regenerates the fixture for every port.

## Handler

`job.Handler(fn, HandlerOptions)` is the SDK's `handler()`, for a platform cron that calls a URL (a Kubernetes CronJob with `curl`, Azure Container Apps jobs behind a scheduler, Render, Fly.io): framework-free like the dashboard (`Handler.HandleAsync(CronwatchRequest, CancellationToken)`), and on ASP.NET Core `app.MapCronwatchHandler("/cron/nightly", "nightly-report", async (JobContext job, HttpContext http, CancellationToken ct) => ...)`. It runs the function as a recorded run with the trigger `"handler"` for each request whose `Authorization` is `Bearer <secret>`, read as the dashboard reads its bearer (the scheme in any case, then any whitespace) and compared in constant time; the secret is the option's, else the client's (`CRON_SECRET` by default, read when the client is made, `""` counting as unset); `Secret = HandlerSecret.None`, or the client's `CronSecret.None`, lets anyone run the job. With no secret and no opt-out, outside development, it answers 503 with the SDK's JSON; a wrong or missing bearer is 401. A run is answered with `{"ok","job","run","status","durationMs"}`, 200 or 500, and the error's first line only when a secret was required, with the headers of the SDK's `json()`. The function may return a `CronwatchResponse` (or on ASP.NET Core an `IResult`) of its own, which is passed through and fails the run at 400 or more with `HTTP <status> <reason>`. A throw is a failed run answered 500, as the SDK answers a throw. The handler answers with the run as recorded, handed to it by the run itself, rather than reading it back from a store that may be down. The function runs in the request with the request's `RequestAborted` token linked into the run's, so a request whose client goes away cancels the job as a platform's timeout would; an app that wants the job to outlive the request starts it on its own. `MapCronwatchHandler`'s endpoint allows anonymous requests only while a secret guards the handler (`Handler.IsOpen` is false) and the app puts no authorization policy on it or on a group around it, the dashboard's `Finally` convention; a handler open to anyone takes the app's authorization policy, the dashboard's rule (phase 5's fix). An Azure Functions timer trigger or AWS Lambda adapter is made only if someone asks, as the Go port's Lambda adapter was the only one made.

## Hosting

`Cronwatch.Hosting` is how nearly every .NET service would hold the client: `builder.Services.AddCronwatch(o => { ... })`, or `AddCronwatch((services, o) => ...)` for options that need other services (the app's `NpgsqlDataSource`, its channels). It registers `CronwatchClient` as a singleton, binds the `Cronwatch` section of `IConfiguration` over the options for what configuration can say (`Retention`, `Token`, `CheckEvery`, `Environment`, the defaults), with the code's options applied after, and registers every `IChannel` in the container as a channel. `CheckEvery` (a minute by default; `null` for none, where another process checks) runs the check as a hosted service on the client's `TimeProvider`, the SDK's `start()`, started after the host starts and stopped before it stops. The error handler is the app's `ILogger`, the environment is the host's when CronWatch's own variables are unset (see Rules), and each run's function runs inside a log scope with `cronwatch_job` and `cronwatch_run` (see Telemetry). The options binding uses the configuration binder's source generator (`EnableConfigurationBindingGenerator`), so it stays AOT compatible.

`app.Services` disposes the client when the host stops, after the hosted services have stopped, so a run a `BackgroundService` was in the middle of is recorded failed through its cancelled token before the client lets go of its store (see Tasks and state).

### Hosted jobs

.NET has no cron scheduler in the box: a job inside a service is commonly a `BackgroundService` looping on `PeriodicTimer` or `Task.Delay`, which runs on its own clock while the job CronWatch watches is declared with a schedule written somewhere else, and the two can drift apart unnoticed. `Cronwatch.Hosting` offers one small helper that makes them one definition: `services.AddCronwatchJob<NightlyReport>("nightly-report", new JobOptions { Schedule = "0 2 * * *", Timezone = "UTC", Grace = "15m" })`, where `NightlyReport` implements `ICronwatchJob` (`Task RunAsync(JobContext job, CancellationToken ct)`). One hosted service runs every such job at the fire times the croner port gives for its schedule (`every 5m` too), each fire a run with the trigger `hosting` (`schedule` before 0.11, renamed so every integration's trigger is its name, plan D17), its class resolved from a new DI scope per run and disposed after it, its token cancelled at the job's timeout and at the host's shutdown. A fire that comes while the job's previous run is still going is skipped, not queued, and written to the log once per run it waited on, so a slow job cannot pile up behind itself. It is a scheduler for one process: every replica of a service runs its hosted jobs, as a `BackgroundService` does, and the README says to use Hangfire or Quartz with a shared store where a job must run once across a cluster. An app with a loop of its own needs no helper: it declares the job with its schedule and calls `job.RunAsync` in the loop (see Decisions, 14).

*Built in phase 4.* One hosted service runs every `AddCronwatchJob` job, one loop per job on the client's `Clock`: the jobs are declared as the host starts (a bad schedule stops it with the SDK's message), and the loops wait for `IHostApplicationLifetime.ApplicationStarted` before their first fire. A cron's next fire is counted from the later of the last fire and now, so a process that was paused does not catch up in a burst; an interval counts from the last fire (`Job.NextFire(after, lastRunAt)`, public for a scheduler of the app's own). A timer is armed for at most a day at a time. The loop says it is waiting for a fire only once its timer is armed, and a run is counted from before it starts until its task has completed, so a test on a `FakeTimeProvider` never moves the clock past a timer not yet armed (which would then wait a whole interval more) and never finds no run under way while the last one's task is still finishing (which would skip the next fire); both were flakes under CPU load. Stopping cancels the runs' tokens and waits for them within the host's shutdown timeout; what is left is recorded by the client as it is disposed.

### A plain crontab

A program a crontab runs needs no integration: make the client in `Main`, run the job, return 1 on failure, and a second crontab line runs a check, both on a store both processes reach (SQLite on the box, or the app's database). The check line needs the same store and channels as the job, which only the app knows, so the command-line entry is the app's own program, not a tool of the library's. `CronwatchCli.RunAsync(factory, args, stdout, stderr)` in the core takes the app's own factory for its client and runs `check` (one check, the result printed as `cronwatch: checked 3 jobs, sent 1 alert`, the client disposed) and answers the status (0, 1 for a failed check or a factory that throws, 2 for a command it does not know) and never ends the process, the Elixir and Java audits' rule that a check entry point never halts a running app. In a Generic Host app, `await app.RunCronwatchCommandAsync(args)` in `Cronwatch.Hosting` does the same with the host's own services: given `cronwatch check` it builds the client from the container without starting the hosted services (so no web server, queue, or hosted job starts), checks once, and answers the status; given anything else it runs the host as `RunAsync` would. A crontab line is then `dotnet /app/MyApp.dll cronwatch check`. A `dotnet tool` of the library's own (`dotnet cronwatch check`) was weighed and left out, as every other port left out its own: a tool installed apart from the app cannot load the app's store driver or its channels' secrets, and would need a configuration format of its own to learn them (see Decisions, 16). `examples/crontab` is that program on SQLite, with a test that runs its two lines as two processes on one file.

## Scheduler integrations

The SDK has none; these follow the Go, Rust, Elixir, and Java ports', whose shared rules (declaring entries as jobs, several entries of one name on different schedules being one job without a schedule, tags for the integration and the app, jobs gone declared again without their schedule, workers elsewhere declaring from the store's definition, schedules checked against the scheduler's own fire times, retries as the gem's Sidekiq rules) are `Cronwatch.Bridge`, carried over from the Java port's `dev.cronwatch.bridge` with every audit's fixes from the start: `Unschedule` reads what is declared again under the declaring lock and writes every declaration before it returns; a declaration's write is held to 30 seconds, and a sync an integration starts itself to 30 more; `Fallback` reads the store before it declares and declares nothing when the read fails, and a job `Declare` has declared meanwhile wins; a job `Fallback` declared and the dashboard has forgotten since is dropped and declared again from the store at its next run, as the Rust port's `held` does, so `Unschedule` never takes the schedule out of a job another process schedules (the cross-port check's); a throw in one declaration's write is that declaration's failure and never leaves the writer marked busy; a declaration's write whose caller gave up does not keep waiting on a hung store; the answer of a fire-time check is kept per job, expression, zone, and year, so an unchanged cron's fire times are not walked again at every read (the Java audit's). A run whose start failed needs a placeholder wherever a scheduler reports a run's start and end as separate calls, so each integration keeps what the end needs on the scheduler's own object for the invocation (nothing when the attempt is not watched or its start failed), and the two always pair. The app tag is the PHP port's `appTag()` character for character (MD5 when empty or long), and the app is the integration's `App` option, else `$CRONWATCH_APP_ID`, else `IHostEnvironment.ApplicationName`, else the entry assembly's name.

A run seen from outside the function (a filter or listener told of its start and end) is opened and closed by the two halves of `RunAsync`: `job.OpenAsync(RunOptions)` answers an `ObservedRun` (`CloseAsync(exception)`, `CloseWithAsync(value)`, `TakeBackAsync()`), so the running row, the activity, the process-exit hook's record, and the rest are `RunAsync`'s, as the Java port's `job.open` and the Elixir port's `Exec.open/2` are. `RunOptions.WithId` gives the run the integration's id, and `RunOptions.MayTakeBack` leaves missed and stuck open until the run is known not to be given back. `ObservedRun.MakeCurrent()` sets `CronwatchClient.Current` in the calling flow and answers an `IDisposable` that restores what was there, for an integration whose callbacks are synchronous (see Runs). These are public, in the `Cronwatch` and `Cronwatch.Bridge` namespaces, so the integration packages reach nothing internal and an app can write an integration of its own for a scheduler not listed here.

### Hangfire

`Cronwatch.Hangfire` watches Hangfire 1.8 (`Hangfire.Core` 1.8.0 or newer, 1.8.25 the newest, on `netstandard2.0`), the job scheduler .NET apps run most, with recurring jobs on a cron, retries (ten by default), and a dashboard of its own, over SQL Server, Redis, Postgres, and other storages. `services.AddHangfire(c => c.UseCronwatch(services))`, or `GlobalJobFilters.Filters.Add(new CronwatchHangfireFilter(cw))` without DI, and nothing changes in the app's jobs.

- *Each attempt a run.* An `IServerFilter`: Hangfire's `BackgroundJobPerformer` calls `OnPerforming` in the worker's thread just before the job's method and `OnPerformed` there just after, with the exception the method threw in `PerformedContext.Exception`, and it calls them synchronously, awaiting an async job method with `GetAwaiter().GetResult()` between them. So `OnPerforming` opens a run (trigger `hangfire`, id `hangfire:<app>:<job id>:<attempt>`, the attempt counted from 0 in a job parameter of the integration's own, `CronwatchAttempt`, since Hangfire's `RetryCount` stays the same when a job is requeued from its dashboard or fetched again after its worker died; phase 5's fix) and makes it current, which, set in a synchronous call on the thread that then runs the job, reaches the job's method; `OnPerformed` closes it and takes it off the thread in `finally`, so a pooled worker thread keeps nothing. Phase 4 holds both with tests on 1.8.0 and the newest; if a Hangfire release is found to call the filter from an async frame, the run is made current by a `JobActivator` scope instead. Each retry is a new attempt and a new run: failing attempts open one failed alert and the one that succeeds closes it, and `FailuresBeforeAlert` says how many attempts to allow first.
- *What Hangfire gives back.* A job stopped because its server is shutting down (its `CancellationToken` or `IJobCancellationToken` cancelled by the server's shutdown, which Hangfire answers by putting the job back in its queue rather than failing it) is taken back as a run given back (the row deleted, nothing judged), as a River snooze is in the Go port and an Oban snooze in the Elixir one; one cancelled because it was deleted from Hangfire's dashboard is a failure. A run that may be given back closes missed and stuck only once it is known not to be.
- *Failures before the method.* A job Hangfire fails before it performs it (its type or method no longer loads, a `JobLoadException`, or its arguments no longer deserialize) never reaches `OnPerforming`; an `IApplyStateFilter` sees its move to `Failed` with no run open and records a failed run through `RecordRunAsync`, so a recurring job broken by a deploy alerts at its first fire rather than waiting for missed.
- *Which jobs.* The recurring jobs, read from the storage's connection (`GetRecurringJobs()`: the id, the cron, the zone id, the queue, and whether Hangfire itself flags it as broken) when the integration starts and every minute, each a job named after its recurring job id (`nightly-report`), on its cron in its zone (a Windows zone id converted; see Zones). A job a recurring job enqueued carries the id in its `RecurringJobId` parameter, so a server whose own code never registered the recurring job still records it, declared from the store's definition through the bridge's `Fallback`. A job that is not recurring (a fire-and-forget or delayed job) is watched only when named, with `[CronwatchJob("import")]` on its method or in the integration's options by its type and method, so a queue of a million email jobs is not a million runs. Jobs are tagged `hangfire` and `hangfire:<app>`.
- *Schedules.* Hangfire reads its crons with Cronos, which it carries inside its own assembly; Cronos takes five fields or six with seconds first, `?`, `L`, `W`, and `#`, and names such as `@daily`. Each is declared as written with a `?` written `*` (croner reads `?` as a day field naming every day, the Java audit's finding for Quartz and Spring), and checked with `Bridge.CheckFires` against Cronos's own reading (the `Cronos` package, a dependency of `Cronwatch.Hangfire` at the version Hangfire carries, and the `NextExecution` Hangfire itself stores beside each recurring job); one the two read differently is reported once and watched without a schedule, as every port does for its schedulers.
- *The check.* A recurring job of its own, `cronwatch-check`, every minute (`UseCronwatch(..., scheduleCheck: true)`, or `CronwatchHangfire.ScheduleCheck(recurringJobManager)`), with `[AutomaticRetry(Attempts = 0)]` and `[DisableConcurrentExecution]`, runs the sync (the recurring jobs declared again, settled, then unscheduled, within 30 seconds) and a check once per minute across every server of the cluster, since Hangfire enqueues a recurring job once per fire under its own distributed lock; its runs are never a job.

The tests run a real Hangfire server on `Hangfire.InMemory` storage always, and on `Hangfire.PostgreSql` when `CRONWATCH_TEST_PG` is set, with recurring jobs every second (Cronos's seconds field) and jobs enqueued by the tests: the recurring jobs declared (a zone, a Windows zone id, `@daily`, a `?`, an expression Cronos reads differently reported), a job failing twice through retries and then succeeding (three runs, one alert and its recovery, the output logged through `Current`), an async job method, a job aborted by its server's shutdown given back, a job whose type no longer loads recorded failed from the state filter, a job deleted from Hangfire declared again without its schedule, a named job that is not recurring, the worker thread carrying no run after a job, and the check job unscheduling a recurring job removed. Hangfire.Core is LGPL 3; `Cronwatch.Hangfire` references it as an ordinary package dependency, which the license allows, and carries none of its code.

*What phase 4 found.* Hangfire calls the server filter synchronously on the worker thread and runs the job method, async ones included, inside that thread's execution context (`ExecutionContext.Run`, or `Task.Factory.StartNew` on the default scheduler for an async method), so `MakeCurrent()` in `OnPerforming` reaches the job and disposing it in `OnPerformed` leaves the thread clean; a test holds that the next job on a one-worker server sees no run. The job's own exception arrives wrapped in `JobPerformanceException` and is unwrapped. A cancellation during the server's shutdown arrives raw and the worker requeues the job, so the run is given back, as is one a filter after ours cancels (`OnPerformed` sees `Canceled`); a `JobAbortedException` from a job deleted from the dashboard is a failure. A job whose type or arguments no longer load throws `JobLoadException` before any server filter runs, and `AutomaticRetry` swaps its `FailedState` for a `ScheduledState` during election, so an apply-state filter would never see it: the filter is an `IElectStateFilter` instead, finding the failed state among the candidate and traversed states and recording the run under the same id, never twice. Hangfire 1.8.25 carries Cronos 0.11.1 inside its own assembly (identical once decompiled), which `Cronwatch.Hangfire` takes as a package; 1.8.0 carries 0.7.1, which refuses macros such as `@daily`, so Hangfire 1.8.0 refuses them too. Hangfire renamed the server filter's parameter within 1.8 (`filterContext` in 1.8.0, `context` later), so CA1725 is off on the filter with that reason. Hangfire.Core asks for Newtonsoft.Json 11.0.1, which has a known high-severity vulnerability (GHSA-5crp-9r3c-p9vr) and fails restore under warnings as errors, so the package asks for 13.0.4. The entry points are `GlobalConfiguration.Configuration.UseCronwatch(cw)` and `UseCronwatch(serviceProvider)` for the life of the process, and `CronwatchHangfire.Start(cw, options)`, which answers an integration the app can dispose (its filter taken off `GlobalJobFilters` and its reading stopped), and since Hangfire's filters are the process's, one integration watches Hangfire per process: a second `Start` or `UseCronwatch` stops the one before it (phase 5); the check is a static `CronwatchCheckJob.RunAsync()`, so it needs no job activator. The app name is the `App` option, else `CRONWATCH_APP_ID`, else the entry assembly's name, without `IHostEnvironment.ApplicationName`, which would need a Hosting dependency and defaults to the entry assembly's name anyway. Hangfire keeps its filters, storage, and type resolver in statics, so the tests run one at a time in one class, on `Hangfire.InMemory`; the Postgres storage tests were not built.

### Quartz.NET

`Cronwatch.Quartz` watches a Quartz.NET 4 scheduler (`Quartz` 4.0 or newer, released 2026-09-03 and on `net10.0` alone): `services.AddQuartz(q => q.UseCronwatch())`, or `CronwatchQuartz.WatchAsync(cw, scheduler)` without DI. Quartz is the other scheduler .NET apps run, clustered over an ADO.NET job store in many of them. Quartz 4 made every listener member return `ValueTask` and gave each a default implementation, so a listener still written against 3.x's `Task` members compiles and silently implements nothing (Quartz's own release notes warn of it); the integration is written against 4's interfaces, and a test fails if Quartz never calls it. Quartz 3.x (3.19, still maintained) is not supported by this package, since one package cannot implement both lines' interfaces; see Decisions, 13.

- *Each firing a run.* A global `IJobListener`: Quartz's `JobRunShell` awaits `JobToBeExecuted` before the job's `Execute` and `JobWasExecuted` after it, with the `JobExecutionException` it caught, so the first opens a run (trigger `quartz`, id `quartz:<app>:<scheduler instance id>:<fire instance id>:<refire count>`, a random part added to the instance id when the scheduler is not clustered, since every such scheduler is `NON_CLUSTERED` and two processes could otherwise give two firings one id, the Java audit's finding) and puts it on the job's `IJobExecutionContext`, and the second closes it, failed with the exception's cause (an exception `Execute` threw is wrapped by `JobRunShell`). A `JobExecutionException` with `RefireImmediately` is a failed attempt and its refire a new run. A vetoed firing opens nothing. A firing another listener stopped after ours opened it (its `JobToBeExecuted` threw, so Quartz never runs the job or calls `JobWasExecuted`) is given back, the Java audit's case.
- *`Current` in a Quartz job.* The listener's members are async, and a value an async method sets in an `AsyncLocal` is undone when it returns (see Runs), so the listener cannot make the run current for the job. `UseCronwatch()` therefore also wraps the job factory Quartz's DI integration uses: the job it hands Quartz is the app's job inside a thin one whose `Execute` reads the run from the context, makes it current, and calls the app's, so `CronwatchClient.Current` and `job.Log` work inside a job with no code. Quartz reads `[DisallowConcurrentExecution]` and `[PersistJobDataAfterExecution]` from the `JobDetail`'s type, not the instance, so the wrapper changes neither. Without DI, the run is on the context (`context.CronwatchRun()`), and a job that wants `Current` calls `MakeCurrent()` itself.
- *Which jobs.* Every `IJobDetail` the scheduler holds with at least one trigger, named after its `JobKey` (`nightlyReport` in the `DEFAULT` group, `reports.nightly` in another), read when the integration starts, again when an `ISchedulerListener` says a job or trigger was added or removed (whose calls only ask the integration's own task to read again, since they come from inside Quartz's own locks), and every minute. Quartz marks itself shut down before it tells its listeners, so a read begun in that gap is refused with `The Scheduler has been Shutdown.`; that is the watch stopping, not an error, and is not reported (a CI flake of the audit's shutdown test, reproduced by delaying the read). A job with one `ICronTrigger` is declared on its expression in the trigger's zone (a Windows id converted), its `?` written `*` and a seventh, year field of `*` or `?` left out; Quartz's days of the week count from 1 for Sunday, so each is checked with `Bridge.CheckFires` against Quartz's own `CronExpression.GetTimeAfter`, and one that differs is reported once and watched without a schedule. Quartz 4 also takes Unix five-field expressions and changed how an interval cron fires through a repeated autumn hour; the check reads whichever the installed Quartz does. A `SimpleTrigger` repeating forever is declared `every <interval>`; a calendar interval, a daily time interval, a trigger with an excluding calendar, or several triggers on one job is a job without a schedule, as the bridge has it.
- *Recovery.* In a clustered store, a job a node was running when it died is fired again on another node with `context.Recovering` true: that firing's start finishes the earlier firing's run, if it is still running, as failed with `Quartz recovered the job after its node stopped`, as the Java port's Quartz and the Elixir port's Oban rescue do, the earlier run found among the job's recent runs by this app's id prefix, another instance, and the original fire time Quartz puts in the recovering trigger's data.
- *The check.* `CronwatchCheckJob`, `[DisallowConcurrentExecution]`, scheduled once every minute (`q.UseCronwatch(o => o.ScheduleCheck = true)`), runs the sync and a check once per minute across a cluster; its runs are never a job.

The tests start a real Quartz scheduler on the RAM job store always, and on the ADO.NET job store over Postgres when `CRONWATCH_TEST_PG` is set (its tables made from Quartz's own script), with triggers that fire each second: jobs declared (a zone, a year field, a `?`, a day of the week Quartz reads differently reported, a simple trigger, a job with two triggers), a job failing twice through refires and then succeeding, a throw, a veto, `Current` inside a job through the factory, a listener after ours that throws, a job deleted at run time declared again without its schedule, the check job unscheduling a job the scheduler dropped, and a recovery on the ADO.NET store after a scheduler is shut down without waiting for its jobs.

*What phase 4 found.* Quartz.NET 4.0.0 and 4.3.0 both mark themselves trimmable and AOT compatible, so `Cronwatch.Quartz` is `IsAotCompatible`, and 4.0.0's core already carries DI and hosting (the `Quartz.Extensions.*` packages start at 4.0.1 and are not needed). Every `IJobListener` and `ISchedulerListener` member returns `ValueTask`, takes a `CancellationToken`, and has a default body, and a test fails if Quartz never calls ours. The context has no per-firing store, but one context object serves the listener, the middleware, and the job across refires, so runs are kept in a table keyed by the context and in a map keyed by fire instance id. Quartz 4 calls no listener when an attempt it refires ends; it calls `JobToBeExecuted` again with a higher `RefireCount`, so the next attempt's start closes the previous run failed, with the job's exception when the middleware saw it, else `JobExecutionException: Quartz refired the job`. A trigger's retry policy fires each retry with a new fire instance id. A job's throw arrives wrapped twice (`JobExecutionException` around `JobExecutionProcessException`) and is unwrapped to the job's own. A listener after ours that throws stops the job and is reported only as a scheduler error, a `JobExecutionProcessException` naming the firing, on which the run is given back. `Current` is set by a job execution middleware (Quartz 4 wraps each attempt in its middleware), not by a wrapping job factory: it changes nothing Quartz reads from the job's type and needs no factory; a scheduler watched with `CronwatchQuartz.WatchAsync` without the builder gets its run from `context.CronwatchRun()`. Through the builder the integration attaches when the scheduler starts, or at its first firing, and is disposed at its shutdown. A Unix five-field trigger is stored in Quartz's six-field form, so only six or seven fields are met; an interval cron such as `0 */30 * * * ?` fires in both occurrences of a repeated autumn hour, which the fire-time check allows near the change. The recovering firing's original fire time is under `QRTZ_FAILED_JOB_ORIG_TRIGGER_FIRETIME_AS_STRING`, read as epoch milliseconds or a date; Quartz refuses SQLite for a clustered store, so the recovery test runs on Postgres (`CRONWATCH_TEST_PG`) with tables Quartz provisions under a prefix of the test's own.

### Coravel

Coravel (6.0.2, last released 2025-01-17) is the third scheduler seen in .NET apps, lighter than the other two. It is not integrated: its scheduled tasks have no stable names unless the app gives each one (`PreventOverlapping("id")`), its `ScheduledEventStarted` and `ScheduledEventEnded` events are broadcast through its own dispatcher after the fact rather than in the task's flow, and an invocable's failure reaches only an `OnError` callback, so an integration would pair events by guesswork. An invocable that should be watched wraps its body in `job.RunAsync`, which the README shows, and an integration is made only if someone asks (see Decisions, 15).

## Keeping in step

`conformance/` at the repo root holds JSON cases generated from the TypeScript build by `scripts/conformance.mjs`. The .NET tests replay every case, comparing values as the JSON the SDK writes, byte for byte, reading the files from the repository (their directory found by walking up from the test assembly to the repository's root; no package carries them): `duration.json` (103 cases at 0.8.0: parse 68, format 26, relative 9) and `schedule.json` (723: parse 62, fires 64, nextFire 4, expectation 572, runCovers 13, autumn 8) against the duration and schedule code, `output.json` (231: 204 redactions, 16 error messages, and 11 expect texts, with the cap) against the output code, `evaluate.json` (50 scenarios, every event played through the pure functions, as the script's `Sim` plays them), `format.json` (104: 32 alerts, 38 numbers, 14 caps, 7 definitions, 13 expect checks) and `health.json` (145) in the core, `store.json` (prune 3, compareAndSetState 11, updateRunIf 8, 16 foreign versions, and 6 `nul` steps) against every store, `channels.json` (every section) against the channels, `triage.json` (24) against triage, and `pgcron.json` (29 and the hold) against the source. A test fails when the SDK writes a fixture file this port does not know. The tests run in UTC: on Linux and macOS the test project sets `TZ=UTC` for the test host, and on Windows, where `TimeZoneInfo.Local` ignores `TZ`, every client in the tests is given a `TimeProvider` whose local zone is UTC, and a test checks the zone the fixtures were read in. A behaviour change lands in TypeScript first, `npm run conformance` regenerates the fixtures, and this solution is fixed until they pass. Nothing new is expected in the fixtures for this port: the PHP and Go ports already added what a port without the official clients needs (`triage.json`'s `wire` cases).

The foreign-row fixes every port took at 0.8.0 are part of phase 1, not findings for its audit: `RunDuration` held from 0 to 2^53 - 1; `StateVersion` counting a version that is not a whole number as 0, in the client, the memory store, and the SQL of every dialect; a time before the year 1 or after 9999 written in words wherever the SDK would write a date (`before 0001-01-01 00:00:00 UTC`, `after 9999-12-31 23:59:59 UTC`, on the timeline `before 1 Jan 0001 00:00` and `after 31 Dec 9999 23:59`, a date in another year with its year), with no relative part, and a tracker's `startedAt` as `null`, since `toISOString` throws for such a date and .NET's `DateTime` cannot hold one; and a cron that counts from a start before the year 1 as from the year's first millisecond, finds no fire after 9999, and asks croner's walk only within the years it answers for, moving a time outside 400 to 2800 by whole 400-year cycles of 146,097 days (a whole number of weeks, so dates and weekdays repeat) and moving the fires back, as `schedule.ts`'s `runsAfter` does. `health.json`, `store.json`'s `foreignVersion` and `nul`, `format.json`, `channels.json`, `triage.json`, `schedule.json`, `evaluate.json`, and the golden seed hold every case.

Croner parity is also checked against croner itself, as the other ports do: 3,000 expressions from three fixed seeds in zones with and without daylight saving, from times around the clock changes, where the SDK in Node (reading `packages/sdk/dist`) must give the same error message or the same fire times; it skips, with the reason, when `node` or the built SDK is missing. The same generator run against Cronos, Quartz.NET's `CronExpression`, and NCrontab is a report, not a gate, skipped unless asked for, so the reason for porting rather than depending stays measured, as the Java port's report on Spring, Quartz, and cron-utils does: `ReadingsReportTests` in `Cronwatch.Quartz.Tests` (the Cronos Hangfire carries, 0.11.1, and NCrontab 3.4.0 test dependencies there), skipped unless `CRONWATCH_READINGS=1`, checks the Java report's 40 generated expressions with a seconds field (seed 20260929, in UTC, America/New_York, Europe/London, and Australia/Lord_Howe) with `SchedulerBridge.CheckFires`, as the integrations check a declared job. At phase 5: Cronos reads 18 as croner does (22 name a day of the month and a day of the week both, which Cronos requires to match together and croner either); Quartz.NET 4.3.0 16 (given `?` where the other day field is `*`, as the integration declares it: 16 name both day fields, which Quartz.NET 4 takes and matches its own way, 5 name a day of the week by number, which Quartz counts from 1 for Sunday, and 3 are refused for a day of the week 0); NCrontab 17 (22 both day fields, and `0 */4 * * 10 *` in Australia/Lord_Howe, whose clocks go forward half an hour at 02:00: croner and Cronos fire at 02:30, and NCrontab, which has no zones and is given the zone's wall clock, next fires at 02:32, the report passing over the times the change skips as an app would). Where the Java report found every library reading the Lord Howe change otherwise, Cronos reads it as croner does.

*Why port croner rather than use a .NET cron library.* Three were weighed. Cronos is what Hangfire uses and the best of them on time zones, but it matches a day of the month and a day of the week its own way, reads `L`, `W`, and `#` as Quartz does, and has its own messages. NCrontab is the oldest and most downloaded, reads five fields (six with an option), has no zones at all, and has its own messages. Quartz.NET's `CronExpression` requires seconds and a `?`, counts the days of the week from Sunday as 1, has a year field, and lives in a scheduler no plain app should take for a parser. CronWatch needs the SDK's messages and fire times byte for byte, which six ports already get from a line-for-line translation checked against croner itself; the Java port's `internal/cron` is the nearest code to start from, and C#'s `long`, `Math.DivRem`, and `checked` arithmetic make it nearly a transliteration.

## Testing and CI

`dotnet test` in `packages/dotnet` is the whole suite; the Postgres, MySQL, MariaDB, and pg_cron tests run when their `CRONWATCH_TEST_*` variables are set, as the other ports' do. The tests are xUnit v3 (the `xunit.v3` package) on the Microsoft Testing Platform runner, the framework most .NET libraries and .NET itself test with; the test projects target `net10.0` and the newest .NET, so the suite runs on both while the packages target `net10.0` alone. The client, store, handle, finish-once, and routes tests are the SDK's, ported, as the Go, Rust, Elixir, and Java ports ported them.

- *No tight wall-clock tests.* The SDK's fake clocks are `FakeTimeProvider` (`Microsoft.Extensions.TimeProvider.Testing`), given as the client's `Clock`: every timer the client arms (a job's timeout, the interval, a channel's deadline, the retry budget, the process-exit hook's five seconds) comes from its `TimeProvider`, so a test advances the clock and asserts, and no test sleeps and hopes. Where a real timer must run (a socket deadline in the hardening suite, a scheduler firing each second in the integrations' tests), the assertion waits for an outcome with a generous bound, never for an elapsed time within a narrow window, the lesson of every port's flaky CI runs.
- *Culture and line endings.* The suite runs twice in CI, once under the invariant culture and once with `CurrentCulture` and `CurrentUICulture` set to `tr-TR` for the whole test assembly, so a format or comparison that reads the culture fails a byte-for-byte replay. Child processes' output is read with `\r\n` taken as `\n`, since a program's `Console.Out` on Windows may end lines either way, the Java port's Windows lesson; the library itself writes `\n`.
- *Properties.* The fuzz targets of the Rust port are property tests here, seeded xUnit tests over a small generator of the tests' own (`Gen`), which names the seed of a failing case, as the Java port's are (its Decision 24): `Js.Parse` and `Stringify` round trips, duration text through the public options, a cron expression in nine zones and its fire times each later than the last, a stored pattern run by the engine as a test and as a replacement within its budget, a request to the dashboard in five configurations (the routes catch a throw and answer 500, which the property counts as a failure), and stored rows read, written, and read back. They run a few hundred tries each in `dotnet test`, and `CRONWATCH_TRIES=N` multiplies them for a longer run, which `fuzz.yml` makes once a week beside the Rust and Java targets. FsCheck and CsCheck were weighed: FsCheck brings F#'s core library, and neither names a seed more usefully than a generator of forty lines.
- *Static analysis.* The .NET SDK's own analyzers at `<AnalysisLevel>latest-recommended</AnalysisLevel>` with `EnforceCodeStyleInBuild`, warnings as errors, and the rules this port cannot do without raised to errors by name in `.editorconfig`: the culture rules above, CA2007 (`ConfigureAwait`), CA2016 (forward the `CancellationToken`), CA2012 (`ValueTask` used once), CA1849 (no blocking call in an async method), CA5359 and CA5398 (certificate validation and TLS versions), CA2000 (dispose), and the trimming and AOT analyzers `IsAotCompatible` turns on. `Microsoft.CodeAnalysis.PublicApiAnalyzers` (a build-time analyzer, never a dependency an app sees) keeps `PublicAPI.Shipped.txt` and `PublicAPI.Unshipped.txt` beside each package, so anything added to or taken from the public surface is a line in the diff, the counterpart of the Java port's module exports and javadoc; package validation (`EnablePackageValidation`, with the last release as its baseline once there is one) refuses a release that breaks the previous one's API unless the change is written down. `dotnet format --verify-no-changes` checks the formatting against `.editorconfig`. ## Releasing

NuGet has trusted publishing: nuget.org added it in 2025, and its documentation (updated 2026-09-01) describes it for GitHub Actions and GitLab. The owner adds a trusted publishing policy on nuget.org (the account menu, Trusted Publishing) with the repository owner `cronwatchdev`, the repository `cronwatch`, the workflow file `nuget.yml` (the file name only), and the environment `nuget`; its scope allows pushing new packages and new versions of packages matching `Cronwatch*`. In the workflow, `NuGet/login` (pinned by commit) exchanges the job's GitHub OIDC token (the job needs `id-token: write`) for a nuget.org API key that lives one hour, given the nuget.org profile name (not the email address) as `user`, which the workflow reads from the environment's variable `NUGET_USER`; each OIDC token buys one key. No API key is stored anywhere. A policy for a private repository is only temporarily active for seven days until a first publish through it gives nuget.org the repository's and owner's GitHub ids, after which it is permanent; for a public repository it is active at once.

Publishing is `.github/workflows/nuget.yml`, on a pushed `v*` tag or by hand for a tag, off until the repository variable `NUGET_ENABLED` is `true`, as `pypi.yml`, `crates.yml`, and `hex.yml` are, in two jobs so the owner sees what will be published before it is:

- `pack`, with no secrets and no environment: checks that `<Version>` is the tag's (after `ci-passed.yml` has waited for the tag's CI on main to pass), sets up the .NET SDK, runs `dotnet pack -c Release` on the solution, checks each package's file list as CI does, and uploads the five `.nupkg` files as the run's artifact.
- `publish`, needing `pack`, in the environment `nuget` with required reviewers: the owner opens the artifact, looks, and approves. It downloads the artifact, logs in with `NuGet/login`, and pushes with `dotnet nuget push *.nupkg --skip-duplicate`. NuGet has no atomic multi-package publish: each package is pushed on its own and appears once nuget.org has validated and indexed it, usually within minutes. The core is pushed first, then `Cronwatch.Hosting`, then the rest, so no package is listed before one it needs; `--skip-duplicate` makes a run started again after a partial failure push only what is missing.

Packages are not author-signed. nuget.org repository-signs every package it accepts, which is what `dotnet nuget verify` and NuGet's own trust checks read; an author signature needs a code-signing certificate from a certificate authority NuGet trusts, bought and renewed every year or so and held as a secret, for a mark few apps check, so it waits until someone asks. The owner's nuget.org account needs two-factor sign-in, which nuget.org asks of every account that publishes.

The first release is published from CI too, by trusted publishing, unlike the Java port's first publish by hand: the policy's scope allows a new package, the `pack` job's artifact is the review the Central Portal's staging gave the Java port, and a push by hand would need a long-lived API key made for the one push and revoked after. Before the first run: the prefix reservation is asked for (see Package IDs and releases), the policy is added on nuget.org, the environment `nuget` with its reviewers and the variable `NUGET_USER` are made here, and `NUGET_ENABLED` is set to `true`, as `nuget.yml`'s opening comment lists. If trusted publishing is not available to the account when the time comes, the fallback is an API key made on nuget.org scoped to push only, only to `Cronwatch*` packages, expiring in a year, kept as the `nuget` environment's secret `NUGET_API_KEY`, never the repository's, and revoked once trusted publishing works. A version pushed cannot be deleted, only unlisted or deprecated, so nothing is pushed before phase 1 works.

## Where it cannot match the SDK

What is known before any code, mostly shared with the Go, Rust, Elixir, and Java ports; phase 5 completes the list.

- A bad zone is refused when the expression is read rather than when a fire time is asked for, as the other ports do. (A date no month has, `0 0 30 2 *`, never fires, and a one-time date is refused, `CronPattern: a one-time date is not supported`, as the SDK now settles both: see the schedules page.)
- Zones come from the system through `TimeZoneInfo`, where Node's come with its ICU: on Linux and macOS as new as the system's `tzdata`, and on Windows the registry's rules, which keep less history; a zone that changed its rules recently or long ago can differ. A system with no zone database (a chiseled container image without `tzdata`, Windows with `InvariantGlobalization`) has no named zones at all, and a job naming one is refused. Without a `Timezone`, a cron is read in the client's `TimeProvider.LocalTimeZone`; on Windows `TZ` does not set it.
- `TimeZoneInfo` holds every UTC offset to whole minutes, so a zone's local mean time before it took standard time (New York's -4:56:02 before 1883, Amsterdam's +0:19:32 to 1937) is rounded, and a fire time from those years can differ from Node's by under a minute; only a foreign row's far start meets it. On Windows, historic offsets before a zone's first rule follow the OS's data, not the IANA history: the registry's rules for a zone begin with its current standard offset, so New York in 1800 is -5:00 there (checked on the `dotnet-platforms` CI entry), and no setting of .NET's gives `TimeZoneInfo` the IANA rules on Windows (ICU maps the name to a Windows zone and nothing more; `TZDIR` is read only on Linux and macOS). Offsets for instants outside `DateTimeOffset`'s years 1 to 9999 are taken at the nearer end, which croner is asked about only in UTC, the 400-year shift doing the rest.
- Error names are .NET's simple type names and frames are .NET's (`Example.Reports.BuildAsync (Reports.cs:42)`, the async state machine written as its method), not JavaScript's classes; inner exceptions are not written. Under Native AOT or without PDBs, frames have no file or line.
- .NET cannot stop a running function; the run's token asks it to stop, and a function that ignores it runs on and is marked stuck by a check, as in the SDK. A run open when the process stops is recorded failed by the process-exit hook, where the SDK records nothing; a process killed outright or ended by a `StackOverflowException` records nothing, as a killed Node process does.
- A value logged is a `string`; `JobContext.Log` takes one, which the app formats (an interpolated string), where `console.log` joins its arguments and writes objects as JSON.
- A `Dictionary` handed in whole where the SDK keeps an object's order (a `Budget` or `Floor`, metrics given at once) is written in its enumeration order; the collection initializers and the ordered types keep the order given.
- `ConsoleChannel` writes to standard output and error as the SDK's does, but with `Cronwatch.Hosting` the error handler writes through `ILogger`, so its line carries the app's logging format.
- The default transport sends no `User-Agent` where fetch sends its own, triage sends `cronwatch-dotnet/<version>`, and `HttpClient` writes `Host` first, content headers after request headers, and `Content-Length` itself, where fetch keeps the order given; the tests pin what .NET sends.
- A request that gets no answer fails with `<origin>: <the exception's simple name and message>` (`HttpRequestException: Connection refused`), in place of fetch's `fetch failed`; a redirect is an answer outside 2xx (`... answered 307`), where fetch with `redirect: "error"` throws; either way nothing is sent where it points. An answer's head is held to 64 KiB.
- A webhook URL whose host is outside ASCII is refused as `not this URL`, since .NET's IDN mapping is not WHATWG's. A host with an underscore is accepted, since `Uri` and WHATWG read it alike, where the Java port refuses it.
- A header name .NET knows goes out in its own casing (`Authorization`, `Content-Type`), where fetch sends names lowercased; header names are not case sensitive.
- A channel's time past what a JavaScript `Date` holds (8.64e15 ms either side of 1970) fails the send with `Invalid time value`, the message of the `RangeError` JavaScript throws.
- A body past 1 MiB is answered 413 (a sign-in's reads as no token, and is answered the sign-in page again); the SDK leaves the limit to the server in front of it. A form something ahead of the dashboard already read is taken from ASP.NET Core's parsed form, which is the same answer for every body the dashboard's pages and `@cronwatch/mcp` send.
- Through Kestrel, the answer's headers are written in Kestrel's order and its casing for the headers it knows, with its `Date` and `Server`, and a `Host` Kestrel will not accept is refused with its own 400 before the routes see it; straight into `Routes.HandleAsync` the answer is the SDK's, header for header.
- An interval longer than 2^53 ms is held at 2^53 ms, since state times are `long`s, as in the other typed ports. An alert's time is a whole millisecond, so a foreign alert whose `at` has a fraction is read as the millisecond it falls in, and its retry key names that millisecond. A `sending` entry is read as its lease's end, a fraction rounded up, and its alert; one that is not an object, or whose alert is not one, is kept without the part it lacks until the next check lets it go, where the SDK keeps such an entry as it was.
- The dashboard's locked page and a handler's 503 name the .NET API (`RoutesOptions.Token`, `DashboardToken.None`, `HandlerSecret.None`, and the `Cronwatch:Token` configuration key), where the SDK names its options.
- A run failed by an HTTP answer names the status's reason (`HTTP 503 Service Unavailable`), from the answer's `ReasonPhrase` or RFC 9110's table, where a `Response` the SDK's function builds itself has none (`HTTP 503`).
- JSON nested more than 256 deep is refused, a request body so nested reads as none, and a stored value so nested fails its row's read; a stored `matches /.../` pattern that recurses past 512 frames or runs out of its budget does not match, and one of more than 4096 characters or with groups nested more than 100 deep is not read. These are the Rust port's bounds, kept for the same answers.
- A job given `Expect.That` with a different predicate is not declared again by a source (both store `custom function`); the SDK compares the function's source text.
- `DisposeAsync` waits for a check under way to end, as the SDK's `close()` does, then up to five seconds for the other sends and recordings in flight (a run's alert, its triage), and cancels what is left, where the SDK's `close()` waits for those whole. Called from the check's own flow (a source, a channel, or an error handler that disposes the client), it does not wait for that check.
- On SQLite the statements number their parameters `?1`, `?2` and on Postgres a JSON parameter is cast `$n::jsonb`, where `sql.ts` writes `?` and binds untyped; the schema and every stored byte are the SDK's.
- The SDK has no scheduler integrations, no hosted jobs, no `deleteRunIf`, no telemetry, and no process-exit hook.

## Decisions

The owner settled the draft's open questions before phase 1, taking each recommendation:

1. **The package IDs** are `Cronwatch`, `Cronwatch.Hosting`, `Cronwatch.AspNetCore`, `Cronwatch.Hangfire`, and `Cronwatch.Quartz`, cased `Cronwatch` to match the namespace and every other port; the owner asks `account@nuget.org` for the private prefixes `Cronwatch` and `Cronwatch.*`, so no placeholder is published. The fallback, if the prefix is refused and `Cronwatch` is taken meanwhile, is `Cronwatch.Sdk` and packages beneath it, the namespace unchanged.
2. **The floor is `net10.0` alone**, tested on 10 and the newest release; the floor moves to 12 only when 10 leaves support.
3. **The client is `CronwatchClient`** in the namespace `Cronwatch`.
4. **DI and ASP.NET Core live in packages of their own**: the core depends on nothing, `Cronwatch.Hosting` on the `Microsoft.Extensions.*` abstractions, and `Cronwatch.AspNetCore` on the shared framework's `Microsoft.AspNetCore.App`.
5. **`SqlStore` is in the core**, over `System.Data.Common`'s `DbDataSource`, with no driver package of its own and the drivers as test dependencies; Postgres's JSON parameters are cast `$n::jsonb` and SQLite's parameters numbered `?1`, the schema untouched.
6. **Zones are `TimeZoneInfo`**, with the port's own list of IANA names for matching without regard to case, and Windows' registry rules accepted as a difference for years long past; NodaTime or an embedded database only if someone meets a difference that matters now.
7. **One async API**: `Task` and `Task<T>` for everything that touches the store or the network, `CancellationToken` last, no blocking `Run` beside `RunAsync`, `ValueTask` only for `DisposeAsync`.
8. **A cancelled run is the SDK's**: a function that throws when its token is cancelled at the timeout is a failed run with what it threw, the ordinary failure alert; one that runs on is marked stuck by a check.
9. **The process-exit hook is on by default**, marking runs still open in this process failed within five seconds through the conditional write, removed at `DisposeAsync`, off with `ProcessExitHook = false`.
10. **The environment** is `CRONWATCH_ENV`, then `APP_ENV`, then the environment the app gave, then `ASPNETCORE_ENVIRONMENT` and `DOTNET_ENVIRONMENT`, in ASP.NET Core's order, lowercased; in `Cronwatch.Hosting`, the one given is the host's `IHostEnvironment.EnvironmentName` (see 45). An unset environment is not development.
11. **`MapCronwatch` endpoints are anonymous to the app's authorization while the dashboard has a token**, without antiforgery and left out of OpenAPI; an open dashboard (`Open = true`) takes the app's policy.
12. **Hangfire** is built in phase 4 for Hangfire 1.8.0 or newer, as the draft describes it.
13. **`Cronwatch.Quartz` is for Quartz.NET 4**; Quartz 3 only as `Cronwatch.Quartz3`, if someone asks, and phase 4 builds for 3 first if 4 has not settled.
14. **Hosted jobs**: `AddCronwatchJob<T>` in `Cronwatch.Hosting` in phase 4, a scheduler for one process.
15. **Coravel is not integrated**; the README shows an invocable wrapping its body in `job.RunAsync`.
16. **A command line**: `CronwatchCli.RunAsync(factory, args, ...)` in the core and `RunCronwatchCommandAsync(args)` in `Cronwatch.Hosting`; no `dotnet tool` of the library's own.
17. **Telemetry**: an `ActivitySource` and a `Meter` named `Cronwatch` in the core, and log scopes through `Cronwatch.Hosting`.
18. **The step budget** is the Rust and Java ports' 50 million steps with the same fail rule, and the 512 frames, 4096 characters, 100 groups, and 256 JSON levels. Phase 1 measured an exhausted budget on .NET 10 (SDK 10.0.401, a Release build, an Apple M-series machine), three rounds over 32,000 characters each: `\n*\n*\n*\n*\n*x` gave up in 128 to 308 ms, `.*x` in 167 to 250 ms, `(?:a|b)*x` in 171 to 185 ms, and `(?:a+a+)+x` in 143 to 239 ms, far under the two seconds that would have lowered it, so it stands. A test that runs a pattern to its budget holds it to a generous bound, not a measurement.
19. **Publishing**: trusted publishing from `nuget.yml` from the first release, a `pack` job the owner reviews and a `publish` job in the `nuget` environment with required reviewers, off until `NUGET_ENABLED` is `true`; pushes ordered core first with `--skip-duplicate`; no author signing. `scripts/release.mjs` prints the push by hand beside it, as the fallback.
20. **Static analysis**: the SDK's analyzers at `latest-recommended` with warnings as errors and the culture, async, cancellation, and TLS rules raised by name in `.editorconfig`, the trimming and AOT analyzers, and `dotnet format`; not StyleCop or SonarAnalyzer. (`PublicApiAnalyzers` and package validation: see 34.)
21. **Tests** are xUnit v3 on the Microsoft Testing Platform (`xunit.v3.mtp-v2`), `FakeTimeProvider` for every clock and timer, the suite run a second time under `tr-TR`, and the properties as seeded tests over generators of the tests' own.

Phase 1 settled these, which the draft left open:

22. **Everything internal is in one namespace, `Cronwatch.Internal`**, the folders under `Internal/` only arranging the files, so no class is named as a namespace it sits in (`Cronwatch.Internal.Output.Output`) and no namespace hides a type.
23. **`JsObject`, `Json`, and `JsonParseException` are public in `Cronwatch`** (the exception named apart from `System.Text.Json.JsonException` in phase 5), as the Java port made its `json` package public (its Decision 23): a state's `Extra`, a definition's fields, and `JobOptions.Field` hand JSON values out and take them in. The number writer, the date arithmetic, and the rest of `Js` stay internal. `ValueList<T>` and `ValueMap<TKey, TValue>` are public too: the records' lists and maps, immutable and compared by content, so a record's value equality holds (`ImmutableArray<T>` compares by reference).
24. **Warnings have a handler of their own**, `OnWarning` (by default a line to standard error), beside `OnError`: the in-memory store in production and `Start()` with `Deliver.AtCheck` are not failures, and the SDK writes them with `console.warn`, not through `onError`.
25. **The PDB is embedded in the assembly, and there is no symbols package**: `dotnet pack` refuses a `.snupkg` with nothing in it (NU5017), and an embedded PDB serves SourceLink and a debugger without a second push.
26. **CI runs on .NET 10 alone until .NET 11 is released** (November 2026), when the test project gains the `net11.0` target and the job a second entry.
27. **The pure evaluation reads the client's local zone from the calling thread**: a cron without a zone is read in the client's `TimeProvider.LocalTimeZone`, which `Evaluate` does not carry, so the client runs each evaluation synchronously inside `EvaluateDeps.InZone`, which holds the zone on the thread for that call only.
28. **Case folding in the engine comes from a table of Node's own answers** (`scripts/canonical.mjs` writes `JsreCanonicalTable.cs`, 184 runs), since .NET's invariant case mapping is not JavaScript's Canonicalize (U+1F80, for one).
29. **Frames are read through `DiagnosticMethodInfo.Create(StackFrame)`** (.NET 9 and newer), which trimming and Native AOT keep without warnings, where `StackFrame.GetMethod()` would warn; a frame names its file, never the build machine's path. Runtime plumbing is left out by type name (`System.Runtime.CompilerServices.`, `System.Runtime.ExceptionServices.`, `System.Threading.Tasks.`, `System.Threading.ExecutionContext`).
30. **The zone list** is written by `scripts/zones.mjs` from a `tzdata.zi` (the system's by default), keeping the names Node's `Intl` accepts: 597 from tzdata 2026c on Node 24.14.1.
31. **The tests run in UTC through a module initializer** that sets `TZ=UTC` and clears `TimeZoneInfo`'s cache before any test, and every replay that reads the local zone names UTC itself, so Windows, where `TZ` is not read, agrees; `CRONWATCH_CULTURE=tr-TR` makes the second run's culture every thread's.
32. **`Alerts` sends to the console until it is touched**: channels added by a collection initializer replace the console, and `Alerts = []` sends nowhere, as the SDK's `alerts: []` does.
33. **MySQL and MariaDB waited for phase 2**, which added `SqlStore.MySql` and taught `SqlStore.For` the `MySqlConnection` of MySqlConnector (which serves MariaDB too); `SqlStore.Postgres`'s statements, numbered and cast, ran against a server there unchanged.
34. **`PublicApiAnalyzers` waited for the first release, and came with the audit**: phase 5 added it (5.6.0, build-time only), each package's surface in `PublicAPI.Unshipped.txt` and `PublicAPI.Shipped.txt` empty until the first release moves it across, RS0026 and RS0027 off since every async overload takes an optional `CancellationToken` last. Package validation waits for the first release, when there is a baseline to hold a release against.
35. **`RunOptions.DiscardWhen` and `MayTakeBack` are in phase 1**, since the draft's API names them and a run given back is a rule of the runs, not of an integration; `OpenAsync` and `ObservedRun` wait for phase 4.

Phase 2 settled these:

36. **The transport is `ITransport` in `Cronwatch.Alerts`**, one method, `PostAsync(TransportRequest, CancellationToken)`, answering a `TransportResponse` of a status and a body `Stream` that `Post` reads a chunk at a time and disposes; `CronwatchOptions.Transport` sets the client's, each channel's and triage's options take one of their own, and `ChannelContext.Transport` and `TriageContext.Transport` hand the client's to them. A context made without a client's uses one `HttpClientTransport` shared by the process. `Post` shortens its deadline only through an internal setting, and the hardening tests pass a short deadline to the call itself, so no test changes a global another reads.
37. **The EF Core rollback is tested as a `DbTransaction` on the app's own connection**, which is what an EF Core transaction is, rather than with EF Core as a test dependency; the `TransactionScope` test enlists a real connection of the app's and shows its write rolled back while the run stays.
38. **A lone surrogate in a JSON key or string** is written by `Js.Stringify` as the escape `\ud83d`, as `JSON.stringify` writes it; Postgres's `jsonb` refuses that escape, so such a write fails on Postgres as the SDK's does, and MySQL and SQLite keep it. `WellFormed` binding covers text columns only.
39. **Channels are `<Name>Channel` classes made from `<Name>Options`**, with static `SlackChannel.Webhook` and `DiscordChannel.Webhook` (see Decisions, 65); every options class takes `Link` (`Func<Alert, string?>`) and `Transport`; `To` and Datadog's `Tags` are `IList<string>` for collection initializers; the webhook's headers are ordered pairs, a name given again keeping its first place and its last value; New Relic's `AccountId` is a string; SES and Bugsnag read the time from a `Clock` option (a `TimeProvider`) where the SDK takes a `now` function; Twilio's `Segments` is 3 when unset and held to 1 to 10. An email link counts as http or https by comparing ASCII letters only, as `/^https?:\/\//i` does.
40. **Triage reads its environment through a seam**: `AnthropicTriage` reads `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL` through `Env` each time it runs, and an internal constructor takes the reader, so no test changes the process environment. A missing key is `Anthropic triage needs an ApiKey, or ANTHROPIC_API_KEY set`. `ApiKey`, `Context`, and `BaseUrl` are never printed (a gateway's URL can carry a credential); `DefaultModel`, `DefaultEffort`, `DefaultMaxTokens`, and `FallbackBeta` are public constants, as in the Java port.
41. **pg_cron's options** are `PgCronOptions`: the SDK's `options`, an object or a function, is two properties, `Options` and `OptionsFor`, refused together (`PgCronOptions: give Options or OptionsFor, not both`), as `Pick` is beside `Jobs` or `JobIds`; options that set a schedule or timezone are refused, and from `OptionsFor` that job is reported and not declared, as in Java. The SDK's helpers are statics on `PgCronSource` (`ToSchedule`, `DefaultJobName`, `ToRun`, `HoldMs`), since a class `Cronwatch.PgCron.PgCron` would be named as its namespace. `Timezone` unset reads `cron.timezone` from `pg_settings`, else UTC with one warning. Npgsql hands `timestamptz` over as a `DateTime`, floored to whole milliseconds. The query layer is an internal delegate, so the tests' fake `cron` schema needs no public interface, and syncs take turns on the core's own async queue.

Phase 3 settled these:

42. **The web types are in the namespace `Cronwatch.Web`**: `Routes`, `RoutesOptions`, `DashboardToken`, `Handler`, `HandlerOptions`, `HandlerSecret`, `CronwatchRequest`, `CronwatchResponse`, `WebBodyReader`, `WebBodyTooLargeException`, and `Adapters`, beside `cw.Routes(options)` and `job.Handler(fn, options)` in `Cronwatch`. The token and the handler's secret are `DashboardToken` and `HandlerSecret`, converted from a string, with `None` for the SDK's `null`, as `CronSecret` is. A `CronwatchRequest`'s target and headers have an `init` accessor and an `internal get`, read through `Header(name)` and `Path`, and `Routes.Token()`, the token in use, is a method, so the secret walk finds no getter holding one.
43. **A handler's function is `Func<JobContext, CronwatchRequest, CancellationToken, Task>` or `Task<T>`**, the request's token linked into the run's. A `CronwatchResponse` it returns is the answer and fails the run at 400 or more (`HttpFailure` reads its status); on ASP.NET Core the function takes the `HttpContext`, and an `IResult` it returns travels as `CronwatchResponse.Carrying(result, status)` and is executed by the adapter, its `IStatusCodeHttpResult` status judging the run. The handler's secret is the client's cron secret as the client read it when it was made, as the SDK reads `cronSecret` once, not on each request. `MapCronwatchHandler` takes the job or its name, the name found through `cw.DeclaredJob(name)`, which answers null for a job not declared here.
44. **`AddCronwatch` takes `CronwatchHostOptions`**, a mutable class of the client's options set in a callback (`AddCronwatch(o => ...)` or `AddCronwatch((services, o) => ...)`), since `CronwatchOptions` is init-only and its secrets cannot be read back from another assembly to be copied. The `Cronwatch` configuration section is read by hand (`Retention`, `Token`, `CheckEvery`, `Environment`), not by the binder's source generator: four strings need no generator and the package stays trimmable. Channels are the options' once `Alerts` is touched (a channel added, the list cleared, or set, even to `[]`, which sends nowhere, as the core's `Alerts = []` does; phase 5's fix), else every `IChannel` in the container, else the console. It registers the options, the client, and a `RoutesOptions` holding the configured token, which `MapCronwatch` and `UseCronwatch` take when given none. `NoCheck = true` runs no hosted check.
45. **The environment in a host** is CronWatch's own two variables first, then the options' `Environment` (from code or `Cronwatch:Environment`), then the host's `IHostEnvironment.EnvironmentName`, handed to the client as its `Environment`, which outranks .NET's two variables: the host has read them already, and a stale one must not turn a host run with `--environment Production` into development, where a handler without a secret runs for anyone, which a review found.
46. **The golden seed sets the clock where no `DateTimeOffset` can**: two of its runs start before the year 1 and one after 9999, which a `TimeProvider` cannot report. The client reads now through an internal `Timings.Now` when it is set (the SDK's `now` option, which the Java port has as `clock`), and `Cronwatch.WebTest` is the one assembly besides the tests the core's internals are visible to. The public API keeps `Clock`, a `TimeProvider`.
47. **The dashboard's origin reader is `Internal/Web/Origins`**, which phase 3 carried over from the Java port with punycode and IP readers of its own beside phase 2's `WhatwgUrl` for the channels. Phase 5 put it on `WhatwgUrl`: `WhatwgUrl.Parse(value, idn: true)` lowercases a host outside ASCII and writes each such label in punycode (RFC 3492, up to 1024 bytes of host) where the channels refuse one, and `Origins` keeps only the option's messages, `Bare`, `OfRequest`, `IsLoopback`, and the punycode encoder, so the IPv4 and IPv6 readers are one. Both readers read all 904 texts of `channels.json`'s `urls` as Node does (the origin option as the SDK's `configuredOrigin`); the merge changed two answers, each now the SDK's: a forwarded host whose dot segments resolve to `/` (`app.example/.`) is a host, as `new URL` resolves it before the SDK tests the path, and an origin option of another special scheme that is no URL (`ws://[`) is refused as no URL, not as another scheme.
48. **The body reader** reads at most 1 MiB and one byte through an `ArrayBufferWriter`, and a body that reads back empty when ASP.NET Core's `IFormFeature` already holds a parsed form (something ahead called `ReadFormAsync` or `Request.Form`) is written back from that form with `Adapters.FormBody`. A request whose `RequestAborted` is cancelled ends without a report, and a failed write of the answer after the client went away is dropped.
49. **Not in phase 3**: the log scope with `cronwatch_job` and `cronwatch_run`, which phase 4's `CronwatchOptions.RunScope` hook is for and `AddCronwatch` sets once both are merged; and `examples/aot`, which waits for phase 4's examples.

Phase 4 settled these:

50. **The bridge's static class is `SchedulerBridge`**, in the namespace `Cronwatch.Bridge` beside `Watch`, `Entry`, `FireTimes` (a delegate; `SchedulerBridge.Walking` makes one from a next-fire function), and `ScheduleException`, since a type named as its namespace makes every caller write `Cronwatch.Bridge.Bridge`. `Watch` is async where it touches the store (`SettleAsync`, `FallbackAsync`, `UnscheduleAsync`) and holds its declaring lock, a `System.Threading.Lock`, only across synchronous code; `Declare` stays synchronous and writes through a task of its own, each write held to 30 seconds. `Entry` copies the options it is given.
51. **A fire-time check is kept in `FireTimeChecks`**, in the bridge rather than in each integration: by job, expression, zone, and UTC year, with `EndRead` dropping what the last read did not ask about, so a cron is walked once a year per process. The check finds a zone's clock changes by walking its offsets an hour at a time and each change to the second, since `TimeZoneInfo` lists no transitions.
52. **`CronwatchOptions.RunScope`** (`Func<JobContext, IDisposable?>`) is called in the run's flow as each function starts and disposed as it ends, and by `ObservedRun.MakeCurrent()`; a throw is reported as `run scope for <job>`. `AddCronwatch` sets it to an `ILogger` scope of `cronwatch_job` and `cronwatch_run`, written `cronwatch_job=nightly cronwatch_run=...` by a logger that prints scopes.
53. **An `ObservedRun` closed again answers the run as the first close recorded it**, or as it was opened when it was given back; its activity starts in `OpenAsync` (the caller's current activity its parent) and is made current by `MakeCurrent`.
54. **`Job.NextFire(after, lastRunAt)` and `CronwatchClient.Clock` are public**, for `AddCronwatchJob` and any scheduler of the app's own that runs a job on the schedule CronWatch watches.
55. **`RunCronwatchCommandAsync` disposes the host** after a `cronwatch` command, having built nothing but the client from its container, and `CronwatchCli.RunAsync` takes an `IReadOnlyList<string>` and the writers, so an app passes `args[1..]`; neither ends the process.
56. **Each integration package asks for its floor**: `Hangfire.Core` 1.8.0 and `Quartz` 4.0.0 in the packages' dependencies, while the tests override to the release under test (1.8.25 and 4.3.0 by default), so a package built for the tests never raises an app's floor.
57. **`Cronwatch.Hangfire` records a job that never loaded during state election** (`IElectStateFilter`), not when the state is applied, since `AutomaticRetry` turns that failure into a retry first; and **`Cronwatch.Quartz` sets `Current` with a job execution middleware**, not a wrapping job factory. Both integrations merge their job defaults with a job's own options through the public `Describe` and `Field`, as an integration of the app's own would.

Phase 5 settled these:

58. **A Hangfire attempt is counted by the integration**, in the job parameter `CronwatchAttempt` (`CronwatchHangfire.AttemptParameter`), from 0, and a run's id is `hangfire:<app>:<job id>:<attempt>`; retries count 0, 1, 2 as before, and a requeue from Hangfire's dashboard or a fetch after a dead worker is a new attempt, where Hangfire's own `RetryCount` is not. One integration watches Hangfire per process, since its filters are the process's.
59. **An endpoint is anonymous to the app's authorization only while a secret guards it**: `MapCronwatch` while the dashboard has a token (Decision 11), `MapCronwatchHandler` while the handler has a secret (`Handler.IsOpen` false). Anything open takes the app's policy.
60. **The public names that clash with the framework's are changed in 0.11**: `CustomChannel.Create` for a channel from a lambda and `JsonParseException` for a JSON value that is not the record it was read as, since `Channel` and `JsonException` are in `System.Threading.Channels` and `System.Text.Json`, which an ASP.NET Core app imports beside `Cronwatch`. The other names the audit weighed are left to the owner (see Phases, 5).
61. **Names changed in 0.11 keep their old spelling as a deprecated alias** (the 1.0 plan, D11): the packages have been on NuGet since 0.9.0, so each renamed or moved name stays, marked `[Obsolete]` with the replacement in its message, listed under Deprecated in the README and on the .NET page, and goes in 2.0 (a name public only by accident goes in 1.0 instead: Decisions, 66 and 68). `CronwatchClient.Start` is `StartChecking` (plan D21), since a job's `StartAsync` opens a run.
62. **The framework-free request and answer are `CronwatchRequest` and `CronwatchResponse`** (plan D12), since `System.Net`'s obsolete `WebRequest` and `WebResponse` made a file importing both namespaces ambiguous; `WebAdapters` is `Adapters`, the Java port's name (plan, Part 5). The former types stay, `[Obsolete]`: `WebRequest` and `WebResponse` are wrappers with implicit conversions both ways (a subclass cannot be returned where the old type was assigned, and a type alias cannot cross assemblies), so `WebResponse answer = await routes.HandleAsync(new WebRequest(...))` compiles as before and a handler's function may return either; only a handler lambda that names its request's type must change, since an overload taking the old delegate would make every untyped lambda ambiguous. `WebBodyReader` and `WebBodyTooLargeException` keep their names, which clash with nothing.
63. **The three optional store interfaces are named after their methods** (plan D13): `IUpdateRunIfStore`, `ICompareAndSetStateStore`, and `IDeleteRunIfStore`, as every other port names the methods. The former `IConditionalRunStore`, `IStateCasStore`, and `IRunDeletingStore` stay, `[Obsolete]`, each extending its replacement and declaring its method again, with the replacement's method forwarding to it, so a store of an app's own that implements one, even explicitly (`Task<bool> IStateCasStore.CompareAndSetStateAsync(...)`), still compiles and is found by the client's `is` test; `MemoryStore` and `SqlStore` implement both names.
64. **The extension methods are in Microsoft's namespaces** (plan D14): `AddCronwatch` and `AddCronwatchJob` in `Microsoft.Extensions.DependencyInjection` (the classes `CronwatchHostingServiceCollectionExtensions` and `CronwatchJobServiceCollectionExtensions`, a name of their own so the former class's is not ambiguous in a file that imports both namespaces, as the Web and Worker SDKs' implicit usings and a job's `using Cronwatch.Hosting;` do), `RunCronwatchCommandAsync` in `Microsoft.Extensions.Hosting`, and `MapCronwatch`, `UseCronwatch`, and `MapCronwatchHandler` in `Microsoft.AspNetCore.Builder` (the class `CronwatchAspNetCoreExtensions`), so an app calls them with no `using`, as it calls `AddHealthChecks` and `MapHealthChecks`; Hangfire's and Quartz's `UseCronwatch` stay in `Cronwatch.Hangfire` and `Cronwatch.Quartz`, those frameworks' own conventions. `ICronwatchJob` moved from `Cronwatch` into `Cronwatch.Hosting`, beside `AddCronwatchJob`. The former classes, `Cronwatch.Hosting.CronwatchServiceCollectionExtensions` and `Cronwatch.AspNetCore.CronwatchAspNetCore`, stay `[Obsolete]` with the same methods as plain static methods, not extensions: an obsolete extension of the same name in a namespace the app also imports would make every `services.AddCronwatch(...)` ambiguous. For the same reason `ICronwatchJob` keeps no alias in `Cronwatch`: a job's file imports `Cronwatch` for `JobContext`, so an alias there would make the new name ambiguous in every file that also imports `Cronwatch.Hosting`; a job written before 0.11 adds `using Cronwatch.Hosting;`, and an app's `using Cronwatch.Hosting;` or `using Cronwatch.AspNetCore;`, no longer needed, still compiles.
65. **Three small items settled for 0.11** (plan D15): `TwilioOptions.Segments` is an `int?` (it was a `double?`, the SDK's number; the channel still floors and holds it to 1 to 10). The webhook shortcut is on the channel type, `SlackChannel.Webhook(url)` and `DiscordChannel.Webhook(url)`, since no other channel had a pair; the static classes `Slack` and `Discord` stay, `[Obsolete]`, forwarding. `CronwatchHostOptions` keeps its settable properties, since `AddCronwatch(o => o.Store = ...)` sets them in a callback where `CronwatchOptions`' `init` properties cannot be set, so rather than wrap the client's options, a test (`HostOptionsTests`) holds the two in step by reflection: every client option but `RunScope`, which the host fills, is a host option of the same type, and the host's own are `CheckEvery`, `NoCheck`, and `Token`. It found `Transport` missing from the host's options, now added.
66. **Public means documented** (plan D25): of `Json`, only `Parse`, `ParseObject`, and `Stringify` are promised; `Quote`, `Kind`, `Copy`, `TryNumber`, and `MaxDepth` were plumbing that leaked, and are `[Obsolete]` until 1.0 removes them (public by accident, so they do not wait for 2.0 as a rename does; the plan, D11), forwarding to the internal `Cronwatch.Internal.JsonText`, which the port's own code calls. The integrations quote with `Json.Stringify`, which writes a string as `Quote` did, rather than through `InternalsVisibleTo`, so a newer core never breaks an older integration. The data types the API's signatures carry (`JsObject`, `Metrics`, `ValueMap`, `ValueList`, and the records) stay public.
67. **The bridge is for integration authors, outside the 1.x promise** (plan D27): `Cronwatch.Bridge` stays public, since `Cronwatch.Hangfire` and `Cronwatch.Quartz` are built on it from other assemblies, and every type in it says so in its documentation, as the .NET schedulers page does; it may change in any minor release. Its static class keeps the name `SchedulerBridge`, which the plan has the Java port take.
68. **The store kit promises its entry point** (plan D28): `StoreContract.RunAsync`, which runs the whole contract, as every other language's kit promises only its own. `StoreReplay` and `FinishOnce`, once promised beside it, and the fixture helpers, `StoreContract.NewRun` and `ForeignRows` (which forward to internal ones), are `[Obsolete]` until 1.0 removes them; the port's own tests still run the replay and the finish-once scenarios through them.
69. **The 0.11 behaviour changes, carried over from the SDK**: `RecordRunAsync` holds a run id to 1 to 200 characters as a run's start does (`conformance/client.json`'s `runIds`); stored data a newer release wrote (an unknown state or definition field, an unknown condition, an unknown run status or trigger) is kept through every write, which the port already did and `client.json`'s `unknownFields` now holds, over the memory store, SQLite, and Postgres; `GET <base>/api` answers `{"ok":true,"library":"Cronwatch","language":"dotnet","version":<CronwatchClient.Version>,"api":1}`, and silence and unsilence over the API answer the job's summary, `{"ok":true,"job":...}`; the webhook's body starts with `"schema":1`; a one-time date is refused with the SDK's own message, `CronPattern: a one-time date is not supported`. The development table was already the SDK's, and `EnvTests` replays it.
70. **The SDK's 2d19e502, carried over**: an evaluated finished import's placeholder row (`RecordRunAsync` writes it `running` until its pending marker and finish land) carries `FinishedAt` set to when it was written (an import still running keeps `FinishedAt` null, so it is never stranded and times out by the job's timeout as any running run does), and a check closes one still `running` `SendLeaseMs` after that (`Evaluate.IsStranded`, replayed from `health.json`'s `isStranded`) as `timeout`, its `FinishedAt` and `DurationMs` kept, with the error `Imported, but its finish was never written; marked as timed out` and the run's own error after a newline, alerting as a stuck run, so a later retry that succeeds still recovers it. `RecordRunAsync` refuses, before writing anything, the fields C#'s types still let be wrong: a `Status` that is not `running`, `ok`, `failed`, or `timeout`, and a `Trigger` that is null; the times and durations are `long`, always finite, and the error and output are strings or null. Slack cuts its body and its triage block after escaping without splitting an `&...;` entity or a surrogate pair (`channels.json`'s "an emoji across the cut"). A job's handler reads its bearer as the routes do. The routes answer `HEAD` on the pages and the API's reads as their `GET` would, without the body, and never run the check (`HEAD <base>/api/check` is a 404); golden.json's seven `HEAD` captures run through every replay. The run recorder's 16 KB tail for an expect rule is kept as a window of lines joined only when it is read, and the whole text below 32 KB in a `StringBuilder`, so a `Log` no longer copies either. And from the audit of the adapter: `MapCronwatch` and `MapCronwatchHandler` called `AllowAnonymous()` whenever a token or secret guarded them, and an `IAllowAnonymous` anywhere on an endpoint makes ASP.NET Core's authorization middleware skip every policy, so `.RequireAuthorization("Admins")` on the answer, or a `RequireAuthorization()` on a group around it, was silently ignored. The anonymous allowance is now a `Finally` convention, run once every other convention (the app's and its groups') is in, that adds `AllowAnonymousAttribute` only when the endpoint carries no `IAuthorizeData`, `AuthorizationPolicy`, `IAuthorizationRequirementData`, or `IAllowAnonymous` of its own. An app with only a fallback policy still reaches the dashboard's sign-in and a platform cron's bearer, an app's own policy is enforced ahead of the token or secret, and an open dashboard or handler is unchanged. An always-true `AuthorizationPolicy` as metadata was considered and refused: with any policy metadata present, ASP.NET Core's `AuthorizationPolicy.CombineAsync` no longer adds the default policy for a bare `[Authorize]`, so a group's plain `RequireAuthorization()` would have been dropped instead.
