# The Go port

`packages/go` is the Go module `cronwatch.dev/go` (package `cronwatch`): the same library as `@cronwatch/sdk`, for Go apps, from a `main` a crontab runs to a service with robfig/cron, gocron, River or Asynq inside it. It is a port, not a new design, made the way the Ruby gem and the Python and PHP packages were (see their `DESIGN.md`), and like the Python and PHP ports it is made in phases. The TypeScript SDK is the source of truth for every behaviour, message and stored byte; when the two disagree, the Go side is wrong.

## Rules

- Go 1.25 or newer (`go 1.25` in `go.mod`), tested on 1.25 and 1.26 in CI: the two newest major releases, which is exactly what Go's own release policy supports, so an app on a Go that still gets security fixes can use the module and nobody is asked to support one that does not. The code uses 1.21's `context.WithoutCancel`, `context.WithTimeoutCause` and the `min`/`max` builtins and 1.22's per-iteration loop variables; the floor is set by support and by the module path (the `go-import` tag's subdirectory field, below, is read only by the 1.25 go command), not by syntax.
- The core module has no requirements at all: its `go.mod` names no other module, and `go mod tidy` keeps it so. Cron parsing and fire times are a port of croner 10 (`internal/schedule/cron`, as the Python port's `_cron.py` and the PHP port's `src/Cron`), zones come from Go's own `time` package (an app without a zone database imports `time/tzdata`), JSON is written by `internal/js` (not `encoding/json`, whose escaping and key order differ), and secret redaction runs on `internal/jsre`, a small backtracking engine with JavaScript's semantics (Go's `regexp` has no lookaround and refuses a bounded repeat past 1000, and the SDK's patterns need both). It refuses what it does not implement rather than read it as something else: lazy quantifiers, named groups, backreferences (`\1`, `\k<name>`), `\c`, `\p{...}` and `\u{...}`. Database drivers appear only in `sqltest`, a module of its own that holds the SQL store's tests (see Storage).
- Times are `int64` epoch milliseconds everywhere, as in the SDK and the other ports, so `evaluate` ports line for line and stored rows are identical. Durations are `float64` milliseconds inside (a definition may hold `1.5`, which the SDK keeps), and the public API takes `time.Duration` where Go code would pass one.
- Anything that leaves the process (store rows, JSON columns, alert JSON) uses the SDK's exact field names, key order and values, so a Node, Ruby, Python, PHP, Go and Rust process can share one database and `@cronwatch/mcp` works against any of them. Each public type's `MarshalJSON` is `JSON.stringify` byte for byte (`internal/js`): numbers as JavaScript prints them (`2` not `2.0`, `1e-7`, `1e+21`), keys in JavaScript's order (array-index keys first in ascending order, then the rest as inserted; `js.Object` keeps that order and `Metrics` keeps it for a run's numbers), only control characters, quotes and backslashes escaped (never `<`, `>` or `&`), and a byte that is not UTF-8 written as U+FFFD, as a JavaScript string decoded from those bytes has it. Call `MarshalJSON` (or `json.Encoder` with `SetEscapeHTML(false)`) for those bytes: `json.Marshal` passes a type's own JSON through its HTML escaping, which rewrites `<`, `>`, `&`, U+2028 and U+2029. The stores call `MarshalJSON` directly.
- A definition keeps its fields in the order they were given. The SDK writes `{ ...defaults, ...options, name }` with `expect` moved last, so the stored JSON follows the object literal an app wrote; Go has no literal to follow, so job options are functional options, applied in the order given, and a Go process declaring a job writes the same bytes a Node process declaring it with its options in that order does. Fields a newer writer added are kept.
- So are the fields a newer writer added to a job's state, and to the alerts it queues: an alert in `undelivered` or `sending` that holds a key this release does not write (at its top, in its details, in a breach) or is of a type it does not know keeps the object it was read as (`Alert.read`), and is written back and retried with every key in its place, as the SDK carries the object; so does an entry of `sending` with a key of its own.
- Alert titles and messages are the SDK's text, character for character, with numbers as `toLocaleString("en-US")` writes them: ICU's rounding, which starts from the shortest decimal digits of the double (1234.56785 rounds up, though its binary value is just below) and rounds half away from zero.
- Lengths and cuts are in UTF-16 code units, as JavaScript counts them (`js.Length16`, `Slice16`, `Tail16`). A cut through a surrogate pair leaves U+FFFD where JavaScript would keep a lone surrogate, which is the character that surrogate becomes once written out as UTF-8 (to a store, a hash, a network), so the stored bytes are the same.
- Secret redaction uses the SDK's patterns, copied verbatim as JavaScript source into `internal/output` and run by `internal/jsre` over UTF-16 code units, so a quantifier counts an emoji as two, `\s` is JavaScript's set, `\b` and `/i` are ASCII-only as they are in JavaScript without the `u` flag, and every one of `conformance/output.json`'s 204 redaction cases gives the SDK's bytes.
- Every condition opens once and closes with a recovery. No repeat alerts. A job whose schedule is removed while missed is open has missed closed by the next check with a recovery of its own (`reason: "unscheduled"`).
- Errors are returned, never panicked, except by the `Must` helpers for package-level declarations (`MustNew`, `MustJob`). A job's function returns an error, which fails the run and is returned from `Run`. A panic in a job's function is recorded as a failed run (`panic: <value>` and up to five frames of the panicking goroutine, innermost first, `    at function (file:line)`, as a JavaScript stack reads) and then carries on up the stack, so no run is left `running` to be reported stuck later; a job's handler is the exception, answering it 500 as the SDK answers a throw (see Handler). The store failing never stops a job: store errors go to the error handler, and the job's own outcome is returned.
- An error is written `Name: message`: the error's type name when it is an exported type (`PathError: open x: no such file or directory`), `Error` for the standard library's unnamed ones (`errors.New`, `fmt.Errorf`, joined errors) and unexported types. Go errors carry no stack, so a returned error has no frames; a panic does.
- The environment is read in one place, `env.go`: the first of `CRONWATCH_ENV`, `APP_ENV` and `GO_ENV` set to more than whitespace, trimmed as JavaScript trims, so a blank one is skipped (the SDK reads `NODE_ENV` last); `development`, `dev`, `local`, `test` and `testing` are development and `prod` is production, as in the PHP port. It decides whether the in-memory store warns that it forgets on restart, whether the dashboard makes a development token when none is configured, and whether a job's handler runs without a secret. The other reads are the SDK's own: `CRON_SECRET` (the client's cron secret) and `CRONWATCH_TOKEN` (the dashboard's token), and Claude triage's `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL`, the variables the official Anthropic client reads, in `triage`.
- Safe for use by many goroutines at once: the client, a job, a run handle, a job context and every store.
- No em or en dashes anywhere, as in the rest of the repo.

## Module path and releases

The module path is `cronwatch.dev/go`, a vanity path served by a `go-import` tag from cronwatch.dev that points into this repository, with Go 1.25's subdirectory field:

```html
<meta name="go-import" content="cronwatch.dev/go git https://github.com/phillips-jon/cronwatch packages/go">
```

The go command then fetches `packages/go` from the monorepo, and versions are tags prefixed with that directory: `packages/go/v0.6.0` for release 0.6.0 (the go command's rule for a module below a repository's root, `modfetch.newCodeRepo`, which the subdirectory field feeds). The three options weighed:

- *`github.com/phillips-jon/cronwatch/packages/go`, tags `packages/go/vX.Y.Z`.* Works today with no infrastructure. But the import path names a personal GitHub account and a directory layout forever: moving the repository to an organisation, or `packages/go` anywhere else, is a new module path and a breaking change for every importer, and `packages/go` reads badly in an import block.
- *`cronwatch.dev/go`, tags `packages/go/vX.Y.Z`* (recommended). The path is the product's own domain, like the docs, and says nothing about where the code lives: the repository can move, be renamed or be split later by changing one meta tag, and importers change nothing. The tags are the same as the first option's, so nothing about releasing differs, and no second repository or split workflow is needed. The cost is that cronwatch.dev must answer `?go-get=1` for the module path (a static page is enough), and that the subdirectory field needs the Go 1.25 go command, which is also the oldest Go this module supports; the module proxy, which runs a current Go, caches every version it has served, so a release keeps resolving through the proxy even if the site is down.
- *A split repository* (`github.com/phillips-jon/cronwatch-go`, tags `vX.Y.Z`), as the PHP package reaches Packagist. It gives the shortest tags and works on any Go, but it is a second repository, a deploy key and a split workflow to keep working, for nothing a Go importer can see, since Go, unlike Packagist, reads modules from subdirectories.

The last element of the path is `go`, not the package name `cronwatch`; the package clause says `cronwatch`, so code refers to `cronwatch.New` and goimports writes the import as `cronwatch "cronwatch.dev/go"`, as it does for `gopkg.in/yaml.v3`. Other packages of the module are `cronwatch.dev/go/sqlstore`, `cronwatch.dev/go/storetest`, `cronwatch.dev/go/alerts`, `cronwatch.dev/go/triage`, `cronwatch.dev/go/pgcron` and `cronwatch.dev/go/bridge`, all under the same tag. The scheduler integrations are modules of their own nested under `packages/go` (`cronwatch.dev/go/robfigcron`, `cronwatch.dev/go/gocron`, `cronwatch.dev/go/river`, `cronwatch.dev/go/asynq`; see Scheduler integrations), so an app pulls only the scheduler it uses and the core stays requirement-free. The dashboard is in the core package, not a `web` package as first planned: it is `cw.Routes(...)`, a method, which a package importing `cronwatch` could not add, and its timelines use the evaluation's own unexported rules (grace, timeouts, stuck runs, the schedule's fires) as the SDK's do.

The site change is for a later phase and the owner's approval. It is a page at `/go` (and one per nested module, such as `/go/river`, each naming its own path and subdirectory, since for a module below the tag's prefix the go command puts the subdirectory field after the module's own directory, `river/packages/go`, not before it) holding the meta tag above and a link to the docs, served for `?go-get=1` requests; with the site's nginx, one `location ~ ^/go(/|$)` answering the right tag for the path does it. Until then nothing can `go get` the module, which is fine before its first release. If the owner prefers not to serve it, the fallback is the first option: change the path in `go.mod`, the imports and this file, and nothing else.

`version.go` holds `const Version`, the release version, bumped by `scripts/release.mjs` with the others (the VERSIONED table); a Go module's real version is its tag, so the PUBLISH table prints the tag to add to the release commit and push (`git tag -a packages/go/vX.Y.Z ... vX.Y.Z^{}`). `packages/go/sqltest` and `packages/go/examples` hold tests and examples only and are never tagged or imported. The integration modules are tagged `packages/go/<name>/vX.Y.Z` at the same version, and the PUBLISH row prints those tags too. Each requires the core (and `gocron`, `river` and `asynq` require `robfigcron`, for its conversion of robfig/cron schedules) at the same release, with a `replace` to the directory beside it for development, which an app requiring the module ignores; the VERSIONED table bumps those requirement lines, so a release's modules require each other at that release. None of them carries a version constant of its own. An integration module requires its scheduler at the oldest release it supports, so an app on that release can use it; CI also tests the newest.

## The Go API

```go
import (
	cronwatch "cronwatch.dev/go"
	"cronwatch.dev/go/sqlstore"
)

store, err := sqlstore.New(db, sqlstore.Postgres) // the app's *sql.DB and driver
cw, err := cronwatch.New(
	cronwatch.WithStore(store),                           // default: a MemoryStore
	cronwatch.WithAlerts(cronwatch.ChannelFunc("pager", page)), // default: Console()
	cronwatch.WithRetention("30d"),
)

nightly, err := cw.Job("nightly-report",
	cronwatch.Schedule("0 2 * * *"), cronwatch.Timezone("UTC"),
	cronwatch.Grace("15m"), cronwatch.Timeout(30*time.Minute),
	cronwatch.Expect("Report written"), cronwatch.Budget("cost", 2),
	cronwatch.FailuresBeforeAlert(1))

err = nightly.Run(ctx, func(ctx context.Context, job *cronwatch.JobContext) error {
	path, err := buildReport(ctx) // ctx is cancelled at the job's timeout
	job.Log("Report written:", path)
	job.Metric("cost", 1.2)
	return err
})

report, err := cronwatch.RunValue(ctx, nightly, func(ctx context.Context, job *cronwatch.JobContext) (string, error) {
	return "Report written", nil // a string is the output when nothing was logged
})

result, err := cw.Check(ctx) // missed and stuck runs, retries, pruning; a *CheckResult
cw.StartChecking(time.Minute)        // a goroutine that checks every minute (long-running services)
cw.Silence(ctx, "nightly-report", 2*time.Hour)
```

The shape follows Go's conventions while keeping the SDK's names recognisable: `cronwatch({...})` is `cronwatch.New(options...)`, `cw.job(name, options)` is `cw.Job(name, options...)`, `job.run(fn)` is `job.Run(ctx, fn)`, `recordRun`, `resumeRun`, `jobsWithRuns` and `jobSummary` are `RecordRun`, `ResumeRun`, `JobsWithRuns` and `JobSummary`. Every call that can reach the store takes a `context.Context` first and returns an `error`; nothing panics for a bad option or a store failure.

- *Functional options, not an Options struct*, for both the client and jobs. For jobs it is the only way to keep a definition's fields in the order given (see Rules). For the client it keeps the SDK's three-way options readable: `WithCronSecret(s)` and `WithoutCronSecret()` where the SDK has a string, `null` and absent; `WithRedact(fn)` and `WithoutRedaction()` where it has a function and `false`; `WithDeliver(cronwatch.DeliverAtCheck)`. `WithDefaults` takes the job options `Grace`, `Timeout`, `Timezone` and `FailuresBeforeAlert`, and refuses others with an error.
- *Durations* take the SDK's text or a Go duration: `Grace`, `Timeout`, `MaxDuration` and `WithRetention` are generic over `~string | ~int | ~int64 | ~float64`, so `Grace("15m")`, `Grace(15*time.Minute)` and `Grace(900000)` all compile; text is stored as written and a `time.Duration` as its milliseconds (as the Python port stores a `timedelta`). Methods cannot be generic in Go, so `Silence` and `StartChecking` take a `time.Duration`.
- *Expect* is three options: `Expect(text)` (contains), `ExpectMatch(*regexp.Regexp)` (Go's syntax, stored as `matches /source/`, flags being inline in Go; `regexp` runs in linear time, so a pattern that backtracks without end in V8, such as `\n*\n*\n*\n*\n*x`, needs no bound here, and it answers `format.json`'s pathological cases in full, with the failure the bounded ports give when they stop) and `ExpectFunc(func(string) bool)` (stored as `custom function`; a panic in it fails the run with `Output check threw: ...`).
- *Job functions* are `func(ctx context.Context, job *JobContext) error`. The context is the caller's with the job's timeout added (the SDK's `signal`), cancelled with a cause naming the job and its timeout (a `context.DeadlineExceeded` for `errors.Is`), and carries the `JobContext`, so code deep in a call chain can find it with `cronwatch.Current(ctx)`. `RunValue[T]` is `run()` for a function that returns a value, generic because methods cannot be: a `string` is the output when nothing was logged (and what `expect` checks), and an `*http.Response` of 400 or more fails the run with `HTTP <status> <reason>`, as the SDK does for a fetch `Response`.
- *Recording never depends on the caller's context.* Store calls made while recording a run use `context.WithoutCancel(ctx)`, so a run whose caller gave up (a request that ended, a deadline) is still recorded as it ended, rather than left `running` to be reported stuck; the values the context carries (trace ids) still reach the store.
- *Channels, triage and sources are interfaces*: `Channel` (`Name`, `Send(ctx, Alert, ChannelContext) error`; `ChannelFunc` wraps a function, `Console` is the default, `NewChannelContext(report)` makes a context for sending outside a client, and the zero `ChannelContext` reports to standard error as the SDK does for a channel called without one), `TriageFunc` (`func(ctx, TriageContext) (string, error)`) and `Source` (`Name`, `Sync(ctx, SourceHost)`), where `SourceHost` is what a source may use of the client and `*Client` is one.
- *Stores* are the `Store` interface, with the SDK's two optional methods as the optional interfaces `RunUpdater` (`UpdateRunIf`) and `StateComparer` (`CompareAndSetState`), checked by type assertion as `io.WriterTo` is; without them the client falls back to a read then a write, as the SDK does. A third, `RunDeleter` (`DeleteRunIf(ctx, id, job, status)`, one `DELETE ... WHERE id = ? AND job = ? AND status = ?`), has no counterpart in the SDK: it is the PHP port's `deleteRunIf`, which `DiscardWhen` needs (below). `MemoryStore` and `sqlstore` have all three, and `storetest.Run` checks `DeleteRunIf` for a store that has it.
- *A run given back*: `DiscardWhen(func(error) bool)`, a `RunOption` for `Run` and `RunValue`, takes the run back rather than judging it when the function returns an error the predicate answers true for, for an attempt a queue gives back without failing (a River job that snoozes or cancels itself, an Asynq task revoked). The run's row is deleted while it is still running and of the job; nothing is judged, no alert is sent, the job's state is left as it was (failures in a row, and missed and stuck: a run that may be given back closes them only once it is known not to be, as the PHP port's released Laravel job does, so an overdue job that snoozes keeps its one missed alert rather than having it closed and opened again by each check), and the error is still returned. A row a check already marked stuck is left as it is, and a store that is not a `RunDeleter` records the run as it ended (rather than leave it running, to be reported stuck), both reported as `discarding <job>`. A panic is never given back.
- *Writing a declaration now*: `cw.SyncJob(ctx, name)` writes the job declared in this process to the store unless the store already holds that definition (compared as JSON, keys in any order, since Postgres's `JSONB` reorders them), and says whether it wrote. A run or a check writes a declaration once anyway; the scheduler integrations call it so a process that only schedules still puts its jobs in the store, and so a definition another process changed is written back (see Scheduler integrations). The SDK has no counterpart.
- *Nullable values are pointers* (`*int64`, `*string`) in `Run`, `JobState` and `JobSummary`, so `null` and absent survive a round trip. In `JobState`, a nil `PendingRecovery` or `Undelivered` is a state written before the field existed (absent from the JSON), and a nil `Version` is a state written before versions. `Sending` is nil when empty, and absent from the JSON then; an entry another writer stored that is not `{until, alert}` is kept as it was and released at the next check, as `releaseSending` treats it, so it never makes the state unreadable.
- *Deprecated names* carry a `Deprecated:` paragraph, which `staticcheck` reports to callers in other packages, and keep working until the release named: `Start` (renamed `StartChecking`, as the SDK's `start` became `startChecking`) and `robfigcron.Watch` and `cwgocron.Watch` (one way to attach a watcher, `New(cw, o).Option()`), documented before 1.0, through 1.x; `cwgocron.Converted` (`robfigcron.Converted` is the one type), `cwgocron.Panic` (`PanicError`), and what was exported by accident (`JSValue` on seven types, `Stderr`, `Stdout`, `MaxBody`, `ReservedRunIDPrefix`, `pgcron.Hold`, `Schedule`, `JobName` and `RunOf`, `triage.System`) until 1.0, which unexports them. Their uses inside the module go through unexported names, `js.ValueOf` for `JSValue`, and the tests' hooks in `export_test.go`. The README and the Go page list them.

## Runs that span calls

`job.Start(ctx, WithTrigger(t), WithRunID(id))`, `job.Resume(ctx, runID)` and `cw.ResumeRun(ctx, name, runID)` are the SDK's `start()`, `resume()` and `resumeRun()`, and return a `*RunHandle`: `ID`, `Job`, `StartedAt`, `Active`, `Log`, `Metric`, `Flush(ctx)`, `Finish(ctx)`, `FinishWith(ctx, result)` and `Fail(ctx, err)`. They return an error only for a run id no store could hold or one in the pg_cron source's `pgcron:` namespace (the SDK's messages), and for a stored run that belongs to another job. `Run` refuses `WithRunID`, which is for `Start` only.

The client's side follows `client.ts`: a start with an id holds a per-process entry keyed by the job and the id while it reads the store and inserts, so two starts with one id at once in one process record one run and get the same handle, and another job's start with that id fails as it would one call later. `Finish` reads the stored run again, joins the stored output with the handle's (capped) and merges metrics (the handle's win), then judges it with the same code as `Run`. `Flush` redacts the lines it appends and writes only over a row still running and of this job (`UpdateRunIf`); when it cannot, the handle keeps the lines for `Finish`, and it keeps the first 16 KB of what it flushed so `expect` at finish sees an early line. The store never fails out of `Start`, `Resume`, `Flush` or `Finish`: failures go to the error handler as `recording <job>`, `starting <job>`, `resuming <job>`, `flushing <job>` or `finishing <job>`. A store that fails during `Finish` records nothing and leaves the handle active, lines kept, so it can be called again. A finish that records nothing is reported, never returned as an error, and returns nil.

A run is judged once, however many processes finish it: the finish is written only over a stored row still `running`, else over one still `timeout` (a check already counted it as stuck: a late failure is written but not judged, a late success is judged and recovers), through `UpdateRunIf`, one conditional `UPDATE`. Only the process whose write lands evaluates. The stuck check marks a run timed out the same way, so a finish that landed meanwhile wins. `InsertRun` refuses an id already stored, the memory store included. `storetest.FinishOnce` holds the SDK's multi-process tests (two processes finishing one run, two recording one finished run from a source, six starting and finishing one id five times), run against the memory store here and against SQLite, Postgres, MySQL and MariaDB in `sqltest`, each process a store of its own over one database.

## Goroutines and state

The client never blocks a job on anything but its own store writes. Every read-modify-write of a job's state goes through `updateState`: holding the job's mutex (the SDK's `serial()` queue), it reads the state, works out the next one, and writes it only when it changed, with `version` one higher, through `CompareAndSetState` against the version read; a refused write is worked out again from a fresh read, up to 10 times. Only store reads and writes happen under the lock; alerts are sent after it is released. Closing missed and stuck at a run's start happens in a goroutine beside the job, joined before the finish is written, as the SDK's promise is. Concurrent `Check` calls share one check, run in a goroutine of its own with the first caller's context without its cancellation (its values still reach the store), so a caller that gives up (a request that ended) neither fails the check for the others nor leaves a job half checked; each caller stops waiting when its own context ends, with its cause. A panic in the check (a store's, say) is that check's error, and the next `Check` runs a new one, where it once left every later call waiting. `StartChecking(every)` (the SDK's `startChecking()`; `Start`, its name before 1.0, is a deprecated alias) runs checks in a goroutine, the first after a second and then on the interval (a minute by default, five seconds at least); a second call does nothing, and `Stop` ends it (a check in flight finishes). `Close` stops it, waits for the interval's goroutine and for a check already under way (bounded by the check's own channel, triage and retry timeouts), then closes the store, so that check neither writes after the store is closed nor loses the alerts it would queue.

## Delivery

The outbox is the SDK's: the write that opens a condition also holds its alerts, composed, in the state's `sending` list, each with a lease of five minutes (`until`), before anything is sent (`holdAlerts`, in `evaluate.go` with `queueUndelivered`, `releaseSending` and `recordSent`, all replayed from `conformance/health.json`). The sender triages and sends them, then takes them out of `sending` as it records how the send went. A process that stops in between loses nothing: the first check after the lease moves them to `undelivered`, and the retry sends them once, triaged then (twice, when a channel took one just before its process died). `WithDeliver(DeliverNow)` (the default) sends each alert from the process that produced it. `DeliverAtCheck` sends nothing: the alert is queued in the job's state (`undelivered`, at most 20, the oldest dropped first and reported), in the write that opens its condition, for the next check in a process that delivers now, which triages and sends it. An alert no channel accepted is queued the same way and retried once per check, oldest first; one that no longer describes the job (`staleAlert`) is dropped; one check spends at most 20 seconds of wall clock retrying across all jobs. Triage is tried once per alert: `Triage` nil with `TriageTried` set is JSON `null`, never tried again.

Each channel sends in a goroutine of its own with a 15 second context, and triage gets 25 seconds. Go cannot stop a goroutine, so a channel (or triage) that has not returned when its time is up is left to finish; until it has, nothing more is sent to it (the alert counts as not delivered there, and is retried) and no second triage starts, so a channel that ignores its context holds one goroutine rather than one per alert. Each send past its timeout is counted against its channel (and each triage against triage) and uncounts only itself when it returns, so another send to that channel that returns in time never clears a hung one's mark. The Python port does the same with threads. The channels are in `alerts` and Claude triage in `triage` (below); each request of theirs has its own ten second deadline (24 seconds for triage) inside those.

## Channels

`cronwatch.dev/go/alerts` holds the SDK's channels, request for request, on `net/http` alone: `Slack`, `Discord` and `Webhook` (the alert after `"schema": 1`, an HMAC-SHA256 signature in `X-CronWatch-Signature`, `Signature` for a receiver to check it with), the email providers `Resend`, `Postmark`, `Sendgrid`, `Mailgun` and `SES` (signed with SigV4 in `sigv4.go`, checked against the AWS test suite, so no AWS SDK), `Twilio` for SMS, and the trackers `Sentry`, `Honeybadger`, `Datadog`, `Rollbar`, `Bugsnag` and `NewRelic`. Each is made from an options struct with the SDK's option names in Go's case (`alerts.Resend(alerts.ResendOptions{APIKey: ..., EmailOptions: alerts.EmailOptions{From: ..., To: []string{...}}})`) and returns a `cronwatch.Channel` or the SDK's refusal in Go's words (`alerts.Resend needs an APIKey`). Options structs rather than functional options, since nothing here has an order to keep; a boolean the SDK defaults to true is the negative in Go (`SkipRecovered` for Sentry and Rollbar, whose recoveries go out unless it is set), so the zero value is always the default, and `Twilio`'s `Segments` 0 is its default, 3.

The requests are the SDK's: the same URL, header names (lowercase, sent in Go's canonical case, which HTTP reads the same) and values, and body, written by `internal/js` so the bytes are identical; the same stable alert id (the first 32 hex characters of SHA-256 over job, type and time) for Resend's idempotency key, Sentry's event id and Rollbar's UUID; the same error text, `<Provider> <origin> answered <status>: <body>` (Slack's and Discord's `<Name> webhook answered <status>: <body>`, the webhook's without the body). Text JavaScript cuts through a surrogate pair with `slice` (Slack's and Discord's bodies, triage's prompt) keeps the lone half, held as its WTF-8 bytes by `js.Slice16Lone` and written `\ud83d` by `js.StringifyLone`, as `JSON.stringify` writes it, so even those bodies are the SDK's bytes.

Every request goes through `internal/post`, which holds the hardening the SDK and the other ports got in their audits:

- One deadline for the whole request, connecting, sending and reading the answer: a context with ten seconds (`post.Timeout`) under the one the client gives the channel. Past it before an answer is `The operation was aborted due to timeout`, fetch's message; past it while the body arrives is the answer with no body, as the SDK treats a body it could not read. The caller's context ending ends the request.
- A redirect is refused, not followed: the client is used as a copy whose `CheckRedirect` answers `http.ErrUseLastResponse`, even when the app passed one that follows, so the 3xx is an answer outside 2xx like any other and the send fails. Credential headers never go where it points.
- At most 1 MiB of an answer is read (`post.MaxBody`): a channel quotes 200 characters of a refusal, and a gzip answer the transport decodes could otherwise grow without bound.
- TLS is never turned off: the default is Go's default transport; an app's `HTTPClient` (a proxy, a custom root) is its own choice.
- The URL is cleaned as fetch cleans it (characters U+0000 to U+0020 around it dropped, every tab, CR and LF inside removed) and must be `http` or `https` with a host, else `only http and https URLs can be posted to, not ftp:` (the scheme) or `not this URL` (no scheme, no host, a space left inside, or a user name and password, which fetch refuses to send), never quoting it, since a webhook URL's path is its credential.
- Only the URL's origin appears in any error: an answer's error names it, and a transport failure is `<origin>: <what went wrong>`, every `*url.Error` that would quote the whole URL taken apart however deeply an app's transport nests them, and any other spelling of the URL, its path or its query still in the text (an app's transport that quotes it itself) written as the origin or cut out. A deadline passed is `post.ErrTimeout`, fetch's message, and a `context.DeadlineExceeded` for `errors.Is`. A cookie an endpoint sets never reaches the app client's jar.
- Credentials are trimmed of the spaces and newlines a paste leaves. Header names must be HTTP tokens and values are trimmed as fetch trims them; one with a CR, LF or NUL left inside is refused with an error naming the header, never its value.
- Every secret the channel holds (four characters or more) is cut out of a quoted answer in a prefix of 200 plus the longest secret's length, and only then is the answer cut to 200 UTF-16 units on a code point, so no piece of a secret survives at the edge.

Twilio texts every number at once, a goroutine each (a panic in one, from an app's transport say, is that number's failure rather than the end of the process): the body fitted to the segments allowed (GSM-7 at 153 a segment or UCS-2 at 67 once split, the extension table costing two, a character never split across two, the link kept whole), the alert delivered when any number took it, each refusal reported through the `ChannelContext` as `<error> (to <mask>; <ok> of <n> numbers took the alert)`, and an error only when every number refused it.

`alerts/conformance_test.go` replays every case of `conformance/channels.json` through a recording transport: `sends` and `failures` for Slack, Discord and the webhook, `providerSends` and `providerFailures` for the other twelve (Twilio's requests compared in its numbers' order), `twilioPartial` and `textCuts`, 619 cases. `hardening_test.go` has the rest against real `httptest` servers: every channel refusing a redirect, the deadline, a gzip answer of 64 MiB read to 1 MiB, the URL and header refusals, only the origin in a transport error, an untrusted certificate refused, credentials trimmed, a secret straddling the cut, and Twilio's partial delivery through a client.

## Dashboard

`cw.Routes(options...)` is the SDK's `cw.routes()`: a `*Routes`, an `http.Handler` whose answers are `routes/index.ts` line for line (the same URLs, JSON, status codes, headers, CSP, cookie, redirects, cross-site rule, token and cron secret rules, development token and its sign-in line (the host in it only when `WithOrigin` is set or the request's host is loopback), and 500s reported to the error handler as `routes`, a panic included), and whose pages are `routes/html.ts` and `routes/timeline.ts` byte for byte, the CSS, the app shell (manifest, icons, service worker, app.js, the offline page), the sign-in form and the `<wbr>` after a name's separators included. The options are functional, as the client's are: `WithToken(t)` and `WithoutToken()` where the SDK has a string, `null` and absent (the default reads `CRONWATCH_TOKEN`; "" counts as unset), `WithBasePath`, `WithOrigin` (read as `new URL(value).origin` reads it; anything but an http or https URL is an error from `Routes`, with the SDK's message) and `WithTrustProxy`. A development token is announced once per `Routes` on `Stdout`, where `console.info` writes it. `Routes.Token` is the token in force, the generated one included. The icons are the SDK's PNGs and SVGs, written into `routes_icons.go` by `scripts/make-dashboard-icons.mjs`, whose `--check` covers the Go file too; the style sheet and scripts are copied verbatim into `routes_assets.go`.

The base path is found from the request, since a Go mount says where it is, as the gem's Rack mount and the Python package's `SCRIPT_NAME` do: `WithBasePath` when given; else what `http.StripPrefix` took off (the request target the server kept in `RequestURI` ends with the path left in `r.URL`, and the difference is the mount); else the `ServeMux` pattern that matched (Go 1.22's patterns, read from `r.Pattern`): as many segments of the request's path as the pattern has before a trailing slash, `{$}` or `{name...}`, so `/cronwatch/`, `/cronwatch/{path...}` and `GET /t/{tenant}/cron/` all work; else the SDK's `/cronwatch`, for a handler given to `ListenAndServe` as it is.

What a request says is read as the SDK reads a fetch `Request`: the path from the target as sent (`RequestURI`, so a `%2F` in a job name stays one) as the URL parser leaves it (backslashes as slashes, characters a browser escapes escaped, `.` and `..` segments resolved), the query as `URLSearchParams` parses it (an escape that is not one kept as written), headers joined as `Headers.get` joins them (cookies sent as several headers, as HTTP/2 may, joined with `; `) and compared as the bytes fetch reads (Latin-1), the body as `request.json()` (a byte order mark dropped, values as `String(value)` gives them) and `request.formData()` (URL encoded or multipart, a file field as `[object File]`) read it, and the origin from the request's scheme (https over TLS) and `Host`, lowercased and without a default port. A body is read only once a route wants it (silence, after the token and the job's lookup), and at most 1 MiB and one byte more: past it, or with a `Content-Length` saying so, the answer is 413, `{"ok":false,"error":"Request body too large"}` or the HTML route's message page, as the Python and PHP packages answer; the SDK leaves this to the server in front of it.

`routes_golden_test.go` replays the gem's fixture, `packages/ruby/test/web/golden.json` (57 captures of the SDK's routes over a fixed seed, PNGs as base64), three ways: straight into the handler with the request a server would hand over, and through a real server with the dashboard mounted by `http.StripPrefix` and by a `ServeMux` pattern, its base path found each time; every status, header and body matches, `Content-Length` and the server's `Date` aside (through a server, the two `%zz` captures are Go's own 400, below). `routes_test.go` has the SDK's routes tests (the token, the cron secret, sign-in, the pages and API, cross-site writes, malformed input, clamps, 500s, silences, security headers, escaping, the development token from each of the three variables, the origin options) and the Go ones (the base path, the body cap, HEAD, split cookies, paths as the URL parser leaves them). `CRONWATCH_TEST_GO=1 npm test --workspace packages/mcp` drives `@cronwatch/mcp` against `internal/webserver` (seeded, mounted with `http.StripPrefix`), as it runs against the other ports' dashboards, and CI runs it on both Go versions. ## Handler

`job.Handler(fn, options...)` is the SDK's `handler()`, for a platform cron that calls a URL: an `http.Handler` that runs `fn(ctx, job, w, r)` as a recorded run with the trigger `"handler"` for each request whose `Authorization` is `Bearer <secret>`, compared in constant time. The secret is `WithSecret(s)`, else the client's (`WithCronSecret`, `CRON_SECRET` by default, "" counting as unset); `WithoutSecret()`, or a client made `WithoutCronSecret()`, lets anyone run the job. With no secret and no opt-out, outside development, it answers 503 with the SDK's JSON and reports to the error handler once per client as `handler`; a wrong or missing bearer is 401 `{"ok":false,"error":"Unauthorized"}`. A run is answered with `{"ok","job","run","status","durationMs"}`, 200 or 500, and the error's first line as `"error"` only when a secret was required, with the headers of the SDK's `json()` (`content-type: application/json; charset=utf-8`, `cache-control: no-store`). The context is the request's with the job's timeout, carrying the `JobContext`.

The SDK answers with a `Response` the function returns, and fails the run when its status is 400 or more. Go has two ways to answer, and both count: the function may write its own answer through `w` (a wrapper that notes the status, and passes `Flush` and `http.ResponseController` through), and a status of 400 or more written there fails the run with `HTTP <status> <text>`; or, through `HandlerValue[T]` (as `RunValue` is `Run`'s), it may return an `*http.Response`, which is copied to the caller (headers, status, body, the body closed) and fails the run the same way. A response returned with an error (which the SDK cannot have: a function returns or throws) is closed unread and the caller gets the JSON answer of a failed run, since the run failed with the error; so is one returned by a function that wrote its own answer. A function that writes nothing and returns no response gets the JSON answer; one that returns a string has it as the run's output when nothing was logged. A panic is a failed run like a returned error (`panic: <value>` and its frames) and is answered as the SDK answers a throw: 500 with the JSON, its `"error"` the panic's first line for a caller who sent the secret. Two panics still abort the response, recorded the same way first: `http.ErrAbortHandler`, which is `net/http`'s own way to abort one and is panicked again as it is, and any panic after the function began its own answer, which cannot become the JSON answer and is panicked again as `http.ErrAbortHandler`, so the client sees a broken response rather than a truncated one taken for whole, and the server logs no stack for it. (Before phase 4 a panic carried on to `net/http`, which dropped the connection; the owner chose the SDK's answer.)

`Lambda(h)` is any `http.Handler`, a job's handler or the dashboard, as an AWS Lambda function behind API Gateway (a REST API, an HTTP API with either payload format) or a function URL, for `aws-lambda-go`'s `lambda.Start`, which takes any function of a context and a JSON-decodable event: `LambdaEvent` and `LambdaResult` are plain structs, so the core module needs no AWS module and an app that uses Lambda already has `aws-lambda-go`. The event becomes an `*http.Request` over https (headers from `headers` and `multiValueHeaders`, a 2.0 event's `cookies` as its `Cookie`, a base64 body decoded) and the answer the proxy result (the body as text when it is UTF-8 and base64 otherwise, no `Content-Length`, a header given twice in `multiValueHeaders` for 1.0 and joined with `, ` for 2.0, whose `Set-Cookie` go in `cookies`), with no key the format does not know, since a REST API refuses a result with one. A directly invoked function (EventBridge Scheduler) has no headers to carry a bearer; IAM decides who may invoke it, so its handler takes `WithoutSecret()`. `handler_test.go` has the SDK's handler tests and the Go answers, and `lambda_test.go` REST API, HTTP API and function URL events through a handler and the dashboard.

## Scheduler integrations

The SDK has no scheduler integrations; these follow the gem's Sidekiq and scheduler integrations and the Python and PHP ports' Celery, APScheduler, Laravel and Symfony ones. Each watches a scheduler with no change to the app's jobs beyond one option or constructor: its entries become jobs with their schedules, its runs are recorded, and a job whose entry is gone loses its schedule. What they share is `cronwatch.dev/go/bridge`, in the core module since it needs only the standard library, and outside the 1.x promise (its package doc says so): it is for integration authors and changes in a minor release when one of these integrations needs it to, so promising it would freeze their internals. It holds:

- *Declaring.* `bridge.Watch.Declare(entries)` declares a scheduler's entries as they are now, one job per name: the integration's defaults, then the schedule, then the entry's own options (so a `Schedule` among them replaces the scheduler's), and the tags. Several entries of one name on different schedules are one job without a schedule, reported once (`"twice" is run by 2 gocron entries on different schedules (...)`), as the Python port does for a Celery task beat schedules twice. A declaration that has not changed (compared as `DescribeJob`'s JSON) is left alone while the client still declares it; one forgotten since (the dashboard's forget) is declared again, by the next `Declare`, or by `Unschedule` for an entry still current, so the scheduler's job keeps its schedule rather than being taken for an entry gone when its next run writes it back, and a job `Fallback` declared is declared again the same way, and a problem is reported once per process to the error handler as `declaring <entry>`. What is declared is written to the store in the background (`SyncJob`, one goroutine at a time, 30 seconds a write), since a process that only schedules (an Asynq scheduler whose server runs elsewhere, a River client inserting periodic jobs its workers elsewhere run) neither runs nor checks, and a declaration kept in memory never reached the processes that do; `Watch.Settle` (each integration's `Wait`) waits for it.
- *Tags and the app.* Jobs are tagged with the integration (`robfig-cron`, `gocron`, `river`, `asynq`) and the app under it (`gocron:<app>`), the PHP port's rule for Laravel and Symfony: the app is the integration's `App` option, else `$CRONWATCH_APP_ID`, else the running executable's name, made a tag by `bridge.AppTag`, the PHP port's `appTag()` character for character (lowercased in ASCII only, as PHP 8's `strtolower`, and hashed with MD5 when empty or long). The executable's name is the app's rather than its path, which a deploy may change; two apps sharing a store with executables of the same name, or one app whose processes are different executables, set `CRONWATCH_APP_ID`.
- *Jobs gone.* A job whose entries are all gone keeps its runs and is declared again without its schedule, with its description followed by ` (no longer scheduled)` and its tags, grace, timeout, maxDuration, budget and failuresBeforeAlert (`bridge.Unscheduled`), so it is never reported missed and a missed alert already open closes with the `unscheduled` recovery. Within a process this follows `Declare`; across deploys, `Watch.Unschedule(ctx)` declares again every job the store holds with a schedule and this app's tag that this process has not declared, as the PHP port's `Unscheduled::declare()` does before a check. It first writes back this process's own declarations wherever the store holds something else: an older release still up during a deploy takes the schedule out of a job it does not run, and a long-running process, unlike PHP's, would otherwise never put it back. A process that never saw an entry of its scheduler (a server that runs checks and no scheduler) takes nothing, so it cannot unschedule the app's jobs.
- *Workers elsewhere.* A queue's worker may run in a process that declares no schedule (River's workers, an Asynq server). Its runs belong to the job the scheduling process declared, so it declares that job again from the definition the store holds when it is this app's (`bridge.OptionsOf`: every option a definition can hold, an expect pattern Go wrote as `ExpectMatch`, a custom function as one that passes every output, since the function is the other process's), rather than let its first run write a definition without the schedule (`Watch.Fallback`). When the store cannot be read, nothing is declared and that run goes unrecorded (reported as `declaring <name>`), since a declaration made without the stored one would write over its schedule; and a name `Declare` holds is `Declare`'s, the two taking turns, so a run racing the first sync cannot leave the client holding the definition without the schedule.
- *Schedules checked.* A schedule converted from a scheduler's own is checked against the scheduler's own fire times (`bridge.CheckFires`, the Python port's `_scheduler_check.py` and the gem's check against Fugit): around every clock change of the next five years and from the start of each month of a sample year, CronWatch must not want a run between two of the scheduler's, and away from clock changes every run the scheduler makes must be one CronWatch expects. A schedule that fails is reported with the times that differ (or, for a time daylight saving skips, with the clock change) and the job is watched without one. `bridge.Zone` names the scheduler's zone: an IANA zone as itself, and the process's own (`time.Local`) by `$TZ` or where `/etc/localtime` points, taken only when its offsets are `time.Local`'s over the next five years, so a check in another process reads the schedule in the same zone; otherwise no zone, which each process reads as its own.
- *Retries*, for the queues, follow the gem's Sidekiq rules: every attempt is a run of its own, an attempt that fails (an error, or a panic the queue recovers) is a failed run with its cause, so failing attempts open one failed alert and the one that succeeds closes it, and `FailuresBeforeAlert` rides through retries. An attempt the queue gives back without failing is taken back with `DiscardWhen` (above), as the PHP port takes back a released Laravel job's: nothing is judged or alerted and failures in a row are kept.

### robfig/cron v3

`robfigcron.New(cw, robfigcron.Options{...})` gives the `*Watcher`, whose `Option()` is a `cron.Option`, the one line an app adds (`cron.New(robfigcron.New(cw, opts).Option())`), and whose `Sync` and `Wait` are there for tests and a clean exit. `robfigcron.Watch(cw, opts)`, the same option in one call, is deprecated: one way to write it. It sets the cron's chain to the app's wrappers (`Options.Chain`) with CronWatch's innermost, and its logger to one around the app's (`Options.Logger`, else robfig/cron's default). The wrapper records each run with the trigger `robfig-cron`; a job skipped by a wrapper outside it (`SkipIfStillRunning`) records nothing, and a panic is a failed run that carries on to the wrappers outside it (`cron.Recover`) or ends the program, as it would without CronWatch. robfig/cron logs `start`, `added` and `removed` from its run loop, which is how entries added or removed later are followed: each starts a sync in a goroutine of its own (the loop holds the cron's lock while it logs), declaring the entries and unscheduling the jobs gone. A `cron.WithChain` or `cron.WithLogger` given after Watch replaces CronWatch's; a sync that finds entries none of which were wrapped reports that once.

Names: `robfigcron.Named(name, job, options...)`, or `Watcher.Func(name, fn, options...)`; else a `FuncJob`'s function name without its package's path (`jobs.NightlyReport`, a method value `jobs.Reporter.Run`, `bridge.FuncName`); else the job's type (`jobs.Nightly`). A function literal (`main.main.func1`) is refused and reported, since its name moves with the code around it; so is a name CronWatch does not take. `Options.Jobs` gives options by name and `Options.Exclude` leaves names out. A robfig/cron job has no context and returns nothing, so a plain job fails only by panicking, and `cronwatch.Current` is nil in it; `Watcher.Func` makes a job from a `cronwatch.JobFunc`, which gets the run's context and `JobContext` and fails the run with an error, and records its own runs even where the chain was replaced.

Schedules (`robfigcron.Convert`) are read from the parsed `cron.Schedule`, since robfig/cron keeps no spec text: a `SpecSchedule`'s bits written as the fields croner reads (`bridge.FieldText`: `*`, `*/n`, lists and ranges), a sixth field for seconds when they are not just 0, in the spec's `CRON_TZ` or else the cron's `Location`; with both days restricted either one matches, in both, and a day written as every value (`1-31`) beside a restricted one, which robfig/cron matches with either, is every day. A `ConstantDelaySchedule` (`@every`) is `every <interval>`. Each cron is checked against the schedule's own `Next` (cached per spec and zone); robfig/cron skips a time a spring-forward gap removes, where croner moves it past the jump, so such a time is refused, as are a zone that is not an IANA zone and a `Schedule` of another type. The tests convert every form robfig/cron parses, refuse the gap, a fixed zone, a custom schedule and a date no month has, and run a cron with runs, panics, a `Func` with an error, entries added and removed while it runs, two apps on one store and a chain replaced.

### gocron v2

`cwgocron.New(cw, cwgocron.Options{...}).Option()` is a `gocron.SchedulerOption` (`cwgocron.Watch`, the same in one call, is deprecated) (gocron 2.21 or newer, which has `Job.Schedule()`). It adds `WithGlobalJobOptions(WithEventListeners(BeforeJobRuns, AfterJobRuns, AfterJobRunsWithError, AfterJobRunsWithPanic))`: before a run a `RunHandle` is started (trigger `gocron`), after it finished, failed with the error, or failed with `PanicError: <value>` (`cwgocron.PanicError`; `Panic`, its name before 1.0, is a deprecated alias). gocron recovers a panic only for a job with a panic listener, so CronWatch's records the run and panics again with the same value, as the job would have without CronWatch; the error listener that gocron calls after it (with `ErrPanicRecovered`) is left alone. gocron names only the job that ended, so runs of one job at once are paired with their ends in order. gocron keeps one listener of each kind per job, so a job given its own `BeforeJobRuns` (say) replaces CronWatch's for that job; a job whose own panic listener replaced CronWatch's has its panic failed through the error listener (`ErrPanicRecovered`), which CronWatch's own never reaches, since it panics again. A run gocron skips before it starts (singleton mode, a lock held elsewhere) is not a run, but one `BeforeJobRunsSkipIfBeforeFuncErrors` skips has been started by then, since gocron calls it after `BeforeJobRuns`: it is left running, reported stuck at its timeout, and pairs with that job's next end, so a job with that option is better left out (`Options.Exclude`). A job given its own `AfterJobRuns` or `AfterJobRunsWithError` leaves its runs unfinished the same way. A sync after `Shutdown`, whose `Jobs()` answers nil, takes no job for gone. A task gets no CronWatch context: `cronwatch.Current` is nil in it and its output is empty.

The option is made with `reflect.MakeFunc` on the option's own type: a `SchedulerOption` takes gocron's unexported scheduler, which is a `gocron.Scheduler`, and that is how the watcher keeps hold of it without a second line. The global job option is wrapped the same way to start a sync (after a tenth of a second, so the scheduler holds the job) whenever gocron adds or updates a job; a job removed is unscheduled at the next sync (the next unknown job's run, or `Sync`). A run of a job not declared yet is declared from the store (`Watch.Fallback`) until the sync gives it its schedule. Names are gocron's (`WithName`, else the function's full name, which `bridge.FuncName` shortens); `Options.Jobs` and `Options.Exclude` are by that name.

Schedules (`cwgocron.Convert`, from `Job.Schedule()`): a cron job's crontab parsed as gocron parses it (with `CRON_TZ=` and the scheduler's zone put in front, and the seconds parser, which takes five fields too) and converted as robfig/cron's, since gocron runs it with robfig/cron; a duration job as `every <duration>`; daily, weekly and monthly jobs of an interval of 1 as a cron of their times of day (when they are every combination of their hours, minutes and seconds, as a cron's fields are), days of the week, and days of the month (`-1` as `L`), checked against gocron's own rule for a time of day, `time.Date` in the scheduler's zone, which the tests hold to gocron's own `NextRuns` on a fake clock around New York's clock changes and a month's end. `time.Date` puts a time a spring-forward gap removes an hour early (02:30 at 01:30 standard time), where croner moves it past the jump, so such a time is refused. Anything else (a random duration, an interval of more than 1, other days from the end, a one-time job, a custom `Cron`) is watched without a schedule and reported once. The zone is the scheduler's: gocron has no getter, so it is read from a job's next run once the scheduler has started (gocron gives it in its zone), else `Options.Location`, else `time.Local`, gocron's default; an `Options.Location` that turns out not to be the scheduler's is reported. What gocron's options change without showing in a job's definition is not seen: `WithIntervalFromCompletion` (CronWatch counts an interval from a run's start), `WithStartAt`, `WithStopAt`, `WithLimitedRuns`, and a daylight saving policy other than the default. The panic test runs the scheduler in a child process, since the panic ends it.

### River

River's periodic jobs keep their schedule and constructor unexported, so `cwriver.Watcher.PeriodicJob(schedule, constructor, opts, jobOptions...)` stands in for `river.NewPeriodicJob`, taking the same arguments and CronWatch's options after them. It declares the job, named by the periodic job's `ID`, else the kind its constructor's args have (the constructor is called once more to learn it), and wraps the constructor so each job it inserts carries `"cronwatch": "<name>"` in its metadata beside the constructor's own (River takes metadata from the insert options only). A River schedule is a `PeriodicSchedule` River asks from `time.Now()`: a robfig/cron schedule (`cron.ParseStandard`, which River's documentation uses) is converted by `robfigcron.Convert` in the process's zone, and a schedule whose next fire is always the same time after the time asked, at five times from a sub-second offset to three years on (`river.PeriodicInterval`), is `every <interval>`; `river.NeverSchedule` and schedules of the app's own are reported and watched without one. `Sync`, which the check worker runs, declares the periodic jobs made in this process and unschedules this app's others; every process of one app makes the same periodic jobs, as River asks every client to be configured. River's bundle can change while the client runs (`client.PeriodicJobs()`: `Add`, `Remove`, `RemoveByID`, `Clear`), which the watcher cannot see, so it keeps its periodic jobs by ID: one made again with the ID of an earlier one replaces it (one entry, the new schedule, where two once made a clash watched without a schedule), and `Watcher.Remove(jobs...)`, `RemoveByID(ids...)` and `Clear()`, called beside the bundle's own, take them out, each job no periodic job holds losing its schedule at once. Periodic jobs without an ID are kept as made, several of one kind on different schedules still one job without a schedule.

`Watcher.Middleware()` is a `rivertype.WorkerMiddleware` for `river.Config.Middleware` (River 0.44.1 is the oldest supported; 0.45 and newer need Go 1.26). It records each attempt of a job carrying the metadata, and of the kinds `Options.Kinds` names (runs of a job named after the kind), with `job.Run` around the rest of the stack, so the worker's context carries the run's `JobContext` and the job's timeout. A worker process that makes no periodic jobs finds the job in the store (`Watch.Fallback`). Retries follow the rules above; River recovers a panic, which `Run` records and panics again. An attempt that snoozes (`river.JobSnooze`, a `*rivertype.JobSnoozeError`) or cancels itself (`river.JobCancel`, a `*rivertype.JobCancelError`), or whose context River cancelled with `rivertype.ErrJobCancelledRemotely` as its cause (`client.JobCancel` while it runs), is given back (`DiscardWhen`): a snooze did not fail and did not do the work, and it runs again; a cancel was decided by the app, and if the job was due, its schedule reports it missed. Recording a cancel as a failure was weighed and left out: `JobCancel` is often a deliberate stop (a record since deleted), and a failure alert for it would be noise; the owner chose not failed.

`CheckArgs` (kind `cronwatch_check`, one attempt) and `Watcher.CheckWorker()` run `Sync` and a check; `Watcher.CheckPeriodicJob(every)` schedules it. Its runs are never jobs. The tests run a client on the Postgres `CRONWATCH_TEST_PG` names, in a schema of their own: a job failing twice and then succeeding (three runs, one failed alert and its recovery), a snooze, a cancel, a cancel from outside, a panic, a periodic job's run under its ID, and the check unscheduling a job a periodic job no longer holds; and a worker that makes no periodic jobs keeping the scheduler's definition.

### Asynq

Asynq's scheduler keeps its entries unexported, so `cwasynq.Watcher.NewScheduler(redisOpt, opts)` (and `NewSchedulerFromRedisClient`) make asynq's own `*asynq.Scheduler`, embedded in a `cwasynq.Scheduler` whose `Register` and `Unregister` also declare the entry's task type as a job (`RegisterWith` takes CronWatch's options too). `Watcher.NewPeriodicTaskManager(opts)` wraps the manager's config provider, so the configs are declared each time the manager reads them (at start and every `SyncInterval`), and a config dropped is unscheduled. The cronspec is parsed as Asynq's scheduler parses it (robfig/cron's standard parser: five fields, descriptors, `@every`, `CRON_TZ=`) in the scheduler's `Location` (UTC by default, as Asynq's) and converted by `robfigcron.Convert`. The task type is the job's name; two entries of one type on different cronspecs are one job without a schedule. The check task never is a job.

`Watcher.Middleware()` is an `asynq.MiddlewareFunc` for the server's `ServeMux`. It records each attempt of a task whose type a scheduler in this process declared, whose type `Options.Tasks` names, or whose type the store holds as this app's job (a server in a process of its own finds the scheduler's jobs there, looked up once a minute per type, a type that is not one remembered for that minute). Retries follow the rules above: `asynq.SkipRetry` is a failure (Asynq archives the task), a panic is recorded and panicked again for Asynq to recover, and `asynq.RevokeTask` (the task neither retried nor archived) is given back. `cwasynq.CheckTask()` (type `cronwatch:check`, no retries) and `Watcher.CheckHandler()` unschedule this app's jobs no scheduler here runs and check; schedule it with the scheduler. Asynq 0.25.1 is the oldest supported and 0.26.0 the newest tested. The tests convert cronspecs, declare entries and collisions, give back a revoke, record retries, `SkipRetry` and a panic through the middleware, have a server in a process of its own keep the scheduler's definition (and another app's server leave it alone), and run a real server, scheduler and periodic task manager on the Redis `CRONWATCH_TEST_REDIS` names.

### A plain crontab

A program a crontab runs needs no integration: it declares its job, runs it with `job.Run`, and exits non-zero on the error `Run` returns, and a second crontab line runs a check (`cw.Check`), both on a store both processes reach. `examples/crontab` is that program, in a module of its own so its SQLite driver stays out of the core module, with a test that runs its two commands on one file. A program that stays up checks in itself with `cw.StartChecking(every)`: a goroutine that checks after a second and then every `every` (a minute when 0, five seconds at least) until `Stop` or `Close`; one process is enough, and more are harmless, since a check judges each run once. A command-line tool that wraps a shell command (`cronwatch run nightly -- ./backup.sh`) was left for the owner to ask for: it would need a driver, so it would be a module of its own under `cmd/`.

## Storage

`MemoryStore` is `stores/memory.ts`: a mutex, deep copies in and out, names sorted by byte order (as the SQL stores sort), the same prune rule (each job's newest run is kept whatever its age).

`sqlstore.New(db, dialect, sqlstore.Prefix(p))` keeps the same three tables in the app's database through `database/sql`, with the app's driver and `*sql.DB`: this package imports no driver, so the core module requires none. The SQLite and Postgres dialects are `stores/sql.ts` text for text (the same `CREATE` statements, so `sqlite_master` reads the same whoever created the tables; the same statements, `$n` placeholders for Postgres; `BIGINT` times, `JSONB`, `BIGSERIAL seq` breaking ties, names sorted `COLLATE "C"`; `init` under `pg_advisory_xact_lock(hashtext('cronwatch:<prefix>'))` so many processes can start at once), and the MySQL dialect is the PHP port's (MySQL 8.0.13 or MariaDB 10.6 or newer: `utf8mb4_bin` so names are byte-compared, JSON as `LONGTEXT` holding the SDK's JSON byte for byte, never MySQL's `JSON` type, which would rewrite it, `ON DUPLICATE KEY`, the prune's newest start per job as a derived table, and compare-and-set from version 0 in two steps). A row of another shape than the SDK writes, valid JSON all the same (another writer's, or a hand edit), is read as the SDK reads it rather than failing every read it is part of: metrics that are not all numbers keep the ones that are, and a definition that is not an object is an empty one; before, one such running run failed every check. A state's version counts as the SDK's `stateVersion()` reads it, in the statements and in `JobState` alike: a whole number from 0 to 2^53 - 1, else 0 (a foreign row's `1.5`, `"x"` or `-1`), so the next update writes over such a row where a cast to `BIGINT` failed every compare-and-set of the job on Postgres, and a comparison refused it for good on SQLite and MySQL; each dialect's `CASE` tests the JSON type before any cast, the Postgres and SQLite text is `sql.ts`'s and the MySQL text is the one every port's MySQL store shares (`sqlstore/sql_internal_test.go` pins them), and `conformance/store.json`'s `foreignVersion` cases are replayed on every dialect with the row written as raw text (`storetest.ReplayForeignVersions`). A version that is not a whole number reads as nil; a whole one outside the range is kept as read and counts as 0. MySQL's `trigger` column is `VARCHAR(255)` (the others are `TEXT`), so a longer trigger is cut to 255 characters there rather than lose the run. A compare-and-set from version 0 whose `INSERT` fails on MySQL reads the row back and counts the write as its own when the row holds exactly what it sent (the insert landed and its answer was lost with the connection), as the PHP port's `stateLanded()` does; counting it as refused had the client work the change out again over its own write, and the alert the first attempt opened never went out. MySQL answers the rows an `UPDATE` changed, not the rows it matched, so an `UpdateRunIf` or a compare-and-set that wrote the values already there reads the row back to tell a landed write from a refused one, as the PHP port does.

On SQLite the store holds one connection of the pool for its statements, in turn: an in-memory database is one per connection, a pool's connections would each need the pragmas, and SQLite allows one writer at a time anyway (the SDK's store has one connection too). That connection is put in WAL mode, with the SDK's retry of a busy database while switching (`busy.ts`), then `busy_timeout` 5000 and `synchronous` NORMAL. On Postgres and MySQL each statement runs on the pool on its own, in autocommit, so the store's writes never join a transaction the app has open (a run recorded inside one survives a rollback), and `DeleteJob` is one transaction of the store's own. Rows are read by column name whatever types the driver hands back (`int64` or text for `BIGINT`, text or bytes for `JSONB` and `LONGTEXT`), and JSON columns are parsed in the order the database gives the keys, as the SDK reads them (Postgres's `JSONB` reorders keys; everything written is the SDK's order).

*Why a module of its own for the tests.* A Go module's `go.mod` lists what its tests import too, and the go command reads that list when an app requires the module, so drivers imported by `sqlstore`'s own tests would reach every app's module graph. The SQL tests therefore live in `packages/go/sqltest`, a module that requires `cronwatch.dev/go` through a `replace` to `../` and the drivers (`modernc.org/sqlite`, pure Go, so the tests need no C toolchain; `github.com/jackc/pgx/v5`'s `stdlib`; `github.com/lib/pq`, for the pg_cron source; `github.com/go-sql-driver/mysql`). Build tags were the other way, and were left out: a tagged test file's imports still go into `go.mod`, so they keep the drivers out of the build but not out of the module graph. The core module's own tests use the memory store and the standard library only.

`sqltest` runs, per dialect, the contract test (`storetest.Run`, the SDK's `store-conformance.ts`), the replay of `conformance/store.json` (`storetest.ReplayFixture`), the finish-once scenarios over several stores on one database, and a client end to end; SQLite always, Postgres, MySQL and MariaDB when `CRONWATCH_TEST_PG`, `CRONWATCH_TEST_MYSQL` and `CRONWATCH_TEST_MARIADB` are set. Its node-compat test has the built SDK and `sqlstore` replay the same store calls into two SQLite files and compares what each reads of the other's and every column's bytes and SQLite type, and has a Node client and a Go client take turns on one file and on one job's state version.

## Where it cannot match the SDK

- In the process's own zone (no `timezone`), a wall-clock time in a gap is found by croner's `fromTZ` rule, as it is for a named zone, where JavaScript's local `Date` uses the offset before the transition. The two agree for one-hour gaps; the conformance fixtures run in UTC. The process zone is `time.Local`.
- Croner accepts any zone when it reads an expression and fails on a bad one only when asked for a fire time; the port's parser checks the zone at once. Declaring a job with a bad zone gives the SDK's message either way (`job "x": timezone "Mars/Base" is not an IANA timezone`); a stored definition another writer gave a bad zone is unevaluable in both.
- Zone names are matched without regard to case, as `Intl` does, through the zone database Go reads (`$ZONEINFO`, the system's, or `time/tzdata` when the app imports it). Fixed offsets (`+05:30`) are zones too, as Node 24's `Intl` and croner accept them.
- Go errors carry no stack, so a failed run's error has frames only when it was a panic. Error names follow Go's types (see Rules), not JavaScript's classes.
- A value logged or panicked that is not a string, a number or an error is written as JSON through `encoding/json` (with HTML escaping off): Go's field names and sorted map keys, where a JavaScript object would have its own.
- Two goroutines recording the same finished run from a source at once judge it once, as two SDK promises do, but the SDK's second promise always reports the run as already finished, while a goroutine that reads it after the first finish landed leaves it alone without a word.
- A channel or triage that has not returned past its timeout gets nothing more until it does (see Delivery); the SDK calls it again for the next alert.
- The finish and the rest of a run are recorded even when the caller's context is cancelled (see The Go API); the SDK has no such context.
- Go's HTTP client writes request headers sorted by name, in its canonical case (`X-Api-Key`), not in the order the SDK gives them in lowercase; HTTP reads both the same, and the tests compare each header's name and value. Its own `User-Agent` (`Go-http-client/1.1`) and `Accept-Encoding: gzip` stand where fetch sends `node` and its own list, and triage's user agent is `cronwatch-go/<version>`.
- A redirect is an answer outside 2xx (`... answered 307`), where fetch with `redirect: "error"` throws `fetch failed`; either way nothing is sent where it points and the send fails, as in the other ports. A request that gets no answer fails with `<origin>: <Go's error>` (`dial tcp 127.0.0.1:1: connect: connection refused`) in place of fetch's `fetch failed`.
- The webhook's extra headers are a map, sent in name order, so two names that differ only in case are both sent, as fetch appends them, but in that order rather than as written.
- A request whose target holds an escape that is not one (`/jobs/%zz`) is answered `400 Bad Request` by Go's HTTP server itself, as plain text, before any handler sees it; the dashboard answers such a path with the SDK's page or JSON when it is handed one (a test, an adapter). A byte beyond ASCII sent raw in a path is escaped as that byte, where Node's server reads the target as Latin-1 and escapes each character's UTF-8; browsers escape before sending, so only a hand-made request differs.
- The dashboard's locked page and a handler's 503 name the Go API (`cronwatch.WithToken`, `cronwatch.WithoutToken()`, `cronwatch.WithoutSecret()`), and so does the handler's report to the error handler (`handler refused a request ...`), where the SDK names its options.
- A host outside ASCII longer than 1024 bytes (in a `Host` or `X-Forwarded-Host` header, or an origin given) is not read as a URL, where Node's parser punycodes any length: punycode's time grows with a label's length times its distinct characters, and a request's `Host` is anyone's to send before the token is checked, so a megabyte of them took seconds. No name DNS can hold (253 bytes) comes near it.
- A dashboard request whose context ended before its answer (the caller gave up) is answered 500 without a report to the error handler, since it failed for that alone; the SDK has no request context.
- A body past 1 MiB is answered 413 (see Dashboard); the SDK leaves the limit to the server in front of it. A handler never reads the body; the function reads it as it likes.
- An interval longer than 2^53 ms (`every 20000000000w`) is held at 2^53 ms (some 285,000 years), where JavaScript adds any number to a time: an `int64` of milliseconds would wrap, and drawing the board's timeline once never ended. (A silence ends as the SDK's `silenceEnd` says, on a whole millisecond held at 2^53 - 1, and a stored time past an `int64` reads as its end, not as whatever the platform's conversion gives.) A timeout past what a `time.Duration` holds (some 292 years) is held there, where the conversion wrapped on amd64 and ended the job's context as it started.
- A run's duration is the SDK's `runDuration`: 0 for a start after the finish, and at most 2^53 - 1 ms, worked out without wrapping an `int64` (a foreign row's `started_at` of the lowest `BIGINT` is stuck, and times out with that duration, where the subtraction wrapped and the SDK wrote a duration Postgres refused on every check). Elapsed times shown or compared (the stuck check, a stuck alert's text, the timeline) are worked out in `float64`, as JavaScript does.
- A time before the year 1 or after 9999 (a start read from such a row) is not written as a date, as in the SDK: alert text and triage prompts read "before 0001-01-01 00:00:00 UTC" or "after 9999-12-31 23:59:59 UTC" with no relative part, the timeline "before 1 Jan 0001 00:00" or "after 31 Dec 9999 23:59", and a tracker's `run.startedAt` is null (`js.ISOTime`, `js.BeyondDates`, `js.Stamp`).
- A handler's function that writes a status of 400 or more fails its run with `HTTP <status>` and Go's text for the status (`HTTP 404 Not Found`), where a fetch `Response` made without a `statusText` gives `HTTP 404`; a returned `*http.Response` gives its own `Status`. A panic with `http.ErrAbortHandler`, or one after the function began its own answer, aborts the response once the run is recorded, where the SDK has neither.
- The SDK has no scheduler integrations or `RunDeleter`; the integrations follow the gem's and the Python and PHP ports' (see Scheduler integrations). A run given back with `DiscardWhen` leaves no row, which the SDK cannot do.
- A gocron task and a plain robfig/cron job get no context from their scheduler, so `cronwatch.Current` is nil inside them and a run's output is empty (a `robfigcron` `Func` has both); gocron names only the job a run of which ended, so runs of one job at once are paired with their ends in order, and its options that change when a job runs without showing in its definition are not seen.
- A scheduler's time that a spring-forward gap removes is not converted (robfig/cron skips it, gocron's `time.Date` runs it an hour early, croner moves it past the jump), and the job is watched without a schedule, as the Python port does for APScheduler.
- Bytes that are not UTF-8 in a form or JSON body become one U+FFFD each, where the WHATWG decoder replaces each maximal invalid sequence with one. A host outside ASCII in `WithOrigin` or a forwarded header is lowercased and written in punycode without UTS 46's other mappings (full-width letters, say).
- The dashboard's base path is found from the mount before falling back to the SDK's `/cronwatch` (see Dashboard), as the gem's and the Python package's are.
- A source can only tell a job's options changed from the definition they store, so a job given `ExpectFunc` with a different function is not declared again (both store `custom function`); the SDK compares the function's source text.
