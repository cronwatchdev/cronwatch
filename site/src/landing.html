CronWatch records every run of your scheduled jobs in your own database, and speaks up when one is missed, fails, gets stuck, runs slow or costs too much.

It is a library, not a service. No server to run, no account to make, and run history that stays in your database. An alert carries the error and the last lines of output to the channels you pick, and to Anthropic only if you turn on triage. MIT licensed.

Failure

When a job fails, cron says nothing. CronWatch tells you what broke.

Example: a nightly invoice job

A handler that answers 4xx or 5xx counts as failed too, and so does a run whose output does not contain what you told it to expect: the job that exits cleanly and did nothing. Turn on triage with an Anthropic API key, and each alert carries a diagnosis of two to four sentences.

Code

Say it where the job lives.

One client per app, each job declared once, and a wrapper around the work. The schedule, the grace period and the timeout sit next to the code they describe, and every run lands in the SQLite, Postgres, MySQL or D1 database you already have.

app/api/cron/nightly/route.tsTypeScript

import { cronwatch } from "@cronwatch/sdk";
import { sqlite } from "@cronwatch/sdk/sqlite";  // npm install better-sqlite3
import { slack } from "@cronwatch/sdk/slack";

const cw = cronwatch({
  store: sqlite({ path: "./data/cronwatch.db" }),
  alerts: [slack({ webhookUrl: process.env.SLACK_WEBHOOK_URL! })],
});

const nightlyReport = cw.job("nightly-report", {
  schedule: "0 2 * * *",
  grace: "15m",
});

export const GET = nightlyReport.handler(async (job) => {
  const report = await buildReport();
  job.log("Report written:", report.path);
});

It runs wherever a fetch handler or an async function does, and in every language it can wrap a plain script run from crontab.

Checks

It notices what never ran.

Nothing threw and nothing ran, so nothing was logged. That is the failure cron never reports, and the one a check finds. The same check catches the run that started and never finished. The run that cost three times its median is caught when it reports.

Every condition sends one message when it opens. When a successful run leaves nothing open, one recovered message names everything that was. A job that fails all night pages you once, and the fix announces itself.

The check runs every few minutes, from wherever suits the app:

Conditions

Five conditions and a recovery. That is the whole product.

  • missedA run was due and none started within the grace period. Cron expressions, @hourly, or every 15m, in any timezone.
  • failedThe function threw, the handler answered 4xx or 5xx, or the output did not satisfy expect.
  • stuckA run started and was still going past its timeout, or never reported finishing. A killed process, a serverless timeout, a deploy mid-run.
  • slowA successful run took longer than maxDuration, or more than twice the job’s own recent p95.
  • over_budgetOn a successful run, a number you reported with job.metric() went above its ceiling, or three times its median.
  • recoveredA successful run left nothing open. One message, naming everything that was.

Agents

Ask your coding agent what failed, and why.

CronWatch comes with an MCP server, so Claude Code, Cursor or any MCP client reads the same records you do. It can tell you what broke overnight, read the error and the output, and silence the job while it ships the fix.

claude mcp add cronwatch -e CRONWATCH_URL=https://yourapp.com/cronwatch -e CRONWATCH_TOKEN=your-token -- npx -y @cronwatch/mcp

CRONWATCH_URL is where your app mounts the dashboard. CRONWATCH_TOKEN is the token your app reads from its own CRONWATCH_TOKEN; in development, the app prints a sign-in link with one on its first request. More in the MCP docs.

Why

Why a library, and not a service.

A hosted monitor works by your app pinging their servers, which then alert you. You pay for it with a monthly bill, an account, and a copy of your job output on someone else’s machine.

CronWatch lives in the app that runs the jobs. It writes every run to the database you already have, and sends each alert straight from your app to Slack, Discord, email, SMS, a webhook, or your error tracker.

{{VERSUS}}

It cannot see an app that is down entirely, so pair it with a simple uptime monitor for that.
