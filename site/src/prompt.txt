Add CronWatch to this project so that every scheduled job is recorded and I am
told when one is missed, fails, gets stuck, runs slow or goes over budget.

CronWatch is an open source library: @cronwatch/sdk for TypeScript (Node,
Cloudflare Workers, Deno, Bun), the cronwatch gem for Ruby and Rails,
cronwatch-sdk for Python (Django, Celery, APScheduler), cronwatch/cronwatch
for PHP (Laravel, Symfony, WordPress, Drupal, Craft CMS), and cronwatch.dev/go for
Go (robfig/cron, gocron, River, Asynq). It runs inside my app and writes to
my own database. There is no hosted service, no account and no API key.

First decide which one this project needs. A package.json with a Node server,
Next.js or other JavaScript runtime means the TypeScript steps below; a
wrangler.toml (or wrangler.jsonc) means Cloudflare Workers, which follow the
same steps with the Workers notes in each. A Gemfile
means the Ruby steps (a Rails app follows them as written; plain Ruby, see
https://cronwatch.dev/docs/ruby/). A pyproject.toml, requirements.txt or
manage.py means the Python steps. A composer.json or wp-config.php means the
PHP steps (artisan is Laravel, bin/console Symfony, wp-config.php WordPress,
drupal/core-recommended in composer.json Drupal, craftcms/cms Craft CMS). A go.mod
means the Go steps (github.com/robfig/cron/v3, github.com/go-co-op/gocron/v2,
github.com/riverqueue/river or github.com/hibiken/asynq in it names the
scheduler). If the scheduled jobs live in more than one,
set up each side where its jobs run; they can share one database.

TypeScript and Node

1. Install it with the driver for the store you will use in step 2 (it needs
   Node 22 or newer). The drivers are optional peers, so install one yourself.

   npm install @cronwatch/sdk better-sqlite3     # for sqlite
   npm install @cronwatch/sdk pg                 # for postgres
   npm install @cronwatch/sdk                    # for d1 on Workers: no driver

2. Create one client for the whole app, in its own module, and export it.
   Pick the store that matches this project: sqlite for a long running server,
   postgres for serverless or anything with more than one instance, d1 on
   Cloudflare Workers.

   import { cronwatch } from "@cronwatch/sdk";
   import { sqlite } from "@cronwatch/sdk/sqlite";      // or: postgres from "@cronwatch/sdk/postgres"
   import { slack } from "@cronwatch/sdk/slack";
   // Other channels, one import each: discord, webhook, resend, postmark,
   // sendgrid, mailgun, ses, twilio, sentry, honeybadger, datadog, rollbar,
   // bugsnag, newrelic. Omit alerts for the console.

   export const cw = cronwatch({
     store: sqlite({ path: "./data/cronwatch.db" }),
     alerts: [slack({ webhookUrl: process.env.SLACK_WEBHOOK_URL! })],
   });

   On Workers there is no module-level env: make the client inside the
   handler with store: d1(env.DB) from "@cronwatch/sdk/d1", passing every
   secret from env. See https://cronwatch.dev/docs/cloudflare/

   If the project uses pg_cron (Supabase Cron included), add
   sources: [pgCron(pool)] from "@cronwatch/sdk/pg-cron" with a pg Pool on
   that database; each check then reads pg_cron's own tables. Do not declare
   those jobs yourself. See https://cronwatch.dev/docs/supabase/

3. Declare each scheduled job once, next to the code that runs it. The schedule
   is a cron expression, "@hourly", or "every 15m". Add a grace period, and a
   timeout for anything that can hang.

   export const nightlyReport = cw.job("nightly-report", {
     schedule: "0 2 * * *",
     timezone: "UTC",
     grace: "15m",
     timeout: "20m",
   });

4. Wrap the work. In a route handler use .handler(); anywhere else use .run().
   .handler() checks the Authorization bearer against CRON_SECRET for you, and
   answers 503 without running when CRON_SECRET is unset outside development.

   export const GET = nightlyReport.handler(async (job) => {
     const report = await buildReport();
     job.log("Report written:", report.path);
     job.metric("pages", report.pages);
   });

   .handler() and cw.routes() are fetch handlers. For Express, Koa, NestJS
   or a plain Node server, wrap them with toNodeHandler (or toKoaMiddleware)
   from "@cronwatch/sdk/node".

5. Make missed and stuck runs detectable. A job that never fires cannot report
   itself, so something has to look. In a long running server call cw.start()
   once at boot. On serverless, mount the routes and point a cron at the check
   endpoint every few minutes. On Workers, give the check a Cron Trigger of
   its own that calls cw.check() in scheduled(); never cw.start() there.

   // app/cronwatch/[[...path]]/route.ts in Next.js; elsewhere mount it at
   // /cronwatch or pass basePath to cw.routes()
   export const { GET, POST, DELETE } = cw.routes({ token: process.env.CRONWATCH_TOKEN });
   // then: GET /cronwatch/api/check every 5 minutes, with the bearer token

6. Set the environment variables you referenced: CRON_SECRET, CRONWATCH_TOKEN,
   and whichever alert channel you chose. Do not invent other names.

Ruby on Rails (Ruby 3.2 or newer, Rails 7.2 or newer)

1. Install the gem, generate the migration and initializer, and migrate:

   bundle add cronwatch
   bin/rails generate cronwatch:install
   bin/rails db:migrate

2. Leave the ActiveRecord store the initializer sets (web, workers and the
   check must see the same runs), and set the alert channel there:

   # config/initializers/cronwatch.rb
   Cronwatch.configure do |c|
     c.store  = Cronwatch::Stores::ActiveRecord.new
     c.alerts = [Cronwatch::Alerts::Slack.new(webhook_url: ENV["SLACK_WEBHOOK_URL"])]
   end

   Other channels under Cronwatch::Alerts: Discord, Webhook, Resend, Postmark,
   Sendgrid, Mailgun, Ses, Twilio, Sentry, Honeybadger, Datadog, Rollbar,
   Bugsnag, NewRelic, Console. Their options: https://cronwatch.dev/docs/ruby/

3. Watch each scheduled job in its class. For ActiveJob:

   class NightlyReportJob < ApplicationJob
     include Cronwatch::ActiveJob
     cronwatch schedule: "0 2 * * *", grace: "15m", timeout: "20m"

     def perform
       cronwatch.log("Report written")
     end
   end

   For a Sidekiq job class, include Cronwatch::Sidekiq after Sidekiq::Job and
   call cronwatch the same way. When the job is scheduled by Solid Queue
   (config/recurring.yml) or sidekiq-cron (config/schedule.yml), use
   schedule: :from_scheduler instead of copying the schedule. To watch every
   entry in that file at once, add Cronwatch.declare_from_scheduler!(grace: "10m")
   to the initializer after Cronwatch.configure.

4. Schedule Cronwatch::CheckJob every 5 minutes, beside the other recurring
   jobs, so missed and stuck runs are noticed. In config/recurring.yml:

   production:
     cronwatch_check:
       class: Cronwatch::CheckJob
       schedule: every 5 minutes

   With sidekiq-cron, add the same class with cron "*/5 * * * *". With neither,
   a crontab line runs bin/rails cronwatch:check every 5 minutes.

5. Mount the dashboard in config/routes.rb (no require needed in Rails):

   mount Cronwatch::Web.new(Cronwatch.client) => "/cronwatch"

   Outside development it needs CRONWATCH_TOKEN. Behind the app's own admin
   auth, pass token: nil instead.

6. Set the environment variables you referenced: CRONWATCH_TOKEN and whichever
   alert channel you chose. Do not invent other names.

Python (Python 3.11 or newer)

1. Install it with the extras for what the project uses:

   pip install "cronwatch-sdk[postgres,django,celery]"

   Extras: postgres, django (Django 5.2 or newer), celery (Celery 5.5 or
   newer), apscheduler (APScheduler 3), anthropic (triage). The import name is
   cronwatch. Add it to the project's own dependency file (pyproject.toml,
   requirements.txt) the way the project already does.

2. Use a store every process shares (web, workers and the check must see the
   same runs): cronwatch.stores.postgres.PostgresStore() (reads DATABASE_URL),
   or cronwatch.stores.SqliteStore("./data/cronwatch.db") on one machine.

   In Django, configure it in settings.py and add the app:

   INSTALLED_APPS += ["cronwatch.django"]
   CRONWATCH = {
       "STORE": "cronwatch.stores.postgres.PostgresStore",
       "ALERTS": [Slack(os.environ["SLACK_WEBHOOK_URL"])],   # from cronwatch.alerts import Slack
       "TOKEN": os.environ.get("CRONWATCH_TOKEN", ""),
   }

   Outside Django, make one client with cronwatch.configure(store=...,
   alerts=[...]) in a module every entry point imports.

   Other channels in cronwatch.alerts: Discord, Webhook, Resend, Postmark,
   Sendgrid, Mailgun, Ses, Twilio, Sentry, Honeybadger, Datadog, Rollbar,
   Bugsnag, NewRelic (and cronwatch.Console). Email senders take from_ (from
   is a Python keyword). Their options: https://cronwatch.dev/docs/python/

3. Watch each scheduled job:

   - Celery: cronwatch.celery.install(app) after the app is made. Every task
     beat schedules is watched with beat's schedule, no task changes. Add
     "cronwatch-check": {"task": "cronwatch.celery.check", "schedule": 300.0}
     to beat_schedule.
   - APScheduler: cronwatch.apscheduler.watch(scheduler) before
     scheduler.start(). Every job is watched with its trigger.
   - Django management commands and cron scripts: declare the job in
     <app>/cronwatch_jobs.py (Django imports it at startup), for example
     nightly = cronwatch.django.client().job("nightly-report",
     schedule="0 2 * * *", timezone="UTC", grace="15m"), and wrap the work:
     with nightly.run() as ctx: ... ctx.log("Report written").
     Outside Django, cw.job(...) the same way. Async functions use
     async with nightly.run().
   - A platform that calls a URL on a schedule: nightly.handler(fn) gives
     .django, .flask, .starlette and .aws_lambda endpoints, which need
     Authorization: Bearer $CRON_SECRET.

4. Run the check every 5 minutes so missed and stuck runs are noticed: the
   Celery beat entry above, or a crontab line running
   python manage.py cronwatch_check (Django) or a script calling cw.check(),
   or cw.start() once in a long-running process. One checker per store.

5. Mount the dashboard: in Django,
   path("cronwatch/", include("cronwatch.django.urls")) in urls.py; elsewhere
   cw.routes() is a WSGI app (.asgi for FastAPI and Starlette) to mount at
   /cronwatch. Outside development it needs CRONWATCH_TOKEN. Behind the app's
   own admin auth, pass token=None (TOKEN: None in Django) instead.

6. Set the environment variables you referenced: CRONWATCH_TOKEN,
   CRON_SECRET if you added a handler, and whichever alert channel you chose.
   Do not invent other names.

PHP (PHP 8.2 or newer)

1. Pick the steps for the framework. Each records every run in the app's own
   database through a connection of its own, and needs no other service.

   - WordPress: install and activate the CronWatch plugin
     (wp plugin install cronwatch --activate). Every WP-Cron event is watched
     with no code. Set the alert channel under CronWatch, Settings. If the
     site is not visited every few minutes, add define('DISABLE_WP_CRON',
     true) to wp-config.php and crontab lines running
     wp cron event run --due-now and wp cronwatch check every 5 minutes.
     Stop there: skip steps 2 to 5.
   - Laravel: composer require cronwatch/cronwatch, then php artisan migrate.
     Every task in the schedule is watched, named after its command (give
     closures a ->name()), and cronwatch:check is scheduled for you. Set
     CRONWATCH_SLACK_WEBHOOK_URL or CRONWATCH_MAIL_TO in .env.
   - Symfony: composer require cronwatch/cronwatch, add
     Cronwatch\Symfony\CronwatchBundle::class => ['all' => true] to
     config/bundles.php, and config/packages/cronwatch.yaml with
     cronwatch: { alerts: { slack: '%env(CRONWATCH_SLACK_WEBHOOK_URL)%' } }.
     Every Scheduler message is watched, and the check is added to the
     default schedule, so the worker consuming scheduler_default runs it.
   - Drupal: composer require drupal/cronwatch, drush pm:install cronwatch.
     Every cron run and each module's hook_cron is watched. Set the alert
     channel and the cron schedule under Configuration, System, CronWatch.
   - Craft CMS: composer require cronwatch/craft,
     php craft plugin/install cronwatch. List the console commands the
     crontab runs, with their schedules, and the queue job classes to watch,
     in config/cronwatch.php ('commands' => ['resave/entries' =>
     ['schedule' => '0 3 * * *']], 'queueJobs' => [...]).
   - Anything else (crontab scripts, Slim, a plain PHP app):
     composer require cronwatch/cronwatch.

2. Outside the frameworks, make one client in cronwatch.php at the project's
   root that requires vendor/autoload.php, declares every job and returns
   the client:

   $cw = new Cronwatch\Cronwatch(
       store: new Cronwatch\Store\MysqlStore(getenv('DATABASE_URL')),   // or SqliteStore('/var/lib/app/cronwatch.db'), PostgresStore(...)
       alerts: [new Cronwatch\Alerts\Slack(getenv('SLACK_WEBHOOK_URL'))],
   );
   $cw->job('nightly-report', ['schedule' => '0 2 * * *', 'timezone' => 'UTC', 'grace' => '15m']);
   return $cw;

   Other channels under Cronwatch\Alerts: Discord, Webhook, Resend,
   Postmark, Sendgrid, Mailgun, Ses, Twilio, Sentry, Honeybadger, Datadog,
   Rollbar, Bugsnag, NewRelic, with named arguments. Their options:
   https://cronwatch.dev/docs/php/

3. Watch each scheduled job:

   - Laravel: nothing to do for scheduled tasks; options per task with
     ->cronwatch(['name' => 'nightly-report', 'grace' => '15m']), or
     ->cronwatch(false) to leave one out. Queued jobs opt in with
     #[Cronwatch\Watch(grace: '15m')] on the class.
   - Symfony: nothing to do for scheduled messages; options with
     #[Cronwatch\Watch(...)] on the message class. Messenger messages that
     workers handle opt in with the same attribute.
   - Drupal: queue workers opt in under the settings or with
     #[Cronwatch\Watch] on the worker class.
   - Craft CMS: the commands and queueJobs lists above.
   - A crontab script: $cw = require 'cronwatch.php'; then
     $cw->job('nightly-report', [...])->run(function ($job) { ...
     $job->log('Report written'); }).
   - A platform that calls a URL: $cw->job(...)->handler($fn), then
     ->serve() in a bare script, ->laravel() as a Laravel route action, or
     called with the request in a Symfony controller. It needs
     Authorization: Bearer $CRON_SECRET.

4. Run the check every 5 minutes so missed and stuck runs are noticed:
   Laravel schedules php artisan cronwatch:check itself, Symfony adds it to
   the default schedule, Drupal runs it after each cron run (add
   drush cronwatch:check to the crontab too), Craft CMS needs a crontab line
   running php craft cronwatch/check, and a plain app a crontab line running
   vendor/bin/cronwatch check (which loads cronwatch.php). One checker per
   store.

5. The dashboard: Laravel serves it at /cronwatch behind the viewCronwatch
   gate (define it for your admins); Symfony imports
   '@CronwatchBundle/config/routes.php' under /cronwatch in
   config/routes/cronwatch.yaml behind access_control; Drupal and Craft CMS put
   it in their admin. In a plain app, a public/cronwatch.php requiring
   cronwatch.php and calling $cw->routes()->serve(). Outside development it
   needs CRONWATCH_TOKEN; behind the app's own admin auth, pass
   routes(token: false) instead.

6. Set the environment variables you referenced: CRONWATCH_TOKEN,
   CRON_SECRET if you added a handler, and whichever alert channel you chose.
   Do not invent other names.

Go (Go 1.25 or newer)

1. Install the module, and the integration for the scheduler the project
   uses, if any:

   go get cronwatch.dev/go
   go get cronwatch.dev/go/robfigcron     # or cronwatch.dev/go/gocron, /river, /asynq

   The package is cronwatch: import cronwatch "cronwatch.dev/go". The module
   requires no database driver; the SQL store works over the project's own
   *sql.DB with the driver it already uses.

2. Make one client at startup and pass it to whatever needs it. Use a store
   every process shares (web, workers and the check must see the same runs):

   store, err := sqlstore.New(db, sqlstore.Postgres)   // "cronwatch.dev/go/sqlstore"; or sqlstore.SQLite, sqlstore.MySQL
   slack, err := alerts.Slack(alerts.SlackOptions{WebhookURL: os.Getenv("SLACK_WEBHOOK_URL")})   // "cronwatch.dev/go/alerts"
   cw, err := cronwatch.New(cronwatch.WithStore(store), cronwatch.WithAlerts(slack))

   Other channels in cronwatch.dev/go/alerts, each made from an options
   struct: Discord, Webhook, Resend, Postmark, Sendgrid, Mailgun, SES,
   Twilio, Sentry, Honeybadger, Datadog, Rollbar, Bugsnag, NewRelic. Their
   options: https://cronwatch.dev/docs/go/

   If the project uses pg_cron, add
   cronwatch.WithSources(pgcron.New(db, pgcron.Options{})) from
   "cronwatch.dev/go/pgcron". Do not declare those jobs yourself.

3. Watch each scheduled job:

   - robfig/cron: cron.New(robfigcron.Watch(cw, robfigcron.Options{})), the
     cron's other options after it. Every entry is watched with its spec,
     named after its function; name a closure with
     robfigcron.Named("nightly-report", cron.FuncJob(fn)).
   - gocron v2: gocron.NewScheduler(cwgocron.Watch(cw, cwgocron.Options{}))
     with import cwgocron "cronwatch.dev/go/gocron". Name closures with
     gocron.WithName.
   - River: w := cwriver.New(cw, cwriver.Options{}) (import cwriver
     "cronwatch.dev/go/river"); w.PeriodicJob(...) in place of
     river.NewPeriodicJob(...), w.Middleware() in river.Config.Middleware,
     and river.AddWorker(workers, w.CheckWorker()) with
     w.CheckPeriodicJob(5 * time.Minute) among the periodic jobs.
   - Asynq: w := cwasynq.New(cw, cwasynq.Options{}) (import cwasynq
     "cronwatch.dev/go/asynq"); w.NewScheduler(...) in place of
     asynq.NewScheduler(...), mux.Use(w.Middleware()) on the server,
     scheduler.Register("*/5 * * * *", cwasynq.CheckTask()) and
     mux.Handle(cwasynq.CheckType, w.CheckHandler()).
   - A program a crontab runs: declare the job with
     cw.Job("nightly-report", cronwatch.Schedule("0 2 * * *"),
     cronwatch.Timezone("UTC"), cronwatch.Grace("15m")) and wrap the work in
     nightly.Run(ctx, func(ctx context.Context, job *cronwatch.JobContext)
     error { ... job.Log("Report written"); return err }), exiting non-zero
     on the error Run returns.
   - A platform that calls a URL: mux.Handle("POST /api/cron/nightly",
     nightly.Handler(fn)), or lambda.Start(cronwatch.Lambda(handler)) on AWS
     Lambda. It needs Authorization: Bearer $CRON_SECRET.

4. Run the check every 5 minutes so missed and stuck runs are noticed:
   cw.Start(time.Minute) once in a long-running process (robfig/cron and
   gocron apps included), the River or Asynq check job above, or a second
   crontab line running a command that declares the same jobs and calls
   cw.Check(ctx).

5. Mount the dashboard: routes, err := cw.Routes(), then
   mux.Handle("/cronwatch/", routes). Outside development it needs
   CRONWATCH_TOKEN; behind the app's own admin auth, pass
   cronwatch.WithoutToken() instead.

6. Set the environment variables you referenced: CRONWATCH_TOKEN,
   CRON_SECRET if you added a handler, and whichever alert channel you chose.
   Do not invent other names.

Rules for you:
- Declare every existing scheduled job in this project, not just one. Find them
  in cron config, workflow files, queue schedulers and any crontab.
- Use the real schedules already in use. Do not change when anything runs.
- Keep the job names stable and human readable; they are the identity of the
  job across restarts and deploys.
- Do not add a retry loop or an uptime ping. CronWatch records what happened; it
  does not re-run work.
- If this project already has a dashboard route or auth, mount cw.routes()
  or Cronwatch::Web behind that auth with its token set to null (nil in Ruby,
  None in Python, false in PHP, cronwatch.WithoutToken() in Go) rather than
  exposing it.
- Make sure the process that runs the check knows every job it should expect,
  or a job that never starts at all goes unnoticed. If installs differ, declare
  a job there only where that install runs it.
- Work that starts in one call and finishes in another (a webhook, a queue
  step, a workflow) uses await job.start({ id }) where it begins and
  (await job.resume(id)).finish() where it ends, with the same id both times
  ($job->start(id: $id) and $job->resume($id)->finish() in PHP;
  job.Start(ctx, cronwatch.WithRunID(id)) and job.Resume(ctx, id), then
  Finish(ctx), in Go).
- A job that runs where the network or the app's secrets are unavailable gets
  its own client with deliver: "check" (deliver = :check in Ruby,
  deliver="check" in Python, deliver: 'check' in PHP,
  cronwatch.WithDeliver(cronwatch.DeliverAtCheck) in Go) and the same
  store; the next check sends its alerts.
