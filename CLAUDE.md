- Use Node 24 (`.nvmrc`); better-sqlite3 13 needs Node 22 or newer. Run `npm run check` before committing: it runs the dash check, typecheck and tests. Postgres store tests run when `CRONWATCH_TEST_PG` is set; CI provides one.

- Alert logic lives in `packages/sdk/src/evaluate.ts` as pure functions; keep side effects in `client.ts`. Every condition opens once and closes with a recovery; do not add repeat alerts without a design discussion.
- The site is hand-written HTML and CSS plus markdown docs built by `site/build.mjs` (marked only). Type is Calluna for anything a person reads and Auger Mono for anything a machine printed, both from the owner's Adobe Fonts kit (`use.typekit.net/gie6nes.css`, in `style-src` and `font-src`; the CSP's one other origin is `analytics.joncp.dev`, the owner's Runlight analytics, in `script-src` and `connect-src`, loaded on every page but the contact form's; `scripts/check-links.mjs` fails when a page loads from an origin the CSP in `deploy/nginx.conf` does not allow, or the CSP allows a script origin no page uses). The dashboard that ships in the packages keeps its own font stack. The landing page is set like a printed sheet in neutral greys (colour only for the states the library reports): dark by default (light is the toggle; `data-theme="dark"` is on `<html>` and `theme.js` removes it for a stored light choice), a serif for prose, and a small mono label down the left of each section. Its spine is the dashboard's last-24-hours timeline and jobs board, shown in a flat browser frame and redrawn as SVG by `build.mjs` from the captured page `site/src/demo/dashboard.html`; every mark, alert, reply and board row that claims to be output comes from the captures in `site/src/demo` (`node site/scripts/demo.mjs --capture`, run with `TZ=UTC` after building the packages), never hand-written. Concept illustrations (the checks diagram, the hosted-versus-library diagram) may be drawn by hand in `build.mjs`, as long as they are labelled as illustrations and keep to the same thin lines, mono labels and state colours. The CSP forbids inline styles and scripts: no `style=""` attributes, all CSS in `site/src/style.css`, script only in `site.js`, `theme.js`, `search.js` (the docs search, whose index `build.mjs` writes as a script), and the analytics script. Motion is CSS, starts when `site.js` sees a figure scroll into view, and is off under `prefers-reduced-motion`. No gradients (the one exception is the logo mark's box in the header, by the owner's choice), no colour outside the states (the one exception is the language logos on the homepage install tabs, grey until hovered or chosen, by the owner's choice), glows, shadows, eyebrow badges or pills. `npm run dev:site` serves the site with live rebuild; `npm run dev:dashboard` serves a dashboard of dummy jobs.
- Deploys: once CI passes on a push to `main`, the deploy workflow runs `deploy/release-deploy` on the server via a command-locked SSH key. A push that touches only `site/` and `deploy/` runs only the commits, lint, and site jobs in CI (the packages' jobs skip), so a site or docs change deploys in a minute or two. Nothing is deployed until the repository variable `DEPLOY_ENABLED` is `true`.
- Releases: `npm run release -- <version>` (try `--dry-run` first) bumps every versioned file, runs the checks, builds the gem and checks its file list, commits and tags; it never pushes or publishes. A new package under `packages/` gets a row in both tables at the top of `scripts/release.mjs` (`VERSIONED` and `PUBLISH`); the script refuses to run without them.
- Commits: short messages, no attribution lines. Review the full diff before committing.
